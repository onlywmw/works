### coverage_status 三档规则

```
FULL   → 直接通过能力护栏
PARTIAL → 必须写明：未覆盖维度 + 风险(低/中/高) + 是否允许合main + 裁决人(设计师) + 裁决记录；缺记录打回
NONE   → 原则上「共享面变更 + NONE = 不允许合 main」
```

### 收口 PARTIAL 显式裁决记录（防「大家觉得应该没问题」）

`coverage_decision` 必须含六字段，关键四字段 decision(reason+merge_decision) / decided_by=设计师 / decided_at：

```json
{
  "coverage_status": "PARTIAL",
  "uncovered": "协议异常重连路径",
  "risk": "medium",
  "merge_decision": "approved",
  "reason": "当前变更仅影响 UI 注册层，协议路径未改动；已有历史回归覆盖",
  "decided_by": "设计师",
  "decided_at": "2026-09-01T10:00:00"
}
```

## 五、新发现（如实列出）

1. **共享面定义需共识**：MainActivity 注册表 / 工具面 / 协议·接口 / 全局数据结构 四项为清单初始范围，实际使用中若出现「改了大共享面但不在四项内」的单，需设计师评估扩展或明确不适用——已写入红线 24「任一」表述兜底。
2. **PARTIAL 的裁决记录归属**：`coverage_decision` 由设计师填（decided_by 字段锁定设计师），程序员交付报告里 PARTIAL 时该项应为空待设计师补；验收打回路径为「退回补裁决」而非程序员自行放行。
3. **与 P0-3 审验衔接**：审验员审验时可在 integrity_review 中对共享面单核对 `coverage_status` 是否齐（现为人工核查，自动化属 P2）。
