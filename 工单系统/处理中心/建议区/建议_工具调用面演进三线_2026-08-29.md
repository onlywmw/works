# 建议：工具调用面演进三线（Code Mode SDK / 描述按需加载 / 编排编译）——UPG-01 登记层的下游方向

**来源**：设计师 @2026-08-29（UPG-01 评审后灵感库对账）｜ **投放**：建议区 → 设计师评估转工单
**一句话**：UPG-01 的 ToolDefinition 登记层（三件套单源）是三条「更先进工具调用」路线共同的**数据前置**——批 1 施工时把登记格式按可机读契约做扎实，后续三线都是纯增量，不返工。

## 判断

1. **UPG-01 不被推翻，反而是三线共同前置**：Code Mode 的 SDK 提示节、按需加载的长文档层、编排 IR 的参数语义——全部消费「name/description/inputSchema/output 机读单源」，这正是批 1 收敛的东西。登记层做扎实 = 三线后续零返工。
2. **推荐落地顺序**：Code Mode SDK 生成（补 `:193` 半成品，dsh 有现成范式）> 描述按需加载（短描述常驻 + `tool.help` 长文档，直接缓解 UPG-01 §五 Token 账与精度稀释预警）> EvoC2F 编排编译（观察）。
3. **与 UPG-01 的接口**：批 1 验收的 ToolDefinition 契约即 SDK 生成的 schema 源；频次 Top 榜（批 2 顺带产出）同时是「code 模式默认暴露常用集」的输入。

## 建议处置

- 不单独立项插队——UPG-01 批 1/2 在施期间不扰动；
- UPG-01 批 3 收口或 Token 拍板触发时，**「Code Mode SDK + 描述按需加载」打包出一张新卡**（B 级方向借鉴，dsh 范式 + Skills 规范双实证）；
- EvoC2F 登记 C 级观察（编排 IR 等 executor 层稳定后再评）。
