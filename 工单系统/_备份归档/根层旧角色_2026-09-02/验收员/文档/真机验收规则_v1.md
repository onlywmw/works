## 一、角色与权限

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| **设计师** | 方案/工单设计 + **合 main（唯一）** | 需验收结论 + 全量绿 + 证据链完整 |
| **真机检验员** | 真机验收执行 | 不合 main（归设计师） |
| **验收员** | 出验收结论 + 标注「待设计师合 main」 | 不自行 merge/rebase |
| **程序员** | 施工、报 commit hash | 不验收自己、不合 main、不产验收结论 |

**铁律**：**所有合 main 只能由设计师执行**（含 rebase/冲突处理/ff-only）。验收结论必须带「待设计师合 main」标注；rebase 冲突处理要点写进结论，由设计师执行。

## 二、证据链铁律（验收产物的唯一格式）

1. **一断言一证据**：每条验收判据必须有对应证据——**截图 png + OCR 文本 txt 成对落盘**，无图不验收
2. **落盘路径**：`Desktop\MOV\工单流转中心\验收员\<日期>\<场景>\`；命名 `<场景>-<序号>-<动作>.png`
3. **OCR 通道**：本机 Windows OCR（`_tools/ocr_shot.py`，Windows.Media.Ocr）。中文有字间空格/个别偏差，**以截图为准**；英文/数字/结构可靠
4. **截图纪律**：截前 `KEYCODE_WAKEUP` 唤醒，黑屏截图不算；`exec-out screencap -p`
5. **工具**：`_tools/evidence_shot.sh <场景> <证据名>`（截图+OCR 一条龙）；`_tools/make_overview.py <日期>`（总览表 xlsx+md）
6. **总览表**：每轮验收必生成 `<日期>_总览.xlsx`（证据清单 + OCR 全文）
7. **总报告**：按 `_tools/验收报告模板.md` 填写，含逐项判据/证据/结论/缺陷/阻塞

## 三、验收流程

1. **定级**：L1/L2/L3，拿不准往高定（定错级 = 验收事故第一来源）
2. **五招**：不信自报信实物 / 变异测试杀 mutant / 假覆盖四形态对照 / 真机证据链 / 打回可施工
3. **固定四步**：`install -r` → `am force-stop` → 启动 → 测；装包后核对 `lastUpdateTime`
4. **三态结论**：✅ 过 / ❌ 打回（现象→根因→修法→复验，写到能直接施工）/ ⚠️ 阻塞（写明缺什么、就绪条件）
5. **缺陷分级**：P0 致命 / P1 严重 → 打回；P2 一般 → 带缺陷通过并登记；P3 轻微 → 记录不阻塞

## 四、合 main 规则

- 所有合 main 只归**设计师**；验收员/程序员不做
- 验收结论统一标注「**待设计师合 main**」
- rebase 冲突/重复行等处理要点，写进验收结论，由设计师执行
- 合 main 前要求：全量测试绿 + 证据链完整 + 无 P0/P1

## 工作顺序（多 agent 防撞，2026-08-16 定）

- **工单流转顺序**：设计师出单 → 程序员施工（登记上表）→ 验收员验收（代码层+真机层）→ 设计师合 main
- **合 main 单点**：只设计师合 main；同一时间一个 agent 执行（rebase/ff-only）；撞到→git 实证谁先完成→已完成方跳过、后到者确认不重复
- **合 main 前提**：全量绿 + 真机验收通过；**编译/测试 FAILED 必须停**（即使疑似文件锁先查真红），不得合
- **合 main 顺序**：真机验收通过优先 → 基础先合 → 文档类可先 → 真机受限项设计师核实后定
- **并发防锁**：同一文件/分支同一时间一个 agent（Windows 文件锁 + gradle 互锁）；多 agent 各用独立 worktree
