## TL;DR

**现状**：单仓库、单写点（设计师）、多 Agent（A/B/C 三线）并行，git 已承担基础同步；看板已实现「文件变化 → 自动刷新」单机自动化。
**问题**：多机并发写会撞（尤其 `工单表.xlsx` 二进制 git 冲突不可手工解）；watch 只在本机。
**推荐**：**阶段 1 不引入任何新服务**——「git 串行 + 单写点 + 表可重生成」已足够；**表是投影**（丢了可从库重建）→ xlsx 冲突**降级为无害**；**中央同步服务（方案 C）暂缓**（现在没到「异地高频并发编辑」的程度，避免过度工程）。

## 一、现状与边界

### 1.1 数据模型（E1 唯一权威）

```
工单库.md   ← 唯一真相（58 卡，每个 agent 更新自己的卡状态区）
    ↓ --sync（确定性投影，diff=0 校验）
工单表.xlsx ← 投影（可由库重建——非第二真相）
    ↓ 只读
看板 HTML   ← 展示层（E4，不写库/表；watch 自动刷新）
```

### 1.2 写点（现状红线）

| 角色 | 写什么 | 写点 |
|---|---|---|
| 设计师 | 全部（登记/验收/合 main 段）| 单一写点 |
| 程序员 A/B/C | 交付报告 + 分支 | 不直接写库卡（卡状态由交付后登记） |
| 验收员 | 验收记录 | 验收文件 + 收卡后登记 |
| 审验员 | 自动校验读 | 只读 |

**当前所有角色都在同一台机器**（开发机）——git 仓库是唯一跨机载体（有 origin）。

## 二、同步对象与冲突面

| 对象 | 形态 | 冲突风险 | 处理 |
|---|---|---|---|
| 工单库.md | 文本（可 git 合并） | 中（多 agent 同卡改写） | 单写点 + rebase 串行 |
| 工单表.xlsx | 二进制（git 冲突**不可手工解**） | 高 | **表=投影，冲突→丢弃冲突版从库重建**（--sync） |
| 交付报告/证据 | 文本/独立文件 | 低 | 每 agent 独立目录 |
| 验证产物（看板 html） | 生成物 | 低 | 自动生成，不入人工改 |
| 分支（feat/*） | git | 低 | rebase + ff（设计师合入） |

**关键洞察**：xlsx 是**整个同步链里唯一不可合并的**——但它的**可重生成性**让冲突从「灾难」降为「无害」：
```
检测到 xlsx 冲突 → 不手工解 → git checkout 任一版 → node sync-orders.mjs --sync（从库重建）→ diff=0 收敛
```

## 三、方案对比

### 方案 A：git 串行 + 单写点（现状强化）——推荐

**机制**：
1. 写任何共享文件前：`git pull --rebase origin main`（拉最新）
2. 写
3. `git push`
4. 冲突 = `rebase` 中止 → 看对方改了什么 → 人工裁决（低频应几乎不出现，因为单写点）

**代价**：零新增设施；全靠纪律。

**适用**：当前阶段（单机多代理 = 本质上是**同机并发**，Windows 文件锁其实是真实的串行化器）。

### 方案 B：本机同步服务（watch/sync 常驻）——已部分落地

**机制**：
- `board-watch.mjs`：文件变化（库/表 mtime）→ 自动重生成看板（3s 去抖）——**已上线**
- 可扩展：watch 到 git 层面（pull 发生 → 重跑）

**边界**：只解决「**本机文件变化 → 展示刷新**」，不解决跨机冲突。

### 方案 C：中央同步服务（多机真并发）——暂缓

**形态**（未来需要时）：
```
中央机（或 GitHub CI 轮询）
  ├─ 工件队列：各机 push 私有卡片段 → 中央合并 → 唯一权威库
  └─ 冲突仲裁：同卡片冲突 → 时间戳先到先得 + 人工裁决兜底
```
**收益**：异地多机可同时编辑。
**代价**：新服务、新故障面、新学习成本——**且**：现在所有 agent 都在同一台机（「多机」= 未来编剧）。

## 四、推荐路线

```
阶段 1（现在）：A（串行纪律 + 单写点）+ B（watch 自动刷新）——够用
阶段 2（异机出现时）：A + 「写前 pull 红线上墙」+ 冲突 SOP（xlsx 重建法）
阶段 3（真频繁并发编辑）：C（中央服务）——等痛点出现再立项（防过度工程）
```

**一票否决项**（为什么暂缓 C）：
1. 单机多 agent 的「并发」是**假并发**（Windows 文件锁已串行化）
2. xlsx 可重生成 → 最痛的冲突已经无痛化
3. 中央服务=新的故障源（丢了/挂了=全阻止）——现网络/依赖最小化原则违背
