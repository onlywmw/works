## 一、用户视角（这个功能给用户什么）

**一句话**：侧边栏「我的信息」升级为「**我的资产**」——从「一个装身份信息的大盒子」变成「**分类管理的个人资产库**」：凭据/照片/衣物各成类目、各看各的、各管各的；AI 按类目拿权限（帮你换装可以、碰凭据必审批）；以后新类目（视频/音乐/文档）即插即用。

**数据承诺**：现 vault 全部数据（条目/凭据/证件照）**原样迁移、加密不变、一张不丢**。

## 二、界面与交互设计（v2 核心新增）

### 2.1 入口与导航
- 侧边栏条目改名：「我的信息」→「**我的资产**」（icon：box→archive，沿用 Token 图标体系）
- 点击 → **资产首页**（Vue WebView 页，与设置页同栈同基建：mov-page-server 桥 + allowedPrefixes 加 `asset.`）
- 迁移完成前**兼容期**：老「我的信息」入口保留 30 天（进资产首页自动定位凭据类目+一次性迁移提示），期满移除
- **兼容期老入口只读（评审 2.1 方案 A 定夺）**：兼容期老「我的信息」入口为**只读快照视图**（展示迁移前数据+顶部提示「请前往我的资产管理」）——写操作引导至新入口。彻底消除双写一致性问题（方案 B 适配层双写被否：复杂度+30 天边界）

- **继承**：加密/审批/填充/删除全链（v1 credential 契约）；`👁` 明文查看走既有审批弹窗（only-once，UPG-61 语义）
- **证件照子页签视觉分隔**（评审小建议 1）：子页签标题下加一行小字「证件照与凭据同等安全等级」——强化安全感知
- **P0-3 证件照语义定死（三轮评审）**：证件照 = **kind=picture + securityClass=credential**——「kind 决定这是什么资产，securityClass 决定它有多敏感」（类型与安全等级解耦，架构终态原则）；普通生活照=picture+normal。由此派生全部安全行为：AI 读取/删除、MCP 可写性、only-once、安全中心计分均由 securityClass 派生；UI 证件照子页签保留（视觉归 picture 类目，安全归 credential 级）
- **删除语义显式化**（评审小建议 3）：照片/衣柜类目均走 5s 撤销（非敏感，「删除不打断用户」）；仅凭据立即+审批——类目差异显式写进各管理项 rules
- **新增（小升级点并入）**：
  a. **按平台分组**：credSet 的 platform 字段作分组键（分组视图 toggle 可关）
  b. **证件照管理子页签**：scanPhoto/setPhoto 产生的照片集中展示（看/重拍/删）——原散在条目里
  c. **到期提醒**：metaSchema 增 `expiresAt` 可选字段（OCR 已识别有效期，回填即得）；临近 30 天在资产首页凭据卡上标 ⏰——**到期检测=资产首页加载时实时计算，非后台轮询**（评审 2.3：用户主动打开时计算成本极低；推送通知留后续事件驱动）
- **删除语义不变**：普通条目 5s 撤销 / 凭据立即+审批（UPG-53 契约）

- **审批语义零变化**：凭据明文读取每次确认（only-once）、写类走确认门——升级不放松任何安全边界

首批 20 工具的 EffectSpecs 机制（四元组+保守缺省+回落）**直接复用**，新增按类目条目：

| 工具 | EffectSpec | 说明 |
|---|---|---|

## 四、迁移方案（vault→credential，数据零丢失）

1. **启动检测**：首启发现旧 vault 存储且 credential 类目未初始化 → 触发迁移
2. **迁移步骤**：旧条目逐条转 credential 资产（key→name、加密体按 P0-1 双路径迁移[首选密文零迁移]、metaSchema 补 platform/expiresAt 可选字段）→ 校验条数+抽样解密比对 → 原子切换（新存储生效）→ 旧存储**保留 30 天不删**（回滚窗口）
   - **P0-2 Migration Manifest 全量校验（三轮评审钉死——可证明的零丢失）**：
     - 迁移前生成 migrationManifest：totalCount / assetIds 全集 / sourceHash（密文字节 hash）/ metadataHash / payloadHash
     - 迁移后逐条验证：assetId 一一对应 + metadataHash 一致 + payloadHash 一致（密文搬运零丢失的证明恰恰用密文 hash——同一密文字节复制，hash 必等）
     - 三等式全过才算迁移成功：SOURCE_COUNT==TARGET_COUNT ∧ SOURCE_ID_SET==TARGET_ID_SET ∧ SOURCE_HASH==TARGET_HASH
     - 「抽样解密」保留为功能验证（可解性抽查）；hash 对账为完整性证明——两者互补，缺一不可
     - Manifest 本身入 Evolution Ledger（evolution.MIGRATION_VERIFIED 事件形态，evidence=manifest 文件指针）
   - **P0-1 加密迁移双路径（三轮评审定夺）**：
     - **方案 A（首选·密文零迁移）**：ciphertext 原样搬 + 保留原 KeyVault 密钥引用（mov_vault alias 纳管进 KMS/KeyVault 接口）。技术依据：VaultKeystoreCrypto=AndroidKeyStore 独立别名 AES-256/GCM 不可导出（:16-28 源码锚），与安全体系 v2.1 KMS「KeyVault(AES-GCM 不可导出)+主密钥封装」定义**同源同型**——现有实现即 KeyVault 首个后端，兼容性成立
     - **方案 B（仅换机/密钥轮换场景）**：受保护内存中解封装 → KMS 新密钥重新封装——**业务数据明文语义零变化、迁移过程不落盘明文**（AndroidKeyStore 不可导出密钥在内存中解密即用即毁）
     - **换机场景既有契约**：旧设备密文换设备不可解=按缺项处理（InfoVault 既有行为，非迁移缺陷）——与 v2.1「换机优雅降级」一致
3. **失败回滚**：迁移任一步失败 → 回滚到旧 vault 存储+入口不变（老路径保留），报错留痕
4. **幂等**：迁移标记位防重复执行；中断续跑
5. **验收锚**：迁移前后条数一致/抽样解密一致/加密可解/旧数据零丢失

## 十、MCP 资产访问治理 —— Asset Access Contract（v2.3 新增，四轮评审采纳）

> **定位修正（四轮评审核心结论采纳）**：v2.2 的 MCP 治理（mcpWritable+Gatekeeper+EffectSpecs）回答的是「**这个 MCP 能不能写入某类资产**」（能力门）；本节升级回答「**谁/哪个 MCP/看什么资产/哪些字段/什么条件/能不能带走/多久有效/怎么审计**」（数据权限）——两者叠加构成完整的 MCP 资产访问治理。**v2.2 文档不再宣称「MCP 资产治理已完整」**（此更正来自四轮评审单项 6.5/10 的诚实结论）。

### 10.1 MCP Trust Level（信任三级）

| 信任级 | 定义 | 资产读取 | 敏感资产 | 写入 | 外发 |
|---|---|---|---|---|---|
| **official**（官方/内置） | 随 App 分发/官方签名 | 按声明权限 | 可申请（走凭据级审批） | 按 kind | 受控 |
| **verified_third_party**（已验证第三方） | 签名/审核入库（机制位，MVP 先两级） | 按授权（scope） | **默认禁止** | 白名单类目 | 受控+审批 |
| **unverified_third_party**（未验证第三方） | 任意来源 | 最小权限（仅 metadata 投影） | **禁止** | **禁止** | **禁止** |

> **官方 ≠ 自动允许所有资产**——官方只是信任级更高，不构成绕过用户授权的后门（四轮评审强调，采纳为铁律）。

### 10.2 Field-Level Access（字段级访问——凭据场景定死）

```text
credential
├─ metadata：name / platform / expiresAt        → 可读（投影层默认给）
├─ identity：username                            → 受限（only-once 审批后给）
└─ secret：password（高敏感）/ otpSecret（禁止）  → 高敏感（only-once + NO_REMOTE_EGRESS）
```

权限从 READ/WRITE 细化为：`asset.read.metadata / asset.read.identity / asset.read.secret / asset.write / asset.export`。「帮我查淘宝账号」的返回形态由此唯一确定（默认只给 metadata 投影，identity/secret 需逐级审批）。

### 10.3 Egress Policy（数据外发控制——「看到」≠「可以带走」）

| 数据 | 外发策略 |
|---|---|
| credential.secret / otpSecret | **NO_REMOTE_EGRESS**（凭据明文永不出设备——红线） |
| credential.metadata | ALLOW |
| wardrobe.image / style | ALLOW_WITH_APPROVAL（逐次或 scope 内免重复问） |
| picture.image | ASK（逐次） |
| picture.EXIF | ALLOW |

**「允许 MCP 使用资产」≠「允许 MCP 把资产上传到它自己的服务器」**——两句话在契约里分开写。

### 10.4 Scope（授权粒度——类目 ≠ 授权）

授权结构：`{kind, assetIds[], fields[], actions[]}`——用户授权语义是「**这一件衣服可以给这个 MCP 用**」而非「从今天起可读整个衣柜」。scope 附 `expiresAt`（TTL）+ 用户可随时撤销（撤销后 MCP 再访问=拒绝+审计）。

### 10.5 Asset Access Contract（请求/决策契约）

```json
// 请求（MCP → Gateway）
{"serverId":"mcp.wardrobe","toolId":"wardrobe.apply_outfit","trustLevel":"verified_third_party",
 "assetRequest":{"kind":"wardrobe","assetIds":["wardrobe_001"],"fields":["image","color","style"],"action":"read"},
 "purpose":"virtual_try_on","egress":{"remoteTransfer":true,"destination":"tool-runtime"},"consent":{"required":true}}
// 决策（Gateway → MCP）
{"decision":"allow","allowedKind":"wardrobe","allowedAssets":["wardrobe_001"],"allowedFields":["image","color","style"],
 "expiresAt":"...","egress":"allow","auditId":"..."}
```

### 10.6 调用链（Data Projection 原则——MCP 永不触达存储）

```text
MCP Server → Tool Identity/Trust → EffectSpec → Asset Access Request
  → TrustGate → SecurityGate → ConsentGate → Scope Resolver → Field Filter
  → Egress Guard → Asset Projection（授权后投影） → Audit/Ledger
```

**铁律：MCP 永不直接触达 asset storage / credential ciphertext / KMS key / vault handle**——MCP 看到的只能是经过授权与字段过滤后的**数据投影**（如 `{platform:"微信", username:"138****5678"}`）。

### 10.7 落点与分批（不造第四套权限系统）

- Asset Access Gateway = EffectSpecs/SecurityGate/审批/Ledger **之上的资产数据访问编排层**——复用全部既有件（EffectSpec 三元组→字段映射/SecurityGate 判定/审批弹窗/Ledger 审计），非新权限体系
- **落批**：67-A（框架+迁移，纯本地）不含 Gateway；**67-B 改为「Asset Access Gateway + 衣柜类目+换装 MCP 接入」**——Gateway 先行，衣柜 MCP 作为第一个走 Gateway 的接入方（official 级试点）
- Trust Level 的 verified 层验证机制（签名/审核流程）为后续 subsystem（MVP 先 official/untrusted 两级，verified 留机制位）

---

### 10.8 审批 UI 与 Access Contract 强绑定（五轮细节①）

**铁律：审批弹窗展示的内容必须由 Access Contract 生成，逐字段同源**——禁止后台实际申请 image+style+metadata 而弹窗只写「允许访问衣柜？」的语义错位（后台申请面与用户批准面不一致=治理失效）。
- 展示字段映射：Contract 的 kind/assetIds/fields/actions/egress/purpose → 弹窗逐项人话渲染（大白话映射纪律同 UPG-53）
- 用户批准后：**grant 逐字段落盘**（批准内容=Contract 内容，一个字段不多不少）——审批 UI 与 grant 同源生成

### 10.9 grantId 与 auditId 职责分离（五轮细节②）

- **grantId = 用户批准了什么**（持久授权单元：kind/assetIds/fields/expiresAt——撤销/追踪/复盘的锚）
- **auditId = 这一次发生了什么**（单次调用的审计事件）
- 每次调用：auditId 关联 grantId——撤销 grantId 后所有关联调用即拒；复盘时「这个 MCP 为什么能拿到数据」一查 grantId 即答

### 10.10 Egress Guard 强制位置（五轮细节③——实现级红线）

**Egress Guard 必须位于数据投影之后、MCP 返回之前；仅依赖 Tool 自报 remoteTransfer=false 不得视为有效控制**——平台自己在数据通道上控制边界，不信 MCP 自述（不信自报哲学在数据外发域的落地）。

```text
Data Projection → Egress Guard →（仅允许的数据）→ MCP
```

MCP 自述的 remoteTransfer=false 只作辅助标注（审计展示用），控制权永远在 Egress Guard。
