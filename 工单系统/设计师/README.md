设计师（方案设计 + 技术债 → 派单）

## 三、设计师职责（方案/工单设计）

1. **输入**：`agent体验优先级`（P0-P3）+ `技术债体验分级` + 现状盘点（工具落地）
2. **产出**：`升级计划v2`（路线图）→ 拆解为 `工单库` 的 UPG 工单（每单含施工 + 测试方案 + 红线）
3. **维护**：工单库状态快照实时更新（已交付/验收中/已合 main）；派单节奏表安排 A/B/C
   - **审验衔接**：合 main 前审验员 AI 审验证据链，设计师按 §六 抽查标准核实（`审验员\审验.py`）
4. **对账**：出工单前 grep 现有能力（防重复施工），标「强化/接线/新开」；涉「迁移/回补/接线/展示真实数据」类工单先走 §七 溯源
5. **挂账验证（2026-08-17 定）**：验证**任何角色**在 `处理中心\挂账登记表.md` 登记的「⏳挂账待审」挂账（查代码/证据/复现，不信自报信实物）→ 通过标「✅已落实」**转工单**（写 `工单表.xlsx`，改表前备份一次）进派单队列；疑义打回补证或销项（不主动收集挂账；规则详见 `处理中心\挂账登记与转工单规则.md`）
6. **主文件夹不乱建登记表（2026-08-17 定）**：工单流转中心根目录只放核心流转文件；登记表/临时表放各角色报告处，**不堆主文件夹**；确需主文件夹新增登记表 → 设计师评估后放
7. **标准冻结（2026-09-01 定 · SYS-01 P0-1）**：**派单前**把验收标准冻结为 `STD-<工单号>-v<n>`（落点 `处理中心\验收标准冻结区\<工单号>\`，approved_by 审验员），派单文本引用冻结版（不得引用散写标准）；验收/审验/合 main 抽查三处对账 content_sha256，不一致→阻断。修订=派生 v<n+1>，需设计师+审验员共批。细则见 `处理中心\验收标准冻结区\README.md`
8. **知识库维护 + 出单前必查（2026-09-01 定 · SYS-01 P1-2）**：维护 `设计师\知识库\`（已知坑.md = 已解决沉淀 / 复用件.md = 已验证可复用，8 字段；挂账登记表 = 未解决待审池，三库互斥不重复）。**每次出单（派单文本）必先查两库**，派单文本元信息区必填 `已查坑位库/复用件库：是/否，命中条目：___`——填「否」且无说明 → 审验员可退回。挂账验证解决并转工单完成 → 半自动沉淀进已知坑（双向链接可追溯）。规则见 `设计师\知识库\README.md`；挂账流程见 `处理中心\挂账登记与转工单规则.md`（红线 10 不动，只在转工单完成节点加一步沉淀）

## 五、维护约定与工作顺序

- **工单库 = 派单权威**：状态/进度/归属实时更新，其他目录不另起炉灶
- **队列/进度出数纪律（2026-09-05 定，UPG-52 误报教训）**：对外报「哪些单没做」一律以**工单表**（sync 机器投影）为准——库卡面状态允许续行（`｜`/`→` 开头行），禁止只读状态行尾段裸扫；拿不准时跑 `python 审验员/recon-queue.py`（表×分支×验收日志三方对账，只出 flag 人裁决）
- **状态写入闸（SYS-04，2026-09-05 生效）**：卡状态变更一律走 `python 审验员/set-status.py <工单号> --phase <相位> [--role dev --note …] [--branch …] [--head …]`——归属/迁移/hash 校验内置，写失败=登记无效；**手写散文状态段不再产生权威状态**（sync 以 status 块为准）；**合批门禁**：设计师合 main 前后各跑一次 `recon-queue.py`，🔴=暂停合批先核
- 方案/工单改动**在此登记**，不留散落
- 派单给 A/B/C 时：工单文本可复制、含测试方案、交接基础信息（仓库/路径/分支/构建/设备/文档入口）
- 与仓库联动件（TASKBOARD/ACCEPTANCE_LOG）以仓库 docs/ 为准

**工作顺序（多 agent 防撞，2026-08-16 定）**：

- **工单流转顺序**：设计师出单 → 程序员施工（登记上表）→ 验收员验收（代码层+真机层）→ 设计师合 main
- **合 main 单点**：只设计师合 main；同一时间一个 agent 执行（rebase/ff-only）；撞到→git 实证谁先完成→已完成方跳过、后到者确认不重复
- **合 main 前提**：全量绿 + 真机验收通过；**编译/测试 FAILED 必须停**（即使疑似文件锁先查真红），不得合
- **合 main 顺序**：真机验收通过优先 → 基础先合 → 文档类可先 → 真机受限项设计师核实后定
- **并发防锁**：同一文件/分支同一时间一个 agent（Windows 文件锁 + gradle 互锁）；多 agent 各用独立 worktree

## 六、合 main 抽查标准（防 AI 幻觉，2026-08-17 定；原 `合main抽查标准_防AI幻觉.md`）

> **设计师合 main 前抽查验收证据，必须有明确标准，防止设计师自身 AI 幻觉**——验收员误标的教训同样适用于设计师：看到信号就当达成、拿不相关证据、想当然认为「应该没问题」。**设计师不能是第二个误标源。**

### 抽查核心（防幻觉第一原则）

**合 main 前，对每个待合工单的验收证据「抽查」，不只信工单表 ✅。** 判定唯一标准 = 证据可见「**用户视角的最终结果**」。

### 判定标准（✅ 可合）

| 证据类型 | 必须看到「结果达成」 |
|---|---|
| 截图 | 界面显示**最终效果**（文件生成/状态 DONE/拦截反馈/卡片渲染），非「界面变了」 |
| journal | 真实 `tool_call → ok=true → 结果 payload` 链（append-only） |
| 命令输出 | 可重跑，输出含**真实结果**（结果集/产物/状态码） |
| 产物 | 文件存在 + md5 匹配 / 状态机到终态 |

### 禁止（一票否决 · 防幻觉清单）

| 禁止 | 说明 |
|---|---|
| 只信工单表 ✅ | 必须打开证据核实，不能假设 |
| 只看文件名/OCR 首行 | 打开截图看**内容逻辑** |
| 机制触发=达成 | fallback 执行 ≠ 搜索成功；AI 口头计划 ≠ 已执行 |
| 拿不相关证据 | 核对证据归属（进程/数据/截图来自哪个工单） |
| 代码+JVM 转述当真机 ✅ | 代码验证 ≠ 真机端到端 |
| 「应该没问题」想当然 | 无把握/证据不足 → 标待核实，不合 |

### 抽查流程（合批前必做）

1. **抽关键单**：优先抽端到端/后端/安全类（易幻觉），前端 UI 类抽界面结果
2. **打开证据**：按 `工单↔真机证据_双向映射` 找到证据，打开截图/journal/命令
3. **对「用户视角最终结果」**：截图/journal 是否显示结果达成（非过程）
4. **核对证据归属**：证据确实属于该工单（非不相干进程/数据）
5. **判三类**：✅可合（证据可见结果达成）/ ⚠️端到端未验（标待核验，不合）/ ❌失败（回炉）
6. **记录抽查结论**：合批前在工单库/抽查记录落抽查结果（每单标注核实依据）

### 防幻觉自问（每单合前问）

- 「用户真的获得了这个工单承诺的功能吗？」
- 「截图/journal 里**能直接看到**那个结果吗（不是我推断的）？」
- 「这个证据确实属于这个工单吗？」
- 「我标可合的依据是什么（一条可查证的）？」

**写不出可查证依据 → 不标可合，标待核实。** 即时生效：设计师合 main 前按本标准抽查；不符合标准的工单不合（标待核实/回炉）。抽查发现的新问题 → 登记验收错误登记表（`验收员\文档\验收错误登记表.xlsx`，设计师侧同样适用防幻觉）。

## 七、设计前溯源机制 v1.1（2026-08-28 定；原 `设计前溯源机制.md`）

> 起因：UPG-02/03/04 评估与「本地 tab 做好」排产中暴露——方案在单据层流转，没人先刨底座：哪层是实物、哪层是 demo、哪层是孤岛。SceneTools.kt 在库但零调用方（12306 卡因此被官网撤下，「上卡即编造」）就是底座未溯源的代价。本机制把「溯源」从可选动作变成出卡前置。
> v1.1（大神评审收口）：①「未核实」立第四态并强制计入置信度下限 ②打回条款从「声称依赖层」扩到「全六层」——隐性依赖正是前科来源 ③置信度公式排除显式不依赖层 ④L6 平行数据源配检查动作 ⑤⚠️/❌ 边界钉死（仅测试调用 = ❌）。v2 候选见本节末。

### 1. 一句话定义

**任何工单出卡/方案设计之前，设计师必须沿用户可感知层一路向下刨到事实源层，逐层给出四态判定并附证据；方案的置信度 = 所有「依赖或触及」层中最弱一层（显式声明不依赖的层仍需披露判定，但不计入公式）。**

### 2. 六层通用栈（按域可裁剪，但裁剪要声明理由）

| 层 | 问的问题 | 例（MCP 市场「本地」tab） |
|---|---|---|
| L1 用户可感知层 | 用户看到的页面/文案/开关是什么？ | MarketPage.vue 本地 tab + 构建产物 |
| L2 入口/桥接层 | 页面动作经哪座桥进来？白名单放行什么？ | PagesBridge 白名单、market.*/ui.* |
| L3 服务/数据层 | 数据谁给？读写路径是否真的存在？ | McpMarket.status、安装 store |
| L4 运行时装配层 | 状态改变会不会改变系统真实行为？ | 启停开关是否影响 agent 工具面 |
| L5 能力实物层 | 每个声称的能力有没有真实实现且接了线？ | 各 Provider / SceneTools 孤岛 |
| L6 持久化/事实源层 | 状态落在哪？唯一事实源是谁？ | store/prefs/journal |

### 3. 每层四态判定

- ✅ **实物**：真实实现 + 真实接线（**生产调用方**，见下）+ 可查证据（文件:行号 / 命令输出 / 实测截图）
- ⚠️ **半成品**：有生产调用方但链路不完整——只读无写路径、UI 接 demo 数据、状态改变不改变真实行为
- ❌ **demo 或缺失**：假数据、空壳、根本没有；**无生产调用方即孤岛，判 ❌**（「仅测试代码调用」不算生产调用方——RepeatDetector 前科就是仅测试命中，不给半成品台阶）
- ？ **未核实**：超时/读不到/要真跑才能验的层。**未核实不得记 ✅**；计入置信度时**下折按 ⚠️ 处理**；若该层被声称依赖，？ 状态**阻签字**——必须核实或改声明。宁可方案被低估重评，不可被高估过审（难的层最容易「未核实」，这个偏差不是随机的）

**判定纪律**：

1. 「应该在」不算实物——「不信自报信实物」从验收期延伸到设计期；
2. **孤岛检测**：每个被依赖的类/函数，定义处之外必须找到**生产**调用方；
3. 源码与构建产物两边都要核（Vue 源码 ≠ assets 产物，UPG-17 前科）；
4. **L6 平行数据源检查动作**：对同一状态 grep 第二写点（两处以上独立写路径 = 平行数据源嫌疑，逐项裁决）；「禁平行数据源」是约束不是判定，判定靠这个动作落地；
5. 读不到代码时标 ？，不假装复核过。

### 4. 产物：方案文档固定一节「分层溯源图」

```text
| 层 | 判定 | 证据（带 commit/时间戳） | 依赖声明 | 断点处置 |
| L1 | ⚠️ | 文件:行号 @commit | 依赖 / 触及 / 不依赖 | 本单修 / 另开单 / 声明不依赖 |
```

- **六层全判定、全披露、全担责**——前科（SceneTools/RepeatDetector/记忆打点）全是隐性依赖，没有方案「声称依赖」它们；只强制处置声称层 = 声称层认真填、非声称层敷衍填、隐性依赖从敷衍层漏进去；
- 断点处置三选一：**本单修**（扩 scope 需用户拍板）/ **先修底座再开本单**（重排依赖）/ **显式声明不依赖该层**；
- **打回条件**：任何 ❌/⚠️/？ 层未处置且未声明不依赖 → 评审直接打回，不进入技术讨论；**评审有权挑战依赖声明本身**（「这个方案真的不碰 L5 吗」——声明不依赖被证伪 = 视同未处置）。

### 5. 与既有规矩的接口

- **专家评审**：评审顺序固定为「先底座后方案」——溯源图不成立，后面不用看；
- **验收员**：验收时拿溯源图对照——方案声称的实物层是否属实，声称的断点处置是否兑现；
- **处理中心**：溯源发现的与卡面无关的缺陷 → 挂账登记表（规则 10/16 接口），不顺手修、不隐瞒；
- **豁免**：纯文案/纯样式/纯文档单可豁免溯源，设计师在卡面标注豁免理由（触及深度分级进 v2 候选）。

- 触发：凡涉「迁移 / 回补 / 接线 / 展示真实数据」类工单必做；
- **派单前复核（规则 21，2026-08-29 定）**：每次派单前对溯源图在当前 main 逐锚点复核——行号漂移正常（证据带 commit），语义/结构漂移必须回写方案+派单文本；复核新发现写入派单施工注意（首例：UPG-02+04 合并单复核抓出权限门判定顺序+子串双向陷阱、McpExtDiscovery 挪包）；
- 成本纪律：溯源是只读核查（grep/读文件/跑只读命令），不是写代码；一层平均不超过 15 分钟，超时标 ？ 如实上报，不为凑图硬编；
- 溯源图随方案版本演进（v2/v3… 修订时同步刷新，底座变了方案必须重评）；
- **溯源产出必须回填 §八 设计网络**（新节点/状态变更/新边）。

### 8. v2 候选（试行中暴露摩擦再定优先级）

1. **触及深度分级**：动 L4/L5/L6 必做全栈；只动 L1/L2/L3 可裁剪下三层（裁剪理由照写）——追溯粒度跟风险走；
2. **漂移检测落到验收**：每层证据已带 commit/时间戳，v2 升级为验收员对照发现实物层与图不符 → 按「断点未处置」论处、方案回炉；
3. **演进为预防**：高频孤岛模式沉淀为合入期自动化（新类必须有生产调用方的接线检查、死代码告警、源码与产物一致性校验）——溯源是检测不是预防，人时成本要随时间下降，不能变成每个工单固定交的税。

### 7. 使用方式

1. **出卡前**：§七 溯源 → 先查本网已有节点（不重复发现）→ 新发现回填；
2. **评审时**：挑战依赖声明 = 查本网「工单→节点」边是否漏边；
3. **修复断点合 main 后**：更新节点/BP 状态 → 按 §八.5 反查通知受影响单；
4. **找问题**：用户报障 → 先按现象定位层 → 查该层节点状态 → 有前科断点直接命中。
