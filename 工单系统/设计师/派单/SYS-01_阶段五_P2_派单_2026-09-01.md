## 三、目标：三档优先级自动化（方案 P2-1）

### 第一优先（客观、可脚本判断）

1. **`--ticket` 主链路交付联动**：读工单表 delivery_id 列绑定值 → 重算 `evidence_manifest_sha` 比对绑定值，不一致标「⏳失效」。（补 P0-2 主链路实证）
2. **`--ticket` 主链路时序判断**：读真实 journal + 截图时间 → `time_inconsistency` flag。（补 P0-3 主链路实证）
3. **能力护栏自动核验（P1-1 自动化）**：审验.py 读交付报告「能力护栏」节 → 自动判 `coverage_status`：
   - NONE → 标「禁合 main」flag
   - PARTIAL → 核 `coverage_decision` 六字段（uncovered/risk/merge_decision/reason/decided_by=设计师/decided_at）；**缺字段或 decided_by≠设计师 → 标「打回」flag**（B/C/D 从人工判变机器判）
   - 机器只出 flag，是否放行由验收员/设计师裁决
4. **截图紧凑格式时间戳**：正则补 `YYYYMMDD_HHMMSS` / `YYYYMMDD_HH-MM-SS` 变体，识别 `20260829_220000`。（补阶段二①）
5. **坑位库查询字段核对（P1-2 自动化）**：审验.py 读派单文本「已查坑位库/复用件库」字段 → 缺失或"否"无说明 → flag「退回」。（与 P0-3 同机制）

### 第二优先

6. **截图 OCR / 时间一致性比对**：对界面对账类目增强。

### 保留人工（机器不做）

- 最终是否达标判断
- 边界仲裁
- 语义模糊化深度审（semantic_vagueness 保持 flag+signal 启发式，不追求机器语义判定）
- 共享面无副作用合理性

## 四、验收标准（阶段五 L1）

| 项 | 标准 |
|---|---|
| A | `--ticket` 对**一个真实/构造工单**（含 delivery_id 绑定）跑通：绑定 hash 一致→正常，篡改→标「⏳失效」flag |
| B | `--ticket` 主链路：构造 journal 时间晚于截图的证据 → `time_inconsistency=true`（主链路，非 --dir） |
| C | 能力护栏自动核验：读「coverage_status=NONE」→ 禁合 main flag；「PARTIAL 缺 coverage_decision」→ 打回 flag；「PARTIAL 六字段齐」→ 通过 flag |
| D | 截图紧凑格式 `20260829_220000` 能被正确识别时间并参与时序判断（补正则） |
| E | 派单文本缺「已查库」字段 → 审验.py 标「退回」flag |
| F | **红线不破**：机器只出 flag 不判结论；人工裁决 `integrity_review` 仍在；不新增机制/角色/评分体系；不碰工单表 UPG 主线 |
| G | 全量回归：既有审验.py 功能（--list/--ticket/--manifest/--dir）不回归 |

> 验收重点：A/B/C 是补主链路实证 + 把 P1-1 的 B/C/D 从人工判变机器判，是 P2 的增量核心；D/E 补之前暂缓项。
