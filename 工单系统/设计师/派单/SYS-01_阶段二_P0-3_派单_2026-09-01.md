## 四、目标：P0-3 两层分离 + 审验.py 落地

### 层 A：行为欺骗（Behavioral Suspicion）—— 四分类，机器出 flag 不当结论

| 类别 | 检测信号 |
|---|---|
| ① 原样重跑 | 交付分支 vs 工单表登记 hash，diff 空/极小，仅时间戳/窗口变化 |
| ② 基准过拟合 | 测试代码引用基准/产物本身；断言只查"存在"不查语义；覆盖率高但断言弱 |
| ③ 语义模糊化 | 报告描述与代码行为不一致；"已支持 X"但 X 只被 mock/固定值 |
| ④ 时序不一致 | 截图/日志时间早于工具调用；虚假时间戳 |

### 层 B：证据对象真实性（Evidence Integrity）—— 独立层，不混入四分类

```
file exists / hash matches / timestamp plausible / producer known / source path valid / chain intact
```

### 人工最终裁决（机器只出 flag，人判结论）

- `integrity_flags`（机器）→ `integrity_review`（人工）
- `status: confirmed / cleared / unresolved`；`reviewer / reviewed_at` 必填
- **关键约束**：`integrity_flags` 绝不自动等价"不通过"，最终判定由人工完成
- `unresolved` 必须归属退出：超时（3 工作日）→ 转挂账待设计师定夺（防永久挂起）

## 五、审验.py 功能清单（P0-3 落地）

1. 新建 `审验员\审验.py`（替换全部缺失），保留 `--ticket / --list / --json` 接口
2. 输出加 `integrity_flags` 字段（四分类枚举）：`original_rerun / benchmark_overfit / semantic_vagueness / time_inconsistency`
3. 输出加 `integrity_review` 字段（人工裁决，默认空，由人工填）
4. **P0-2 对接**：hash 自动比对——读取工单表 delivery_id 列的绑定值，对 `evidence_manifest_sha` 重算比对绑定值，不一致 → 标「⏳失效」提示
5. Evidence Integrity 检查（层 B）：file exists / hash matches / timestamp plausible / producer known / source path valid / chain intact
6. 证据链四环节对账（证据链规范 §一）：journal / 截图(含时间戳) / 命令 / 时间一致性

| 项 | 标准 |
|---|---|
| A | `审验.py` 可在工单系统内运行；`--list` 能列出有证据工单；`--ticket` 能对单工单输出 `integrity_flags + integrity_review` 字段 |

| C | 构造「报告描述与代码不符」证据 → `semantic_vagueness` 能识别（或至少给出可复现判断路径） |

| E | 错误处理：无证据目录/无工单表/文件缺失时输出友好错误，不崩溃 |
| F | 不破坏既有：不新增文件到 APP 仓库，不新增机制/角色/库，不碰 `工单表.xlsx` UPG 主线 |

> 验收重点：B/C 两项手动构造边界用例是抓「真做了 vs 口头说」的锚（对应论文"监控抓作弊"），**保留为验收硬项**——这是本方案相对既有"只验证据缺"的核心增量。
