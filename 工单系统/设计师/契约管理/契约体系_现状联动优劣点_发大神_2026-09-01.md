## 四、优劣点分析

### 4.1 强项（系统级）

1. **三层垂直拆开**：Token（值）→ 换皮（形态）→ 换芯（本体）——「UI 可插拔」的地基干净，大神 9.1；
2. **注册制模式已验证**：AssetKind（67-A）→ UIComponent（v4.1）同构落地——「注册即用/替换不破坏」被实测过；
3. **安全红线家族一致**：不信自报/白名单登记/审批门——三条契约（CT-06/07/08）同一个哲学，无互相矛盾；
4. **审计可复用**：TimelineLedger 已验，流转/切换/蒸馏留痕不重造；
5. **契约与验收绑定**：每契约带判据（L1/L2/L3/变异锚），不是纯文档。

### 4.2 弱项 / 风险（系统级）

| # | 弱项 | 证据 / 风险 |
|---|---|---|
| W1 | **结构契约多、流转契约缺** | 所有流转=点对点单跳（胶囊→工具/输入→MCP/资产→填充）——**项目哲学五线型（直通/映射/转换/合并/分流）零契约覆盖**；模块是「库存」，不是「动脉」 |
| W2 | **契约一致性靠人工** | BP-03 同型**两度漏网**（approval.setMode、personalization.setEnabled 漏登记白名单→else 静默 ALLOW）——名单纪律依赖人+变异，无自动化防线 |
| W3 | **验证有自动化盲区** | 状态矩阵（CT-02/03）机器查对比度 OK，但 L2 真机可用性/多步 UI 链路**依赖人工**（历史多次人工补验）；C7 基线生成器非确定性（每次跑产出噪声 diff） |
| W4 | **文档版本管理分散** | 每契约 v1→v2→v3 新文件堆叠（01_外观 5 文件），溯源清晰但**单入口难搜**——契约管理目录（2026-09-01 建）刚解决入口，版本间差异仍靠人肉 |
| W5 | **边界重叠风险** | ①隐私 V1.1 文档 vs app 内 V1.2 文本（文档滞后）②UPG-40 换肤标准 vs CT-02 换皮（内容重叠，互有引用）③CT-10（资产审批链）与 CT-06（审批授权层）边界部分交叉 |
| W6 | **契约尚未机器可读** | 全为 Markdown；契约核心（props_schema/白名单/形态 ID）**无单一程序化权威**——代码与文档靠人肉对齐（W2 的深层原因） |

### 4.3 机会（顺势）

- **DataFlow Contract（CT-13+ 流转契约族）**：五线型通道契约化——「软件活起来」的关键（用户方向，底稿已备）
- **契约机器可读化**：先挑 1-2 条（如 CT-03 ComponentContract / CT-07 白名单）沉淀为 JSON Schema/TS 类型——文档 + 代码同源生成
- **契约一致性自动化闸**：新 handler 注册即校验名单（BP-03 自动化防线，v2 候选已有）；CI 门禁四层（V4-5'）模式推广到其他契约

## 五、优化管理建议（请大神评审裁决）

### 5.1 契约分层治理（建议）

```text
L1 结构契约（已 12 条→持续增）   —— 是什么/可换什么
L2 流转契约（CT-13 起·待立项）   —— 怎么流（五线型）
L3 治理契约（新层·建议）        —— 契约怎么写/怎么验/怎么改（元契约）
```

### 5.2 治理机制建议（四件）

| # | 建议 | 对应弱项 |
|---|---|---|
| G1 | **契约机器可读化**：每条契约的「核心可机读部分」（schema/名单/形态 ID）单源生成，代码引用生成物（如 `docs/ApprovalRegistry.json` 模式推广） | W2/W6 |
| G2 | **一致性自动闸**：注册即校验（新工具/新 handler/新组件注册时契约校验器自动跑，破契约=CI 红） | W2 |
| G3 | **版本台账标准化**：契约管理目录做**版本演进表**（每契约 v1→当前 的变更记录单页），不再靠翻目录 | W4 |
| G4 | **边界消歧评审**：隐私/V1.2 文本同步、UPG-40↔CT-02 合并指针、CT-10↔CT-06 交叉点划清 | W5 |

### 5.3 优先级建议（草案）

1. **G1+G2**（机器可读+自动闸）——治本 W2（人工漏网是 P1 级风险）
2. **L2 立项**（DataFlow Contract）——用户方向 + 弱项 W1
3. **G3+G4**（台账+消歧）——低风险整理，随手做

## 七、大神评审采纳记录（2026-09-01 · 全部采纳+2 微修正）

> **大神结论**：结构契约健康（无问题）；**「12 条管的是零件合格证，没有一条管装配线」**——W1 比我自诊更严重；方案核心=«不要为治理而治理，每个治理动作直接消灭一个已知风险»。

| 裁决 | 大神方案 | 设计师定夺 | 微修正 |
|---|---|---|---|
| Q1 流转 | **不立 CT-13 族**——五线型=Flow Patterns 分类学，嵌回现有契约「Flow Spec 小节」+台账「流转矩阵」；立即=直通+映射，合并/转换/分流随用例 | ✅ 全采纳（纠正我 CT-13 立族方案——避免契约套契约层次混乱） | 无 |
| Q2 元契约 | 不设 L3 文档——治理规则=校验器+模板+台账规则三种形态（防无限递归） | ✅ 全采纳（与「契约=规则+实现+验证」三件套同哲学） | 无 |
| Q3 先后 | **CT-07 白名单开路**（W2 直接现场，半天 ROI 最高），CT-03 第二步 | ✅ 全采纳（CT-07 数据结构天然 JSON；CT-03 八字段复杂度高一个量级） | **复用现有生成物**：不新建 docs/contracts/approval_registry.json，改为给现有 docs/ApprovalRegistry.json（代码已 collect 173 工具面）加 schema 文件+字段对齐（防第二份双源——契约管理本身要防的） |
| Q4 两步走 | 第一步=机读部分权威源生成+md 引用；设计意图/判据/变更历史仍手写；第二步（写代码即写契约）后续再评估 | ✅ 全采纳（一步到位会丢设计/评审上下文） | 无 |
| G1/G2 | **合并落地**——一个校验器+一个 registry 文件=最小闭环（G2 不是独立项） | ✅ 全采纳（我原拆两件，大神纠正） | 无 |
| G3 | 生命周期状态（draft/proposed/ratified/deprecated/retired）+ 变更影响矩阵 | ✅ 全采纳（现在口状态混用=✅定稿/✅工程契约/✅收敛版——统一化） | 兼容期「2 版本周期」的周期定义落地时明确（vN→vN+1 或工单批次） |
| G4 | 三消歧动作（隐私 app 内权威/UPG-40 上游/CT-06 管权 CT-10 管物） | ✅ 全采纳（CT-06 管理操作授权、CT-10 管资产登记——边界划清） | 无 |
| **新增 退役策略** | deprecated 后保留 2 版本周期兼容期；新实现禁依赖 deprecated，旧实现可运行 | ✅ 全采纳（12 条契约只增不退役=真实缺口；一行规则） | 见 G3 微修正 |

### 修订后优先级（大神版 · 采纳）

**P0** CT-07 白名单机器可读化+CI 注册校验（W2 P1 安全风险，半天）→ **P1** 流转矩阵+Flow Spec 直通/映射（W1，1-2 天）→ **P1** 生命周期+影响矩阵（W4，1 小时）→ **P2** 消歧三动作（W5）→ **P2** CT-03 机器可读化（W6，中）→ **P3** 合并/转换/分流随用例（W1 余量）
