# MOV 改造计划 验收标准 v1.0（大神评审稿）

> ⚠️ **本文档已并入合并版**：`工单方案\改造计划+验收标准_合并版_AHE×EvoC2F_2026-08-31.md`（用户拍板合并，2026-08-31）。合并版为唯一权威阅读版（判据编号 Z-/M-/B-/C-/D-/V-/X- 以合并版下篇为准）；本文保留作评审历史溯源，内容不再更新。

> 依据：设计计划 v1.2（含二轮评审 4 P0）+ 三轮评审地基补充。本标准不新增设计决策，只把已定夺项转译为**可执行、可证伪、可留痕**的查核项。设计里没定夺的事（裁决权、漂移校准）不藏在验收里偷偷定，而是作为「开工准入项」强制拍板。

## 〇、总则与判定规则

**验收原则（四条，违反任何一条的判据视为无效判据）**：

1. **每条判据三要素齐全**：验收对象 / 验收方式（一次可执行的操作）/ 通过标准（可证伪的边界）。禁止「已实现」「已优化」「基本完成」类表述。
2. **工具先于文书**：凡能用脚本/测试/钩子自动查的，不设人工审查项；人工审查项必须显式标注 `[CR]`（code review）并写明看什么。
3. **fail-closed 优先**：契约类校验（baseline 五元、教训六字段）缺一即拒，不允许 warning 降级通过。
4. **诚实降级 = 通过的一种形态**：JS 工件类拒收、D 线降观察项、门 3 人工触发版，均为合法交付形态——但必须在 Evolution Ledger / 工单留痕。**静默缩水 = 打回**。

**判定分级**：

| 级别 | 含义 | 后续动作 |
|---|---|---|
| ✅ 通过 | 全部判据过线 | 合入，Ledger 记 ACCEPTED |
| ⚠️ 有条件通过 | 存在缺口但已登记：缺口内容 + owner + 期限 | 缺口进工单系统，Ledger 记 ACCEPTED + 缺口引用 |
| ❌ 打回 | 触发一票否决项（§九）或核心判据未过 | 打回，Ledger 记 REJECTED + 理由 |

**验收体系分五层，顺序不可颠倒**：开工准入（§一）→ 元验收：验门本身（§二）→ 组件级验收（§三–六）→ 横切验收（§七）→ 里程碑终审（§八）。**元验收未全过，任何门不得放行真实候选**——这是本标准最重要的一条顺序约束。

## 一、开工准入验收（阶段零，全部通过才开工）

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| Z-1 | 评测集盘点报告 | 同代码、同 fixture、同环境重跑评测 ≥10 次，记录六指标逐次原始值，产出规模/确定性/方差三属性报告 | ① 报告落档；② **门 2 阈值参数必须从本报告推导**：若评测含真实模型调用且指标抖动 2σ ≥ 1 条用例翻转量，门 2 过渡阈值（「下降 ≥2 条」）复核上调，或评测固定 seed/温度归零；③ 报告明确回答 EvalFixture 是否含真实模型调用（决定六指标覆盖面是管线回归还是模型行为回归） |
| Z-2 | 模型漂移校准定夺 | 决策评审：对照组方案（每次 delta 同跑 main HEAD 无改动对照，判定=差中差）vs 定期基线重跑，二选一拍板 | 决策记录落档 + 实现排期进第一阶段任务卡；不拍板不得开工 A-1 |
| Z-3 | 元验证坏改动构造 | 人工构造 3–5 个**已知必然回归**的坏改动（例：改坏高频工具 schema 校验、desc 反向改写），**先记录预期 delta 方向，再执行** | 坏改动集落档且预期方向已预登记（防事后拟合）；供 §二元验收使用 |
| Z-4 | fixture 扩充认领 | 任务卡：≥40 条目标的来源拆分（B 线反哺 X 条 + 人工撰写 Y 条）、owner、排期 | 任务卡存在且有人认领；否则门 1 切百分比阈值的时点（P0-2）无主，A-2 二阶段不得开工 |

## 二、元验收：验门本身（在任何门放行真实候选前完成）

> 依据：三轮评审第 3 条。六指标是全 MOV 唯一自动化回归底座，门站在它肩上却无人验门。「门只会拒不会放」和「门拦不住」同罪。

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| M-1 | 门 2 拦截力 | 用 Z-3 坏改动集逐个走门 2 | 全部被拒，且**拒绝理由中的指标下降方向与预登记的预期方向一致** |
| M-2 | 门 1 拦截力 | 构造必然失败候选（错误注入用例不过）走门 1 | 被拒，拒绝输出含失败用例定位 |
| M-3 | 门放行力（防全拒门） | 构造干净候选（已知全部用例通过）走门 1 + 门 2 | 双门放行。若干净候选也被拒，说明阈值过紧形同虚设，打回调参 |
| M-4 | baseline 五元触发器 | 单独改动五元中任一元（如升 eval_fixture_version），运行 A-1 脚本 | 脚本报 baseline 失效并拒发（fail-closed 实测），**不是**提示后继续。逐元测五次 |
| M-5 | 判定独立性 `[CR]` | 代码审查门 2 判定输入 | 判定输入不含 manifest 的 risk_tasks / 任何自述字段（红线 1「只信独立重跑」的落地） |
| M-6 | actor 权限 | 以 AI 身份触发候选产出，检查 Ledger 写入 | 只能写 PROPOSED 事件；越权写 ACCEPTED 直接失败（TimelineLedger ACTOR_ALLOWED 实测） |

## 三、A 线验收

### A-1 Manifest 脚本化（交付物是工具，不是文书）

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| A1-1 | 脚本自动化 | 工单提交/验收流程演练：提交时自动跑 baseline 快照，验收时自动跑 delta 对比 | 全程无人工执行步骤；脚本 ≤20 行（超限需书面放宽理由）；输出自动贴入工单 |
| A1-2 | 输出格式 | 检查工单产物 | 含 predicted_fixes（≥1 条）/ risk_tasks / baseline 五元完整字段，缺元脚本拒发 |
| A1-3 | 交叉验证语义 | 提交一个 predicted_fixes 声明与实际 delta 不符的工单 | 脚本输出「预测未命中」标记——验证器做对拍，不是复读开发者声明 |
| A1-4 | 漂移对照（若 Z-2 选对照组方案） | 在模型静默变化条件下跑 delta（或 mock 之） | delta 判定=改动组 vs 对照组差中差；无改动对照组自身漂移超阈 → 产出「环境漂移事件」进 Ledger，不误判为代码回归 |
| A1-5 | 降级路径 | 半自动版演练：开发者自跑脚本 + 验收员抽 1–2 条 predicted_fixes 对拍 | 抽检记录留痕（抽了哪条、对拍结果）；无留痕视为未执行 |

### A-2 三道门

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| A2-1 | 门 1 阈值 | 13 条用例现值下运行 | 绝对错误数阈值「≤1 条失败」生效；切换条件（fixture ≥40 条）配置化，切换发生时产生 Ledger 事件（P0-2） |
| A2-2 | JS 工件类拒收 | 提交一个 JS 工件类候选 | 直接标「不可准入」，零人工解释、零 JVM 重放执行（Q2 定夺的落地） |
| A2-3 | 门 2 held-out | 检查 held-out 划分 | 划分固定、版本化并进 baseline 五元（否则改划分=改基线） |
| A2-4 | 门 3 会话级灰度 | 构造 N 会话 shadow 计数 | 计数**持久化**（非内存态）；转执行迁移产生 Ledger 事件 |
| A2-5 | 门 3 退化回退 | 灰度期间注入高 isError / fabricate_hit 信号会话 | 自动回 shadow + Ledger 记 DEGRADED/ROLLED_BACK。若 B 线蒸馏信号未就位，第一版人工触发可接受，但**必须在交付物上标注「人工触发版」** |
| A2-6 | 生命链同构 | 全程走一个编排类候选：PROPOSED→门过→shadow→canary→stable | 状态迁移全部落 Ledger 且 actor 权限正确；终态可在 Ledger 单查询回答「此技能处于什么状态、为什么」 |

### A-3 Judge 扩判别面

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| A3-1 | 三类判定 | 数值/枚举/包含各 ≥1 正例 + 1 反例 | 正例判是、反例判否均正确，且**判否结果同样落 journal**（对拍失败也是数据） |
| A3-2 | 触发降级 | 构造「只有核对类动词、无标准指定短语」消息 | 提取结果 null（诚实降级），不硬猜 expected |
| A3-3 | 观察层语义回归 | 跑既有 AcceptanceJudge 测试 + expected 不投影检查 | 全绿；expected 不进模型上下文语义不破；不拦截、不阻断流式上屏 |
| A3-4 | 对拍反哺管道 | 端到端跑一条用户对拍数据 | 出现在门 2 回归集输入中且可审计溯源（≥1 条完整样例） |

## 四、B 线验收（根因蒸馏）

| 编号 | 验收对象 | 验收方式 | 通过标准 |
|---|---|---|---|
| B-1 | 三分类正确性 | 构造三类 gold JSONL fixture：超时重试链 / 业务拒绝（不可重试）/ fabricate_hit 事件（用 AgentLoop.kt:446-453 现成字段） | 分类全部正确；分类输出带 evidence 指针 |
| B-2 | evidence 可回溯 | 随机抽 3 条蒸馏产出教训 | 按指针（JSONL 行号）能逐条回溯到原始事件，抽 3 中 0 错 |
| B-3 | 「工具失败≠AI 犯错」 | 负用例：构造纯网络断/500 链 | **不产生教训条目**（网络类失败不得升级为「以后别这么干」） |
| B-4 | 六字段 fail-closed | 提交缺任一字段的教训（P0-3） | 拒绝入池，非降级入库 |
| B-5 | confidence 分层 | 构造低 confidence 教训入池后新开会话 | 新会话开场注入**不含**该条目（注入面过滤有测试用例，非口头承诺）——防记忆垃圾场红线 |
| B-6 | 跨会话判据（里程碑一核心） | 构造用例集 ≥10 条已知坑任务：A 会话犯错→教训入池→新开 B 会话执行同类任务 | ① B 会话 journal 该错误**零复发**；② B 会话开场注入含对应教训（日志可查）。**开发期生产样本不足为既定事实，本判据以构造用例为主判据，生产复发率为后验观测指标、不阻塞里程碑** |
| B-7 | 教训过期机制 | 改动某工具的 registry 投影，观察关联教训 | 相关教训自动降回候选（REEVALUATE）；若未纳入 MVP 范围，必须登记为已知缺口（⚠️ 有条件通过），不得默认通过 |
| B-8 | B/A 边界铁律 `[CR]` | 代码审查蒸馏器输出类型 + 类型系统验证 | 输出**只能**是 fixture/风险提案，不存在任何规则/阻断写入口；提案进回归集必须经过审核事件（§6.2 铁律落地） |
| B-9 | 并列模式不污染 | 跑既有 compaction 测试 + 审查 SummarizationInput 使用 | 对话压缩路径零改动、蒸馏模式走旁路，全绿 |

## 八、里程碑终审（用户判据观测口径）

> 用户判据是最终判据（§〇表），但观测口径必须先钉死，否则「连续两个升级包零反馈」永远验不了。

**里程碑一「它不摔同一个坑了」**（B 线 MVP）：
- 判据：B-1 ~ B-6 全过（构造用例集跨会话零复发 + 开场注入可查）。
- 生产复发率为后验指标，仅记录不阻塞。

**里程碑二「升级包更稳了」**（A-1 + A-2 门 1/2）：
- 判据：§二元验收全过 + Z-3 坏改动完整走一遍「提交→脚本拦截→工单留痕」演练 + 首个真实技能（编排类）走完三道门进灰度。
- 「连续两个升级包零『以前会的现在不会了』」观测口径：**两包间隔 ≥ 1 周；反馈渠道 = 验收员真机走查记录 + 用户反馈工单，双渠道零命中才算数**；走查覆盖面 = 上包 predicted_fixes 声明的全部行为 + 高频工具 20 个。

**里程碑三「快和稳都有了」**（C→D）：
- 判据：C-7 弹窗基线 vs 上线后同口径计数对比下降；写类误动作为零（journal 审计 WRITE×EXTERNAL 零未确认执行）；D 线按 D-1~D-5 或以「降级观察项」留痕形态关闭。
- 若 C-4 裁决权选了严格保守：过渡期弹窗可能先升后降，属已知形态，终审只对比「基线 vs 稳定期」，但过渡期必须在交付说明中预告。

## 九、一票否决清单（触发即打回，不做有条件通过）

| 编号 | 否决项 |
|---|---|
| V-1 | 门 2 判定输入包含 manifest / 开发者 / 进化者的任何自述字段 |
| V-2 | baseline 五元允许缺省或 warning 降级通过 |
| V-3 | B 线蒸馏器存在任何规则/阻断写入口（污染链） |
| V-4 | 低 confidence 教训进入注入面 |
| V-5 | WRITE×EXTERNAL 工具存在任何未确认自动执行路径 |
| V-6 | 元验收（§二）未全过即放行真实候选 |

## 十、本标准自身的治理

- 本标准与设计计划 v1.2 绑定；Z-1 盘点报告产出后，**门 2 阈值参数按报告修订本标准对应行并升版**（v1.1），修订走 A-1 同款流程（修订也是一次变更，留 Manifest 与 Ledger 记录——标准自己先吃自己的狗粮）。

> 一句话总结本标准的立场：**这份计划交付的是「机器证明没改坏」的能力，所以验收标准的第一职责是先证明「证明机器本身是好的」**——元验收（§二）先于一切，其余判据都是为了把「用户感受到的变化」从口号钉成可查账的数字。

## 十一、设计师复核（v1.0 → v1.1 修订 5 处，2026-08-31）

> 复核基线：设计计划 v1.3（含三轮评审定夺记录 + 两项实证）。大神原文全部保留，以下修订以注记形式生效；标准升版 v1.1，修订本身按 §十 走 Manifest/Ledger 留痕。

### R-1【概念错位修正】A1-4 / Z-2：模型漂移对照 vs 纯函数评测的关系（最重要一处）

**实证**（2026-08-31，`ToolOrchestrator.kt`）：`orchestrate` 全程纯函数（关键词检索+规则决策，零 LLM/suspend 调用）——六指标评测结果与云端模型行为**天然正交**：DeepSeek 静默变，纯函数评测的输出一位都不会变。

**推论**：
- 当前六指标态下，「对照组差中差」是空操作（对照组与改动组在模型维度上恒等）——A1-4 原判据在现评测形态下无对象；
- 模型行为面的漂移监测位**不在评测器**，而在生产信号：Judge 对拍通过率统计 + B 线蒸馏复发率观测 + 用户反馈，异常入 Evolution Ledger（「环境漂移事件」）；
- 「对照组差中差」方案**保留**，启用条件 = Z-1 盘点若引入真实模型调用（那时模型漂移才进评测结果）。

**修订**：Z-2 拍板项改为「纯函数态（现）：六指标与模型漂移正交，模型行为面漂移走生产信号监测（Judge/B 线/用户反馈→Ledger）；LLM 实调态（未来，Z-1 定夺）：启用对照组差中差」。A1-4 随之标注「仅 LLM 实调态生效」。三轮评审问题 1 的威胁模型随之精确化：**漂移威胁的是模型行为面（真实对话质量），不是六指标——两条回归防线各守各的门**。

### R-2【去冗余】Z-1 重跑次数

确定性已实证（同上），「同环境重跑 ≥10 次」对纯函数评测是 10 次逐位相同的冗余动作。**修订**：Z-1 改为「确定性声明落档（orchestrate 纯函数实证 + 1 次复核）」；「重跑 N 次量化方差」方法论保留，触发条件 = Z-1 盘点引入真实模型调用。Z-1③（是否含真实模型调用）已由 v1.3 实证回答：**否**。

### R-3【尺度对齐】C-2「打回整批」过严

UPG-01 desc 核实先例是「断言亲杀纠偏 N 条后达标」——纠偏不打回整批。**修订**：C-2 改为「发现不一致 → 该条重核 + 全批加严抽检（5→10）」；连续 2 批出现不一致才升级为整批重核。

### R-4【补边界】A3-4 对拍反哺须过审核事件

用户对拍数据直接进门 2 回归集会从用户侧绕过 B/A 边界（§6.2/V-3 污染链）。**修订**：A3-4 通过标准追加「且经审核事件（§6.2 铁律）——对拍数据与 B 线提案同一条准入通道，无例外」。

### R-5【顺序前移】C-7 弹窗基线升为开工准入 Z-5

C-7 要求 C 线合入前有 ≥30 会话弹窗基线，但采集本身需要时间——留在 C 线验收里等于「C 线开工时基线尚不存在」，会逼出 V-7（事后补录）。**修订**：C-7 前移为 **Z-5（开工准入项）**：第一阶段并行完成基线采集（模拟器构造会话可行），C 线开工准入条件之一 = Z-5 基线已在档。

### 复核结论

**采纳本标准为 v1.1（含上述 5 处修订）**。五层结构（元验收前置/一票否决/标准自治理）与全部其余判据与设计计划 v1.3 一致，无转译走样。特别值得肯定三个超出设计稿的判据：**M-3 门放行力**（防全拒门——「门只会拒不会放」与「拦不住」同罪）、**A2-3 held-out 划分版本化进五元**（改划分=改基线）、**B-6 构造判据与生产后验分离**（开发期样本不足的诚实处理）。复核通过后，本标准与设计计划 v1.3 共同构成开工文件包，待用户拍板拆第一阶段任务。
