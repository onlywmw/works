## 〇、用户视角总览（先看这节：用户会感受到什么）

> 工程机制全部在后文——但每条改造线的立项理由只认用户可感知的变化。下表是验收这些改造线的**最终判据**：如果交付后下表右列没有发生，这条线就算白做。

| 用户场景（今天真实发生的糟心事） | 改造后用户感受到的变化 | 对应线 |
|---|---|---|
| 「昨天还好好用的功能，升级完就不会了」——AI 升级包把原来会的弄坏，用户装完包才发现，只能等下一个修复包 | 升级包更稳：每次改动前后跑同一套评测，弄坏什么的改动进不了包；真坏了自动回退，用户几乎感知不到坏包 | A-1/A-2 |
| 「它同一个坑摔两次」——这个房间里它刚因为查错参数道歉过，开个新对话又犯；教训只活在当前对话 | 同一个坑不摔第二次，而且**换房间、隔几天也不忘**：失败教训沉淀为长期记忆，新对话开场就带着「这个错别再犯」 | B |
| 「它新学的本领不靠谱」——AI 学会的新技能直接上岗，好不好用全凭运气；坏了也没有「退回上一版」 | 它学新本领像应用商店上架：先试用（不真执行）→ 确认不退步才上岗 → 上岗后退化自动降级回上一版。用户可以信任「已稳定」标签的技能 | A-2/A-3 |
| 「让它干事总慢半拍，多步任务一问一答老半天」——查三个班次再对比，AI 得一轮轮问，慢且每轮都耗对话费 | 复杂任务一次说清，它一把并行做完，回复明显变快（同一问题等待时间缩短） | D |
| 「它帮我干活的时快时慢，碰重要东西时又太毛躁」——同时读写你的文件可能冲突；该问的没问、不该问的乱问 | 干活更快但更有分寸：碰重要东西（短信/支付/删文件）的动作必先问你、绝不自动重试；只读的动作不烦你直接干 | C + D |

> 三轴特质的用户翻译：**更懂你 = 记得住你的坑和你的偏好（B）｜更持续 = 不退步、不重复犯、坏了自己降级（A/C）｜更能干 = 更快更稳一把做完（C/D）**。

## 一、项目现状（评审底图）

### 1.1 MOV 是什么

MOV：运行在 Android 上的 AI 生态移动端助手——工具/MCP 能力可视化组合（知识图谱）+ 能力市场（mow.kim）。AI 主线 = DeepSeek 云端模型 + 端侧 harness（工具面 156+、会话/记忆/审批/防编造全链）。评价一个能力值不值得做的三轴：**更懂你 / 更持续 / 更能干**。

### 1.4 缺口诊断（为什么是这四条改造线）

1. **无自动演进/自校正循环**：harness 迭代 100% 靠「工单→程序员→验收员→审验员→合 main」人工链；论文 AHE 证明「编辑前预测+编辑后交叉验证」可自动化其中回归验证环节
2. **轨迹数据沉睡**：会话 JSONL 每天在写（tool_call/claim 链），但除 E3 的 isError 计数外**零结构化消费**——没有失败根因蒸馏层
3. **工具面缺效应/资源维度**：`ToolAnnotations` 只有布尔 hint（readOnly/destructive/idempotent/openWorld），且注释自认「第三方可能不填/填错」——**无并行安全依据**，DAG 化无地基
4. **无技能/编排准入门**：验收靠人工（验收员+审验员），没有「准入前重放+回归 Δ≤0+灰度」的机器门；EvoC2F 实证无门则持续学习回归率 0.8%→7.2%

## 二、改造线 A：harness 演进契约 + 技能准入门（A 级，主线）

**用户场景与体验目标**：用户最怕的不是「AI 不会」，是「**以前会的现在不会了**」。今天这条防线是纯人工（验收员+审验员+真机走查），坏包要靠人撞见；且 AI 自己学会的新本领没有退路。本线交付后：① 改动坏什么机器先知道，坏改动进不了包 ② 新技能带「试用→上岗→退化自动降级」全生命周期，用户可信任「已稳定」标签。工程内容是手段，判据只有一条：**连续两个升级包，用户零「以前会的现在不会了」反馈**。

**合流**：AHE① Change Manifest + AHE③ 回归盲区纪律 + EvoC2F① 验证门控简化版。
**服务特质**：更持续（自校正闭环+防退化）。

### A-1 改造内容（三步；v1.1 按大神评审修订）

**第 1 步｜Manifest 契约进交付流（S）——「做成工具，不是文书」**

大神 Q1 定夺采纳：验证器若只读 Manifest 文本不跑评测，两周后必然沦为走过场。交付物不是报告模板，而是**一个 ≤20 行的脚本/钩子**：工单提交时跑 baseline 快照，验收时跑 delta 对比，输出直接贴进工单——纪律被工具固化，不靠人自觉。降级预案：验证器资源排不上则做半自动版（开发者自跑脚本+验收员抽 1-2 条 predicted_fixes 对拍）。

交付报告 Manifest 节固定格式：

```text
## Change Manifest
- predicted_fixes:  预期改善的评测用例/行为（≥1 条，可查证）
- risk_tasks:       声明有回归风险的用例（诚实列出，不列视为 0）
- baseline:         可复现评测环境快照（v1.2 P0-1 升级，见下）
```

**Baseline 可复现契约（v1.2 P0-1，大神二轮评审定夺）**：baseline 不是六指标数字 hash，是**可复现评测环境快照**，必含五元：

```text
baseline_hash            评测结果 hash
eval_fixture_version     评测用例集版本（用例增删必须升版，否则 baseline 不可比）
evaluator_version        评测器版本
tool_registry_version    工具登记层投影版本
model_runtime_config     模型/运行时配置快照
```

否则半年后「这个 PR 当时为什么是过的」只剩一个无法复现的 hash——不可复现的基线等于没有基线，回归盲区纪律失去物理基础。

**对照组差中差（v1.3 采纳三轮评审问题 1：五元管不住云端模型漂移）**：DeepSeek 是云端 API——模型 ID 不变、行为可能静默变，六指标 delta 无法区分「改动导致回归」vs「模型自己漂了」。补法：每次 delta 评测**同跑一份无改动对照组**（main HEAD 原样重跑），回归判定改为「改动组 vs 对照组」的**差中差**；定期同代码重跑 baseline，漂移超阈即重立基线并把「环境漂移事件」记入 Evolution Ledger。不补这条，只信独立重跑的六指标信的是一把会自己漂的尺子。

验收时验证器做两件事：① predicted_fixes 与六指标 delta 交叉（预测命中才算修复有效）② **risk_tasks 与实测回归对比——但按 AHE 负结果（回归预测 precision 11.8%），回归判定只信独立重跑的六指标，不信 manifest 自述**。这一条写成设计红线。

**第 2 步｜技能准入门 MVP（M）**
候选技能（宏工具/编排模板/生成 JS 工件）入库前过三道机器门：

```text
门1 功能重放：错误注入用例 100%；功能用例 MVP 用绝对错误数阈值（v1.2 P0-2：13 条用例上 95% 无
   分辨率——12/13=92.3% 与 13/13=100% 之间不存在稳定阈值；MVP 定「功能重放 ≤1 条失败」，
   评测集扩充至 ≥40 条后切换百分比阈值并按 fixture scale 自动计算）
门2 回归判定：六指标 held-out 对比——判定粒度按「评测集规模盘点」结果定最小可检测差
   （v1.1 实证：现用例仅 13 条，「任一指标下降即拒」会被 1-2 条用例翻转的噪声卡死；
    盘点前用「下降 ≥2 条用例」过渡阈值，盘点后按样本量定统计边界）
门3 灰度：会话级 shadow 计数（只进规划上下文不执行→N 会话后转执行），退化自动回 shadow
```

**候选准入边界（v1.1 采纳大神 Q2）**：JVM 重放对「编排类候选」够用；**「JS 工件类」候选 MVP 阶段直接标「不可准入」**——现仓无沙箱实体，用 JVM 重放凑合会给后续埋「其实没测到」的假阴性，宁拒不凑。等沙箱资产决策后再开此通道。

与 UPG-52 生命链同构映射：shadow→canary→stable ≙ PROPOSED→ACTIVE→(RE_EVALUATE)→ARCHIVED；TimelineLedger 的 actor 权限直接复用（AI 产候选=PROPOSED，门通过=系统 ACCEPTED）。
**执行环境前置（诚实声明，v1.1 收紧）**：现仓无 JS 沙箱实体（见 1.3 溯源）——JS 工件类候选 MVP 直接拒收（见上）；门 1 对编排类候选用 JVM 侧 EvalFixture 重放。

## 三、改造线 B：失败根因蒸馏层（A 级，AHE②）

**用户场景与体验目标**：AI 最伤信任的行为是「**同一个坑摔两次**」——同一房间刚道歉过，开个新对话又犯。根因：教训只活在当前对话（E3 同 session occurrences≥2），换房间/隔天就忘。本线交付后：AI 犯过的错经确认沉淀为长期教训，**新对话开场就带着「这个错别再犯」**；且教训是它真摔过的（有 journal 证据），不是编的。判据：同一类错误跨会话复发率可观测下降（教训命中→复发零）。

**服务特质**：更能干 + 更持续。**现状**：E3 教训只有条目级 reason（occurrences≥2 注入），journal 的 tool_call 链零结构化消费。

### B-1 改造内容

在 `compaction` 包现有抽象上加**诊断蒸馏模式**（不动对话压缩路径）：

```text
蒸馏器输入：会话 JSONL（tool_call/ok/结果 payload 链）
  → 第一层：per-session 失败片段（连续 isError/超时/重试链）
  → 第二层：根因归因（v1.1 采纳大神风险 3：MVP **三分类**——可重试失败/不可重试失败/编造被拦；
     编造被拦字段现成零成本【实证：guard/fabricate_hit 事件含 matchedPattern/toolCallsZero，AgentLoop.kt:446-453】；
     工具缺陷 vs 环境不可达的细分降为迭代目标——二者 journal 表现同形，需 payload 分析）
  → 第三层：session 级 overview（≤10 条，progressive disclosure——每条带 evidence 指针=JSONL 行号）
产出消费：① 人工（工单输入）② A 线 Manifest 的 risk_tasks 参考 ③ 教训升级为 Memory OS Semantic 条目（AI=PROPOSED，人工确认入池，经 FabricateGuard 校验非编造）

### 6.1 Evolution Ledger（v1.2 P0-4，大神二轮评审新增，插第一阶段）

```

第一版只需记录八字段：`changeId / baseline / change / evaluation / decision / lifecycle / rollback / evidence`。Debug 时可直接回答「这个技能为什么变成 shadow 了」，不用翻五处日志。

### 6.3 架构原则：测试系统不承担它没有观测能力的威胁模型（v1.4 升格，源=R-1）

### 6.4 B/A 边界铁律（v1.2，防记忆→测试→规则的污染链）

**B 只能「提出新的测试」，不能直接改变准入规则**：

```text
✅ B 发现失败 → 提出 risk → 提出 fixture → 人工/系统审核 → 进 regression set
⛔ B 发现失败 → 自动加入硬性阻断规则
```

否则形成「错误→记忆→测试→规则→再阻断」的污染链，一个错误样本就能逐渐污染整个 Runtime。与 FabricateGuard「治感知不治行为」、AHE「归因先于蒸馏」同构。

# 下篇 · 验收标准（v1.1）

## 验收标准 v1.0（大神评审稿，含 §十一 复核升版 v1.1）

> 依据：设计计划 v1.2（含二轮评审 4 P0）+ 三轮评审地基补充。本标准不新增设计决策，只把已定夺项转译为**可执行、可证伪、可留痕**的查核项。设计里没定夺的事（裁决权、漂移校准）不藏在验收里偷偷定，而是作为「开工准入项」强制拍板。

---

## 〇、总则与判定规则

**验收原则（四条，违反任何一条的判据视为无效判据）**：

1. **每条判据三要素齐全**：验收对象 / 验收方式（一次可执行的操作）/ 通过标准（可证伪的边界）。禁止「已实现」「已优化」「基本完成」类表述。
2. **工具先于文书**：凡能用脚本/测试/钩子自动查的，不设人工审查项；人工审查项必须显式标注 `[CR]`（code review）并写明看什么。
3. **fail-closed 优先**：契约类校验（baseline 五元、教训六字段）缺一即拒，不允许 warning 降级通过。
4. **诚实降级 = 通过的一种形态**：JS 工件类拒收、D 线降观察项、门 3 人工触发版，均为合法交付形态——但必须在 Evolution Ledger / 工单留痕。**静默缩水 = 打回**。

**判定分级**：

| 级别 | 含义 | 后续动作 |
|---|---|---|
| ✅ 通过 | 全部判据过线 | 合入，Ledger 记 ACCEPTED |
| ⚠️ 有条件通过 | 存在缺口但已登记：缺口内容 + owner + 期限 | 缺口进工单系统，Ledger 记 ACCEPTED + 缺口引用 |
| ❌ 打回 | 触发一票否决项（§九）或核心判据未过 | 打回，Ledger 记 REJECTED + 理由 |

**验收体系分五层，顺序不可颠倒**：开工准入（§一）→ 元验收：验门本身（§二）→ 组件级验收（§三–六）→ 横切验收（§七）→ 里程碑终审（§八）。**元验收未全过，任何门不得放行真实候选**——这是本标准最重要的一条顺序约束。

## 十、本标准自身的治理

- 本标准与设计计划 v1.2 绑定；Z-1 盘点报告产出后，**门 2 阈值参数按报告修订本标准对应行并升版**（v1.1），修订走 A-1 同款流程（修订也是一次变更，留 Manifest 与 Ledger 记录——标准自己先吃自己的狗粮）。
- 每条验收判据的执行结果（过/有条件过/打回）本身进 Evolution Ledger 的 evaluation 字段——验收历史可追溯，验收员换届不丢上下文。

> 一句话总结本标准的立场：**这份计划交付的是「机器证明没改坏」的能力，所以验收标准的第一职责是先证明「证明机器本身是好的」**——元验收（§二）先于一切，其余判据都是为了把「用户感受到的变化」从口号钉成可查账的数字。

## 十一、设计师复核（v1.0 → v1.1 修订 5 处，2026-08-31）

> 复核基线：设计计划 v1.3（含三轮评审定夺记录 + 两项实证）。大神原文全部保留，以下修订以注记形式生效；标准升版 v1.1，修订本身按 §十 走 Manifest/Ledger 留痕。

### R-1【概念错位修正】A1-4 / Z-2：模型漂移对照 vs 纯函数评测的关系（最重要一处）

**实证**（2026-08-31，`ToolOrchestrator.kt`）：`orchestrate` 全程纯函数（关键词检索+规则决策，零 LLM/suspend 调用）——六指标评测结果与云端模型行为**天然正交**：DeepSeek 静默变，纯函数评测的输出一位都不会变。

**推论**：
- 当前六指标态下，「对照组差中差」是空操作（对照组与改动组在模型维度上恒等）——A1-4 原判据在现评测形态下无对象；
- 模型行为面的漂移监测位**不在评测器**，而在生产信号：Judge 对拍通过率统计 + B 线蒸馏复发率观测 + 用户反馈，异常入 Evolution Ledger（「环境漂移事件」）；
- 「对照组差中差」方案**保留**，启用条件 = Z-1 盘点若引入真实模型调用（那时模型漂移才进评测结果）。

**修订**：Z-2 拍板项改为「纯函数态（现）：六指标与模型漂移正交，模型行为面漂移走生产信号监测（Judge/B 线/用户反馈→Ledger）；LLM 实调态（未来，Z-1 定夺）：启用对照组差中差」。A1-4 随之标注「仅 LLM 实调态生效」。三轮评审问题 1 的威胁模型随之精确化：**漂移威胁的是模型行为面（真实对话质量），不是六指标——两条回归防线各守各的门**。

### R-2【去冗余】Z-1 重跑次数

确定性已实证（同上），「同环境重跑 ≥10 次」对纯函数评测是 10 次逐位相同的冗余动作。**修订**：Z-1 改为「确定性声明落档（orchestrate 纯函数实证 + 1 次复核）」；「重跑 N 次量化方差」方法论保留，触发条件 = Z-1 盘点引入真实模型调用。Z-1③（是否含真实模型调用）已由 v1.3 实证回答：**否**。

### R-3【尺度对齐】C-2「打回整批」过严

UPG-01 desc 核实先例是「断言亲杀纠偏 N 条后达标」——纠偏不打回整批。**修订**：C-2 改为「发现不一致 → 该条重核 + 全批加严抽检（5→10）」；连续 2 批出现不一致才升级为整批重核。

### R-4【补边界】A3-4 对拍反哺须过审核事件

用户对拍数据直接进门 2 回归集会从用户侧绕过 B/A 边界（§6.4/V-3 污染链）。**修订**：A3-4 通过标准追加「且经审核事件（§6.4 铁律）——对拍数据与 B 线提案同一条准入通道，无例外」。

### R-5【顺序前移】C-7 弹窗基线升为开工准入 Z-5

C-7 要求 C 线合入前有 ≥30 会话弹窗基线，但采集本身需要时间——留在 C 线验收里等于「C 线开工时基线尚不存在」，会逼出 V-7（事后补录）。**修订**：C-7 前移为 **Z-5（开工准入项）**：第一阶段并行完成基线采集（模拟器构造会话可行），C 线开工准入条件之一 = Z-5 基线已在档。

### 复核结论

**采纳本标准为 v1.1（含上述 5 处修订）**。五层结构（元验收前置/一票否决/标准自治理）与全部其余判据与设计计划 v1.3 一致，无转译走样。特别值得肯定三个超出设计稿的判据：**M-3 门放行力**（防全拒门——「门只会拒不会放」与「拦不住」同罪）、**A2-3 held-out 划分版本化进五元**（改划分=改基线）、**B-6 构造判据与生产后验分离**（开发期样本不足的诚实处理）。复核通过后，本标准与设计计划 v1.3 共同构成开工文件包，待用户拍板拆第一阶段任务。

## 十二、第二阶段执行细则（v1.2 增补，2026-08-31——四单开工前钉死的操作口径）

### 12.1 Z-5 弹窗基线采集细则（UPG-63）

- **口径定义**：一次「确认弹窗」= ApprovalService 一次 ASK 决策（Decision.ASK 落 journal 的审批事件，含后续用户选择 allowed-once/remembered/denied 全形态；gate 级单独列）。**拒收/静默放行不计入**。

- **采集方法**：模拟器构造 ≥30 个含写类操作的会话（脚本批量构造：vault.set/delete、http.post、note.create、device.toast 等，每会话 3~8 次写类调用），逐会话统计弹窗次数+场景分布（工具名×频次二维表）。

### 12.2 门 3 自动化阈值设计原则（UPG-65）

- **判定单位**：候选技能的**滚动失败率**——最近 N 次生产调用中 fabricate_hit+isError 占比。
- **窗口**：N=10（滚动窗口，非固定时段）；**最小样本**：调用次数 <5 不判定（样本不足继续 shadow，宁多观察）。
- **回退动作**：窗口内失败 ≥3 次（≥30%）→ 自动 DEGRADED 回 shadow + Ledger 事件（evidence 含失败会话指针）；shadow 期重训后可再申请 canary（走既有门 1/2）。
- **宁严勿松的应用**：阈值边界情况（恰好 3 次）一律回退；误回退的代价=重新走门 1/2（分钟级），漏退步的代价=用户信任（不可逆）——不对称取严。
- **持久化**：灰度计数随 Ledger 事件落盘（重启不丢，A2-4）。

## 十三、第三阶段执行细则（v1.3 增补，2026-08-31——UPG-67 D 线预立配套）

> 下篇 D-1~D-5 判据已覆盖「查什么/过线标准」；本节补齐三个「怎么执行」细节。**UPG-67 为预立待前置状态，双门不齐不放行。**

### 13.1 评测集性能维度补充方法（UPG-67 开工第一项）

- **EvalCase 增字段**：`mockCostMs`（该用例内每个工具调用的逻辑耗时——按工具语义给常数：查询类 300ms/写类 500ms/外呼 800ms，虚构但**固定**）。
- **Metrics 扩两列**：`latencyMs`（DAG 计划的 makespan=关键路径上 mockCost 之和，并行收益=串行总成本−makespan）+ `toolCalls`（模型调用次数——DAG 一次规划 vs ReAct 多轮）。
- **确定性判据**：同 fixture 同 changeId 连跑两次，latencyMs/toolCalls/六指标**逐位一致**（纯函数，无时钟抖动）。
- **三列表产出**（D-2）：同一组 MULTI_CALL 用例跑「串行模式」与「DAG 模式」各一次，输出 延迟/调用量/正确率 对照。

### 13.2 DAG 计划接口契约

- **形态**：`Decision.MULTI_CALL` 输出升级为 `DagPlan(nodes: List<DagNode>, edges: List<Edge>)`——DagNode=⟨stableId, args(含 `ref(nodeId,field)` 引用), effectSpec⟩；Edge∈{DATA_FLOW, EFFECT_ORDER, SYNC}。
- **循环检测**：拓扑排序（Kahn）失败 → 返回拒绝计划（`verdict=REJECT, reason=cycle`），**不得进入执行循环**（D-3③）。
- **效应消费**：WRITE×EXTERNAL 节点强制 SYNC 边全序化 + 确认门；未登记 effects 的节点按保守缺省全串行（C 线缺省纪律）。
- **红线**：DAG 仅是 MULTI_CALL 路径的内部形态升级——ToolOrchestrator 对外契约（OrchestrationResult/Trace）零变化；Code Mode 不受影响。

### 13.3 真机采样口径（D-5「实测下降」唯一有效证据）

- **采样方法**：journal 事件链耗时 = 该 turn 内首个 tool_call 时间戳 ↔ 末个 tool_call 完成时间戳（单 turn 工具段耗时，排除模型思考时间）。
- **对照设计**：部署前采样 ≥30 条多步会话（turn 工具段 ≥2 调用）为基线，部署后同口径采样 ≥30 条（任务类型分布对账——类型不齐则按类型分层对比）。
- **成立标准**：工具段耗时**中位数下降** 且 **p95 不上升**（防长尾恶化被均值掩盖）；仅中位数降而 p95 恶化 → 判「不可接受」。

### 13.4 降级与恢复

- **降级触发**：UPG-64 未合 / 性能维度验收不过 / 分布统计覆盖率 <50% 且不扩核实范围——任一发生 → UPG-67 状态改「⛔ 降级观察项（留痕）」+ Ledger `evolution.DEGRADED` 事件（reason=前置缺口）。
- **恢复**：前置补齐后重新走开工准入（设计师显式放行），无惩罚。
