## 一、写点口径（大神 §一 采纳——严格单写点）

### 1.1 数据模型（E1 唯一权威）

```
工单库.md   ← 唯一真相（58 卡）
    ↑ 唯一写点：设计师（据交付报告/验收记录统一登记卡状态）
    ↓ --sync（确定性投影）
工单表.xlsx ← 投影（不可人工直接编辑；冲突可从库重建）
    ↓ 只读
看板 HTML   ← 展示层（自动生成产物，不入 git）
```

### 1.2 写点分工（明确口径，消除矛盾）

| 角色 | 能写什么 | 怎么更新卡状态 |
|---|---|---|
| **设计师** | 工单库.md + 工单表.xlsx（经脚本）+ 派单/方案 | **唯一直接写库人**——据交付报告/验收记录统一登记 |
| 程序员 A/B/C | 交付报告+分支 | **不直接写库卡**——交付后申报，设计师登记 |
| 验收员 | 验收记录+验收文件 | 验收通过/打回=申报设计师登记 |
| 审验员 | 自动校验（只读） | — |

> **红线上墙**：任何 agent 直接改 `工单库.md` 卡状态 = 违反红线（一律走设计师登记）。

## 二、冲突解决顺序 SOP（大神 §二 采纳——6 步）

```
检测到 git 冲突
 │
 1. git status 看冲突文件
 2. 优先解决 工单库.md 文本冲突（人工裁决合并结果）
 3. node sync-orders.mjs --check 校验 md 内部一致性（diff 归因）
 4. git checkout --theirs/--ours 任意一版 工单表.xlsx（丢弃冲突版）
 5. node sync-orders.mjs --sync 从已合并 md 重建表（diff=0 收敛）
 6. git add + commit（过 pre-commit 校验）
```

**顺序铁律**：**先 md 后表**——表是投影，必须基于已合并的真相重建，否则丢另一侧改动。

## 三、生成物与 git 跟踪（大神 §三 采纳）

| 对象 | git | 理由 |
|---|---|---|
| 看板 html/md/data.json | **.gitignore 不入库** | 自动生成物——watch 每刷一次=噪音；只在本地生成 |
| 模板/脚本（board-build/run/watch/sync-orders） | 入库 | 源码=版本资产 |
| 工单表.xlsx | 入库 | 投影产物（交付对账用）；但**禁止人工直接编辑**（编辑=走 sync 重建） |
| **pre-commit hook** | 本机安装 | `sync-orders.mjs --check` 不一致 → 拒绝提交（防陈旧表入库） |

---

## 四、git 操作互斥（大神 §四 采纳）

**红线（README 上墙）**：
> 共享仓库的写操作（`pull --rebase` / `commit` / `push`）同一时刻只允许一个终端执行——多终端同时跑会出现 `.git/index.lock` 报错。

零成本习惯加固；单机多 agent = 一个终端代理执行写操作（本轮已如此）。

---

## 五、方案对比与路线

### 方案 A：git 串行 + 严格单写点（推荐·当前）
写前 `pull --rebase` → 写 → push；冲突=rebase 中止→按 §二 SOP。

### 方案 B：本机同步服务（已部分落地）
`board-watch.mjs`：文件变化→自动重生成看板（3s 去抖）——已上线；产物不入 git。

### 方案 C：中央同步服务（冻结）
**触发条件（大神 R4 采纳）**：`≥2 台物理机分离编辑库卡且冲突 ≥1 次/周`——同机多终端不算异机。
