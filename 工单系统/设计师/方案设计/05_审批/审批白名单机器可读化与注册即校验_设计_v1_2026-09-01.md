## 〇、一句话

**把权限名单从「代码里手写三个 set + else 静默放行」改造为「单源 registry（JSON）+ 生成校验 + guard() 查询 registry 且未登记=ASK（fail-closed）」——堵死 W2：新工具漏登记从「静默 ALLOW」变为「运行时 ASK」+「CI 红」。**

## 一、现状缺陷（实读定位，非文档假设）

### 1.1 洞的代码位置

`McpToolScheduler.kt → PermissionGuard.guard()`（当前 main 树）：

```kotlin
return when (currentMode) {
    Mode.DEFAULT_PERMISSION -> {
        if (sensitiveTools.any { name.contains(it) }) DENY
        else if (isHarmless(name, args)) ALLOW
        else if (writeTools.any { name.contains(it) }) ASK
        else ALLOW   // ← 洞：未知工具静默放行（FAIL-OPEN）
    }
    ...
}
```

### 1.2 根因

**两套清单人工同步断点**：

```text
ToolRegistry（工具注册面）——开发者加新工具必登记（否则工具不可调）✅
权限名单（sensitiveTools/writeTools/harmlessTools）——手工维护，可遗漏 ⚠️
        ↑ 无自动校验连接二者 → 漏登记 = 工具可用但跳过审批
```

### 1.3 漏网实证（两度）

| 案例 | 后果 | 处置 |
|---|---|---|
| `approval.setMode`（MCP 面可调） | AI 可自切审批模式（绕过授权系统） | M3-R2 收编 uiOnlyMcpTools + 登记 |
| `personalization.setEnabled` | AI 静默开数据外发个性化 | UPG-51 合前补登记 |

**两次均由人工抽查发现**——证明「人肉纪律+变异」不可靠；且 **same 洞+支付 handler 进场 = 漏钱**（P0 紧迫性）。

## 二、目标架构（单源 + fail-closed + 注册即校验）

```text
                         ┌────────────────────────────┐
                         │ docs/ApprovalRegistry.json  │  ← 唯一事实源
                         │ （全工具面条目 + 分类字段）    │     生成物（代码 collect）
                         └────────────┬───────────────┘
              ┌───────────────────────┼───────────────────────┐
              ▼                        ▼                       ▼
    approval_registry.schema.json  CI 注册校验器           PermissionGuard.guard()
    （条目结构校验）               （新 handler 未登记        （查 registry 得分类：
                                  = CI 红）                 read=ALLOW/write=ASK/
                                                            sensitive=DENY/
                                                            缺失=ASK 【fail-closed】）
```

### 2.1 单源条目结构（对齐大神示例 + 现有生成物字段）

```json
{
  "version": "1.0",
  "generated_from": "CT-07 语义分类契约 v1 (UPG-68)",
  "entries": [
    {
      "tool": "personalization.setEnabled",
      "category": "write",            // read | write | sensitive | system_baseline
      "riskLevel": "ask",             // free | ask | gate
      "source": "McpToolScheduler.kt", 
      "registered": true
    }
  ]
}
```

- **分类映射**：现有代码名单映射进 registry（sensitiveTools→sensitive、writeTools+systemBaselineDeny→write/system_baseline、harmlessTools→read+harmless 特判保留…）——**逐条迁移不丢语义**（含 file.write 工作区特判、isHighRisk 高危子集语义）
- **全量登记**：registry 覆盖全部 173 工具面条目（生成物原本就有 collect 逻辑——扩展分类字段即可，不新建第二份文件）

### 2.2 guard() 查询化（消除 else）

```kotlin
Mode.DEFAULT_PERMISSION -> {
    val tier = registry.tierOf(name, args)   // 单源查询
    when (tier) {
        Tier.GATE -> DENY
        Tier.ASK  -> ASK
        Tier.FREE -> ALLOW
        Tier.UNKNOWN -> ASK   // ← fail-closed：未登记=需确认（不再是 ALLOW）
    }
}
```

- **UNKNOWN→ASK 是本次修复的安全核心**：漏了也不知道？不弹窗。宁多弹不放过。
- 只读工具未登记会弹窗吗？——**registry 全量登记后**，正常工具都有条目（read→FREE）不会误弹；只有「新工具漏登记」才进 UNKNOWN（正是我们想拦的）
- UI 直调（参数含 `uiCmd`/bridge 内部路径）不经 guard——不受影响（与现状一致）

### 2.4 副作用执行单入口（A7 · 大神 P0 收紧 · v2 新增）

**架构不变量：Agent 副作用执行必须经过统一单通道。**

```text
Agent Tool → Tool Dispatcher → Approval Guard → Handler
```

**禁止**（绕过 Dispatcher 的路径 = 未来 W2 新温床）：

```text
Agent → Handler           （直呼 handler）
Agent → Biz API           （直调商业后端）
Agent → Vault API         （直调保险柜）
Agent → partnerHttp       （直调支付进件通道）
Agent → 任何未过 guard 的执行入口
```

**CI/静态检查**：任何 agent 可达 handler 不经过统一 dispatch/guard → CI 红（与 A1 枚举器同源——注册点扫描时同时校验「注册点所属执行面」）。

### 2.3 CI 注册校验器（G2 并入 G1）

**工具面枚举源（A1 评审收紧 · 必读）**：校验器的「全集」**不得从 registry 自数**（=循环定义永远绿）——独立源=代码注册点  注册表（MainActivity.kt 的  静态扫描）与  工具面装配，二者作为独立枚举源；校验规则=「注册点全名集 ⊆ registry 条目集」。全名集从注册点源码捕获（反射/静态扫描 registry 数据结构），registry 不参与自证。

```text
校验器（脚本/测试，CI 执行）：
  1. 收集工具面全名集（ToolRegistry 注册表，静态扫描）
  2. 对每个工具名：registry.entries 存在 && category==read/write/sensitive 已分类？
  3. 未登记 或 category=="write" 但 riskLevel!="ask" → 校验红
  4. 新增 handler 出现在工具面但不在 registry → CI 红（注册即校验）
```
