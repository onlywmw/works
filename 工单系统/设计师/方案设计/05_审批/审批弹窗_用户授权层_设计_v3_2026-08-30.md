## 〇、一句话（v3 收敛定义）

**把「技术能力 → 用户意图 → 授权决策」做成一个人可读的授权层：审批弹窗只回答用户三件事——「它要做什么、会影响什么、我要不要同意」，且这套解读不依赖 LLM 当硬依赖。**

> v3 最重要的一句：**用户需要知道多少，才能做出一次正确的授权决定？** —— 不是 "怎么把 shell.exec 说成人话"，而是「解释**这一次具体会发生什么**，而非这个工具是什么」。

---

## 溯源诊断（沿用 v1 实证，不再展开）

现有弹窗给用户看 `AI 请求执行：shell.exec / 原因：默认权限… / 参数摘要：command=echo…`（`MainActivity.kt:6155`）——**纯技术黑话**；分类仅有风险三档(gate/ask/free)，**无用户语义层**；分类靠 contains 子串，脆弱（BP-03 / obsidian 误捕前科）。结论不变：风险判定保留作基线，其上叠加**语义/意图/解释层**。

## 一、v3 核心架构（并列，非前后依赖）

```
              ┌─────────────┐
              │ Tool Metadata │  (UPG-01: name/desc/args)
              └──────┬──────┘
                     ↓
          ┌────────────────┐
          │ Semantic Resolver │  (工具→意图/风险标签, N对多)
          └────────┬───────┘
                   ↓
      ┌─────────────────────────┐
      │ Intent / Action / Impact │
      └───────────┬─────────────┘
                  ↓
        ┌────────────────────┐
        │ Explanation Gen     │  人工模板 → 结构化模板 → 仅长尾 LLM
        └─────────┬──────────┘
                  ↓
        ┌────────────────────┐
        │ Permission Gate     │  并列(独立于解释层): gate/ask/free
        └─────────┬──────────┘
                  ↓
             Approval UI
```

**关键（大神 P0）**：权限判定与人话生成是**并列关系**——「要不要审批」和「怎么解释」是两件事，**LLM 挂了绝不能影响 permission pipeline**。安全基线不依赖任何解释器。

### 三原则（v3 P0，守住即为可靠授权层）
1. **LLM 不得决定事实，只能解释事实**（把已知事实重组为人话，禁止猜工具想干什么）；
2. **首次审批不得依赖 LLM 延迟**（高频=人工模板、普通=结构化模板,皆本地零 LLM；LLM 仅长尾兜底）；
3. **用户看到的是「这次具体会发生什么」，不是「这个工具是什么」**。

---

## 二、语义层：意图/风险标签（非工具硬分类）

不做「工具 ↔ 分类」永久一对一映射（一个工具可属多语义，如 camera.capture 既可拍照也取敏感信息），而是：

```
tool → intent → risk signals → human explanation
```

- **intent**（用户能懂的意图，N 对多）：写内容 / 读文件 / 拍照扫码 / 截屏 / 执行命令 / 改系统设置 / 发外部消息 / 装卸应用 / 读隐私信息 / 记账支付 / **删除**……
- **action + impact**：`semanticType + action + impact`，尤其加**不可逆性维度**（写 vs 删除 vs 外发 vs 支付 vs 取隐私，用户心理阈值完全不同）——如 `type=file, action=delete, impact=destructive`。
- 分类器：精确名单优先 + 未覆盖工具走 AI 归类（意图/风险,非工具名）。

## 三、解释生成：三级（LLM 非硬依赖）

| 级 | 覆盖 | 生成方式 | 延迟 |
|---|---|---|---|
| **一级·人工模板** | 高频/高风险(shell.exec/file.write/sms.send/payment.pay/location/contacts/camera) | 本地预置,人工写死 | 0 |
| **二级·结构化模板** | 普通工具 | 工具分类+动作模板+参数槽位,**本地生成,无 LLM**（"AI 想帮你把内容保存到 `xxx`"） | 0 |
| **三级·LLM** | 仅真正长尾(未知 MCP/第三方/复杂业务) | LLM 依据**已解析的结构化事实**(并非原始参数)重组人话 | 容忍 |
| **兜底·不可解释** | 三级兜底 | `⚠️ AI 请求执行一项系统操作 操作:shell.exec`（三级：明确/部分明确/无法确定） | 0 |

**LLM 职责边界（防编造）**：输入必须是**结构化事实**（intent/action/target/argsSchema），LLM 只做「重组人话」，**禁止**从裸参数猜行为（如 `shell.exec python a.py` 不能说成"生成日报"——那是猜）。生成不了 → 走兜底，绝不编造。**LLM 永不成为审批键上的硬依赖**。

## 四、弹窗：收敛为四块信息（v3 定稿）

```
① 发生什么        📝 AI 想帮你保存这份会议纪要        ← 最大字,视觉主体
② 具体对象        保存为 `会议纪要.md` / 发给张三"改到3点"  ← 次级,参数人话化
③ 授权操作        [ 同意 ]   [ 拒绝 ]                ← 视觉中心(weight 最大)
④ 辅助信息(小字)   30 秒后自动取消 · 本次操作会记录到安全日志
                  □ 本次对话中,之后类似操作自动同意
```

- **文案**：「保存到安全日志」而非「会被记录」（少监控感）；
- **同类同意**：用户看**自然语言**（"之后保存类似笔记自动同意"），系统存**结构化规则**（`tool=note.create, parameterPattern="*.md", scope=current_turn`）——不把权限模型暴露给用户；
- 倒计时默认 30s + 设置可调。

## 五、单 A 升级：Approval Capability Registry（不是普通统计清单）

单 A 产出**权限能力注册表**，字段（B 直接复用，无需再分析）：
`tool / semanticType / action / target / argsSchema / humanStrategy(人工·模板·AI·兜底) / risk / approvalMode(ask·gate·free) / fallback(无法解释时怎么说) / priority(高频序) / audit(是否记录) / batchable(是否允许同类自动同意)`

**意义**：A = 审批世界的**全量登记**，B 只做「语义解释器 + 弹窗 + 生成器」，不重复盘点。

## 六、下一步：真实场景测试矩阵（v3 停止堆文档，转向实测）

大神判断对：**不必再堆分类/文档，要做「真实用户审批场景测试矩阵」**——跑 7~10 个真实场景，验证用户能否 **2 秒内**回答「它要做什么 / 影响什么 / 要不要同意」：

> 保存笔记 / 删除文件 / 发消息 / 开摄像头 / 执行 shell / 读取位置 / 支付 / 装应用 / 改系统设置 / 读取隐私

每场景检验：人话是否让用户秒懂、授权操作是否清晰、同类同意是否被正确理解。**这条体验链跑通，系统才算成立；跑不通的点，比任何文档更能暴露真问题。**

## 七、工单切分（v3 定稿）

- **单 A**：Approval Capability Registry —— 全量登记触发审批工具 + 12 字段 + 高频优先级排序（B 的输入）。

- **单 C（建议）**：真实场景测试矩阵 —— A/B 完成后用 7-10 场景实测验证（是否 2s 内看懂），产出结论驱动迭代。
- **依赖**：A 先行；B 依赖 A；C 依赖 B 的弹窗 + 生成器就绪。
