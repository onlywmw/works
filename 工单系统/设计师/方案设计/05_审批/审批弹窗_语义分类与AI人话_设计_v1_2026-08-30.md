## 〇、一句话

**审批弹窗现在给用户看的是 `shell.exec` / `command=...` 这类技术黑话;本设计要让它只说人话——用「用户语义分类 + AI 生成人话 + 直观弹窗」三层,让用户一眼看懂"AI 想替我干什么、要不要同意",并让这套适配自动化(不再逐个手写)。**

---

## 一、背景与来源

- **用户诉求**：「审批弹窗不能给用户看专用名词;我们要出很多弹窗(每个工具都会),要一目了然;不能每次都手工适配,要跟 AI 结合——让 AI 识别内容,自动生成人话。」
- 用户对现有弹窗的评价：「设计的什么玩意、看不懂、画面不直观」 → 已出直观版 UI demo(v4,用户确认)。
- 用户质疑「审批机制没做好分类」 → **本设计做了溯源验证,结论部分成立**(见 §二)。

---

## 二、溯源验证（§七 六层 · 现状诊断）

**触发链**：AI 调工具 → `McpToolScheduler.dispatch` → `PermissionGuard.guard` 判定 `ASK` → `ApprovalService.request` → UI 弹窗(answerer) → 用户三键 → allowed-once/turn 执行。

**六层判定**：

| 层 | 现状 | 判定证据（commit/main 实码） | 结论 |
|---|---|---|---|
| L1 用户可感知 | 弹窗显示 `AI 请求执行：shell.exec/ 原因：默认权限…/ 参数摘要：command=echo…` | `MainActivity.kt:6155 buildApprovalMessage`（技术词全量直出） | ❌ 全黑话，用户看不懂 |
| L2 入口/桥接 | ASK 路径 → answerer(UI) 单一回答者 | `ApprovalService.kt:155-167` | ✅ 链路通 |
| L3 服务/数据 | PermissionGuard.guard 三档判定 | `McpToolScheduler.kt:201-230` | ⚠️ 有风险分级，无用户语义 |
| L4 运行时装配 | 弹窗随 MainActivity 装配 | `:3570-3586` | ✅ 在案 |
| L5 能力实物 | 名单全集：systemBaselineDeny/sensitive/harmless/writeTools | `McpToolScheduler.kt:87-132` | ⚠️ contains 子串匹配，脆弱 |
| L6 持久化/事实源 | turnAllowSet/纯内存；无「工具→人话」持久层 | `ApprovalService.kt:50-63` | ✅ 无平行写点；**缺语义映射层** |

**现状诊断（回应用户"分类没做好"）—— 部分成立**：
1. **有"风险分类"但非"用户语义分类"**：grade = gate/ask/free（技术风险三档），不是"读文件/写笔记/拍照/发消息/执行命令/改系统/装应用"这类用户能懂的类型；
2. **展示层零语义**：弹窗直接抛 toolName + reason + 参数摘要，无一句用户向描述；
3. **分类基线脆弱**：全部用 `contains` 子串匹配（`writeTools.any{name.contains(it)}`），前科 = `BP-03`（else→ALLOW 静默放行）、`obsidian.file.write` 被 `file.write` 误捕（挂账[UPG-02+04] P1，UPG-28 已修精确匹配但同类风险仍在）；
4. **无"工具→人话"语义映射层**：即本设计要补的核心。

> 结论：**风险判定(gate/ask/free)可保留作"安全基线"**；在其上**叠加"用户语义分类 + AI 人话生成 + 直观弹窗"层**；并对 contains 分类做加固（精确匹配/结构化）——分层不推翻。

---

## 三、设计目标

1. **统计**：全量盘出「会触发审批的工具清单」（ask 主源 + 敏感 + 高危），作为适配地基；
2. **用户语义分类**：把触发审批的工具归入用户可懂的类型（读文件/写笔记/拍照扫码/截图/执行命令/改系统设置/发外部消息/装卸应用/记帐…）——这是"分类"的正解；
3. **AI 人话生成**：LLM 依据工具元数据 → 一句人话（"AI 想帮你把会议纪要存成笔记"），**自动、可缓存、有兜底、不编造**；
4. **直观弹窗落地**：用已确认的 demo v4 UI，弹窗只呈现人话 + 语义分类 + 同意/拒绝 + 倒计时；
5. **加固分类基线**：修复 contains 脆弱性（关键名单精确匹配 / 结构化），防误捕漏网。

---

## 四、核心设计 · 四层架构

```
┌────────────────────────────────────────────────┐
│  L1 展示层  直观弹窗(仅人话+语义图标+同意/拒绝+倒计时)  │
│  L2 A路人话  AI 生成人话 → 缓存 → 兜底 → 人工覆盖      │
│  L3 语义分类  工具 → 用户类型(读/写/拍/发/执行/改/装…)    │
│  L4 权限基线  gate/ask/free(现有·加固 contains→精确)   │
└────────────────────────────────────────────────┘
```

### L4 权限基线（保留 + 加固）
- 沿用 `permissionTier`(gate/ask/free)做**安全基线**（判定"要不要弹"）；
- **加固**：敏感/写类关键名单从 `contains` 改**精确匹配前缀/全名**（消 `obsidian.file.write` 被 `file.write` 误捕类风险）；保留 `file.write` 工作区 + private 特判、`isHighRisk`(shell.exec/凭据路径)。

### L3 用户语义分类（**新增 · 这是"分类"的正解**）
- 每个触发审批的工具 → 一个**用户语义类型** + 一个**语义图标** + 一句**人话模板**；
- 分类维度（用户能懂，非风险）：
  | 用户类型 | 例 | 人话核心 |
  |---|---|---|
  | 📝 写内容/笔记 | note.create、obsidian.file.write、memory.save | "存一条笔记/写点内容" |
  | 📄 读写文件 | file.read/write | "读/写一个文件" |
  | 🖼️ 拍照/扫码 | camera.capture、qr.scan、screen.capture | "拍张照/扫个码/截个屏" |
  | ⚙️ 执行命令 | shell.exec | "在设备上执行一个命令" |
  | ⚙️ 改系统设置 | torch/wifi/volume/bluetooth/brightness/silent | "打开/关掉 XX" |
  | 📨 发外部消息 | sms.send、notification.post、a2a.message | "发一条消息/通知" |
  | 📦 装/卸应用 | market.install/uninstall/enable/disable | "安装/停用一个能力" |
  | 🔐 读隐私信息 | contact/location/call.log/identity/sms.read | "读你的联系人/位置/通话…" |
  | 💼 记账/业务 | payment.pay、causal.*、booking/task | "记一笔/处理一个业务" |
- **分类器**：优先**精确名单**（写死大类映射），未覆盖工具走 **AI 归类**（依据 name+desc+args）。

### L2 AI 人话生成（**新增 · 核心机制**）
- **输入**：toolName + desc(UPG-01 三件套已有) + args 摘要 + 用户语义类型；
- **生成**：LLM 依据上述 → 一句人话「AI 想帮你 <用户类型话术> <对象>」（如"帮你把这段会议纪要存成 Markdown 笔记"）；
- **生成范围（v2，大神①）**：高频/核心工具(清单内标记)为**人工预设人话**，预生成、零延迟;仅长尾工具走 LLM 生成 + 工具级缓存;
- **人话 = 模板 + 参数槽位（v2，大神②⑤）**：工具级人话不能是死句,需带**参数槽位**,且参数也**语义化**(`rm -rf /tmp/cache` → "删除临时缓存文件夹",不是裸命令)——`shell.exec` 万能工具因此不会变成空泛的"执行一个命令";
- **缓存**：**工具级**缓存（同一工具人话基本恒定），生成一次复用；存内存/配置态，不每次弹窗调 LLM（省 token + 快 + 确定性稳定）；
- **兜底不编造（UPG-06 原则）**：LLM 生成不了/置信度低 → 显示安全模板「AI 想执行一个操作」+ 该工具的用户语义类型 + 工具名，**绝不编造具体行为**；
- **人工覆盖核心**：对高频/高风险工具(`shell.exec`/写文件/发消息/支付/隐私读)预设**高质人话**，作为 AI 学习样本 + 固定覆盖（保证这些最容易出错的场景质量）；
- **透明**：人话旁可灰字标来源（工具名），不加掩饰。

### L1 展示层（直观弹窗 · 已确认 demo v4）
```
        ┌──────────┐
        │  📝 图标   │
    AI 想帮你存一条笔记      ← 人话(人工/AI+参数槽位)
   把这段会议纪要存成 Markdown…   ← 一句话说明(参数语义化)
   ──────────────────
    30 后 AI 会自动取消这次操作    ← 倒计时(默认30s, 设置可调)
   [ 同意 ]    [ 拒绝 ]
   ☐ 本次对话中,该操作的这类都直接同意   ← 范围=工具+参数模式
   这条操作会被记录 ×──      ← 极灰小字(信任提示)
```

> v2 修订：倒计时 20→30s(大神③)；"同类同意"收窄为"该工具+该参数模式"(大神④)；底部加"这条操作会被记录"灰字(大神⑦)。

## 六、关键设计决策（待拍板）

| # | 决策点 | 选项 | 提议 |
|---|---|---|---|
| D1 | 人话生成时机 | ①工具注册预生成缓存 ②首次弹窗时生成并缓存 | ②首次弹窗生成+缓存（注册预生成会一次性大量 LLM 调用；首次命中再生成最省） |
| D2 | LLM 调用面 | 本地 / 云端 API | 跟随项目现有 LLM 通道；**需确认成本与离线** |
| D3 | 分类粒度 | ①粗(几大类,人工钉死) ②细(每工具)+AI归类 | ①粗为主(用户可懂) + 未覆盖走 AI 归类 |
| D4 | contains 加固 | 精确前缀全名 / 保留子串 | 高危(`shell.exec`/隐私读)/写类关键名单 → 精确优先,避免误捕与漏网(消 BP-03) |
| D5 | AI 人话置信阈值 | 低→兜底模板 | 阈值宁可保守(生成不出就兜底),不编造 |

## 七、验收测点（随单）

- **L1**：① 触发审批工具清单完整性(与 writeTools/sensitive/highrisk 全量对账,无漏) ② 语义分类器对清单逐项命中(用户类型正确) ③ AI 人话生成:有缓存、无编造(断言"AI 想帮你 X"句,样本含 shell.exec/写文件/发消息) ④ 兜底:LLM 不可用 → 模板+工具名,零编造 ⑤ 加固:关键名单精确匹配(变异:改回 contains 误捕 obsidian.file.write → 必红)。
- **L2 真机**：触发多种工具(shutdown.exec/写文件/拍照/装应用/读隐私) → 弹窗各显示正确人话 + 语义图标 + 倒计时;用户点同意/拒绝/本轮均生效;journal 审计成对落;goal 豁免(批2)场景四键可达。
- **L3**：与 UPG-06(确定性防编造)/UPG-01(元数据)/本机能力语义一致无冲突。
- **Token/KV 申报**：LLM 生成人话 = 一次性工具级调用(缓存后零新增);AI 面不进人话(弹窗仅内需)。
