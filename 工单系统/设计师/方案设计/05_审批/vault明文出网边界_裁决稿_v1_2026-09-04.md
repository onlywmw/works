# vault 明文出网边界 · 裁决稿 v1（设计师B @2026-09-04）

> 关联挂账：`挂账-vault明文出网边界裁决【⏳ 待审】`（P1）｜ 关联单：UPG-28 审批闸 / UPG-61 only-once 集 / UPG-75 审批交互
> 状态：⏳ 待审——大神评审 + 用户拍板后转契约/实现任务

## 一、问题复述（一句话）

**`vault.get`（MCP 工具）批准后，敏感明文会进入 LLM 上下文 → 随请求出网到 DeepSeek 云**；用户点「同意读取」时，不一定意识到「内容将用于 AI 回答（=离开设备）」——而仓库里**已有**一条正确通道（`vaultPlain` 直填：解密 → 只填页面/AI 不可见 → 不出网）。

## 二、现状两通道对比（MainActivity 617-753 区 + WorkflowRunner:13-208 实证）

| 维度 | `vault.get`（MCP 工具路径） | `vaultPlain`（S3 workflow 直填路径） |
|---|---|---|
| 入口 | agent 调工具 → 审批闸（only-once 必弹） | workflow fillForm `from=vault.*`——先 `approveVaultRead` 审批 |
| 明文去向 | 批准后明文作为**工具结果进 LLM 上下文** → 随模型请求出网 | 解密后**只直填页面字段**，不进 AI 上下文 |
| 审批文案 | 「同意读取」类文案 | `vaultSpecLabel`（只列字段**中文名**，绝不含值）+「明文只直填页面，不展示给 AI」 |
| 用户知情 | 未明示「内容将用于 AI 回答」 | 已明示（文案在案） |

## 三、问题本质

不全是实现缺陷，是**边界语义不统一**：同一种数据（信息库明文）走两条通道，一条**出网知情**（vaultPlain 明示），一条**知情不足**（vault.get 只讲「读取」，不讲「用于 AI 回答=出网」）。用户的信任假设=「保险柜里的东西我在用，但我没说可以给外面」；实际 vault.get 会把内容交给云端模型。

## 四、裁决选项

| 选项 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A（建议）** | vault.get 保留（agent 工具语义不变），但**审批卡文案升级为明示**：「读取后内容将用于 AI 回答（会发送到云端模型）」；同时**默认敏感类字段（cred.*/密码）在 vault.get 返回前脱敏遮蔽**（只给引用/前 2 位），需要明文走 vaultPlain 直填 | 改审批文案+i18n+部分 handler 返回面 | 低——语义不变，只是知情更透明 |
| B | vault.get 一律改走 vaultPlain 式直填（明文永不进上下文） | **工具语义大改**：agent 拿不到值就无法基于内容推理（如自动配置）→ 破坏现有能力面 | 高——能力断链，需重设计 |
| C | 全量出网明文需**二次独立确认**（除审批双确认外再加「明确同意出网」确认） | 交互加一步（用户已嫌弃弹窗多——UPG-75 方向是「少弹窗」） | 与 UPG-75 冲突，暂缓 |

## 五、建议裁决（待评审）

**采纳 A**：
1. `vault.get` 审批卡文案增加「**内容将用于 AI 回答（发送至云端模型）**」明示（i18n 中英双字典；UPG-75 卡片文案范式）
2. **cred/password 类字段在 vault.get 返回值中脱敏**（`field***` 遮蔽；完整值仅 vaultPlain 直填可拿）——默认安全：agent 绝大多数场景不需要完整凭据（只验证存在性/用户-平台对）
3. 保留 vaultPlain 直填作为**唯一完整明文通道**（S3 已实证：明文不进 AI 上下文）
4. 豁免面：用户显式选择「允许完整读取」（审批卡带第二个选项/或设置开关）——后续单细化 UI

## 六、影响面（若采纳 A）

- `tools/vault` 面：vault.get handler 返回值脱敏分支（纯函数可测）
- `PermissionRegistryData`：vault.get 审批级别描述/yaml 更新
- 审批卡文案：ApprovalService/审批卡渲染（i18n en/zh）+ 契约锚（文案断言防回退）
- 测试：JVM 脱敏纯函数用例 + 审批文案锚 + 变异（脱敏分支删除→红）
- 不做：不动 vaultPlain 通道；不动 only-once 集合（vault.get 保留必弹）
