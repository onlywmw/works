# 工单分类标准 v2.1（定稿 · 2026-09-02）

**状态**：✅ 定稿（两轮大神评审全采纳：v1→v2（9/9）+ v2→v2.1（工程级 7 条）详见 §七）
**前序**：`工单分类标准_设计_v1_2026-09-02.md`（溯源保留）
**目的**：每张工单「1 主分类 + 0~N 标签」——可检索、可盘点、可统计、可防呆

> **总纲（核心原则）**：主分类描述「**这张工单主要在建设什么**」；标签描述「**这张工单还具有什么属性**」。

---

## 一、背景与现状

工单系统原有三维（优先级/线/状态）只回答「多急/谁在动/到哪了」，**没有「这单是什么」**——同类的找不到、盘点靠人肉。本标准的**核心目标**：分类必须嵌进派单与交付流程（必填），不做「回填一次就完事」的一次性动作。

---

## 二、主分类（8 类 · 按工作性质定）

| # | 分类 | 定义 | 判定一句话 | 举例 |
|---|---|---|---|---|
| M1 | **安全 / 合规** | 权限/审批/隐私/审计/红线——不做会出事 | 「这条有红线吗？」 | 审批白名单、隐私政策弹窗、脱敏 |
| M2 | **体系 / 治理** | 改造自己的工具/流程本身 | 「这是在改工单系统/契约/流程吗？」 | 工单系统自改、契约体系、改造计划 |
| M3 | **平台 / 基建** | App 框架/构建/CI/部署/保活——**不包含外部能力接入** | 「不弄它 App 能正常活着吗？」 | 构建链、Termux 保活、双体架构 |
| M4 | **工具 / MCP 集成** | 接「外部能力」入 MOV——第三方工具库/API/协议 | 「是在接别人的能力吗？」 | Obsidian 工具包、12306、浏览器 WebMCP |
| M5 | **商业 / 账号** | 钱/人/账号/经营面 | 「跟钱/人/账号有关吗？」 | 注册登录、支付、风险控制 |
| M6 | **记忆 / 知识** | **只管「AI 怎么记/怎么学」的机制与内容** | 「在让 AI 变聪明一点吗？」 | 记忆体系回补、教训蒸馏、Memory API |
| M7 | **用户资产 / 数据资产** | 用户数据/文件/密码库/资产模型/迁移 | 「在管用户的资产/数据吗？」 | 资产管理注册、vault→credential 迁移 |
| M8 | **UI / 交互** | 外观/组件/页面/手感 | 「用户能看见/摸到的那层？」 | 外观组件级显示、卡片、气泡分流 |

> 兜底：以上都不沾 → **「待定分类」人工裁决**，不许默认为 UI（防掩盖分类缺失）。

### 2.1 边界判例（易混对 · 必查）

| 易混对 | 判定 |
|---|---|
| **M4 工具/MCP vs M3 平台/基建** | 外部能力**入 MOV** = M4；内部运行环境 = M3（如「接外部 API 做保活」→ M4 工具集成；「本机保活机制」→ M3） |
| **M1 安全/合规 vs M5 商业/账号** | 只要涉及**权限/审计/红线** = M1；纯注册/支付流程 = M5（如「登录风控」涉及安全 → M1；「注册表单」→ M5） |
| **M6 记忆/知识 vs M7 用户资产/数据** | M6 只管 **AI 记忆/学习的机制与内容**；**通用数据/文件/密码库迁移归 M7**——哪怕迁移对象是记忆数据（如「记忆数据迁移」→ M7 数据资产） |

### 2.2 M5「模板」限定

- 商业/协议/账号模板 → M5
- 页面/组件模板 → M8
（不按字面「模板」二字归类，按模板的**主体**归类）

---

### 2.3 反例裁决表（优先级最高的纠偏工具）

| 错误倾向 | 错误分类 | 正确分类 | 原因 |
|---|---|---|---|
| 标题出现「安全」就归 M1 | M1 | 按主要交付物 | 安全可能只是横切属性（如 UI 加安全提示→M8） |
| 出现 MCP 就一定 M4 | M4 | 按主要交付物 | MCP Runtime 自身改造可能 M3/M2 |
| 出现「数据」就归 M7 | M7 | 按数据用途 | AI 记忆机制属于 M6 |
| 页面涉及支付就一定 M5 | M5 | 按主要目标 | 支付风控整改可能是 M1 |
| 有用户可见变化就 M8 | M8 | 按主要交付物 | 后端改造导致 UI 变化仍不一定是 M8 |

## 三、标签（0~N 个 · 枚举受控）

| 标签族 | 值 | 说明 |
|---|---|---|
| **动作** | 新增 / 修复 / 重构 / 迁移 / 合规整改 / 收尾 | 这次改动的性质 |
| **对象** | app / web / 文档 / 脚本 / 契约 / 部署 / **数据/模型** / **工具/MCP** | 改到什么层 |
| **触发** | 用户报障 / 主动改造 / 评审要求 / 合规要求 / 验收打回 | 谁发起的（**不含**「用户可感知」——感知是结果不是触发） |
| **性质** | 安全 / 性能 / 体验 / 兼容 / 回归 / 治理 | 横切面——**`安全`仅当主分类≠M1 时使用** |

### 3.1 防同名冗余规则

> **主分类已表达的属性，标签不重复打同名词。**
> 例：主分类=M1 安全/合规 → 标签**不打** `性质=安全`（除非还有另一层横切含义）；主分类=M4 → 标签 `对象=工具/MCP` 用于标注集成对象（M4 表达的是「接外部能力」，`对象` 表达的是「接什么」）。

---

### 3.2 标签词典（系统维护 · 禁止自由造词）

- **标签词典由系统维护**——用户只能从枚举值选择，**禁止自由输入**；新增标签必须设计师裁决后入典
- **基数约束**： **单选**； **单选**； 0~N； 0~N
- 标签表：（枚举唯一权威）；JSON 存储按 （干净、可统计）

---

## 四、分类规则（判定算法 · 主要交付物为唯一依据）

**分类依据（第一原则）**：按**本工单主要交付物/主要改动对象**判定——不按标题、需求来源或最终影响。

**主分类只取 1 个**；判定算法（主要交付物为唯一依据）：

```
第 0 步（动作预判）：若动作 = 纯迁移/数据搬迁
       → 先判「迁移对象属于哪个领域」→ 直接落该领域主分类
       → （记忆数据迁移→M7；密码库迁移→M7；能力迁移→M4；等等）

第 1 步：安全/合规     → 有红线/权限/隐私/审计
第 2 步：体系/治理     → 在改工具/流程本身
第 3 步：商业/账号     → 钱/人/账号/模板（商业主体）
第 4 步：记忆/知识     → AI 记忆/学习机制与内容
第 5 步：用户资产/数据 → 用户数据/文件/密码库/资产
第 6 步：平台/基建     → 框架/构建/部署（不含外部能力接入）
第 7 步：工具/MCP 集成 → 接外部能力入 MOV
第 8 步：UI/交互       → 都是用户可见面
第 9 步：待定分类       → 都不沾（人工裁决，不许默认为 UI）
```

- **一个单多类**：主分类取第一个命中；复合属性全部进标签（如 12306 集成+合规整改 → 主分类 M4 + 标签 `合规整改/修复/对象=工具/MCP`）
- **动作预判只对「纯迁移/数据搬迁」起效**——其余动作正常走树

## 五、落位（进系统）

| 位置 | 改动 |
|---|---|
| 工单表 | 新增「分类」列（单值）+「标签」列（**JSON/数组结构**——不强用逗号文本，如 `[{"k":"动作","v":"迁移"},{"k":"对象","v":"app"}]`，展示层拼接） |
| 工单库卡 | 状态区加 `分类：M4 工具/MCP 集成` + 标签节点 |
| 看板 | 主表加分类筛选；摘要卡可按分类统计 |
| 派单/交付 | **派单文本必写分类**；交付报告带分类（分类必填嵌流程，防一次性回填后无人维护） |

### 5.1 回填流程（58 张历史卡 · 全量一次性）

1. **创建者初填**（设计师/程序员按标准填各自卡）→ **设计师终审**
2. **争议卡进「待定分类」**（不硬塞）——每周清理一次，不留垃圾堆
3. 回填后**看板按分类统计一次**，检查分布合理度（有无某类异常多/少）

---

## 六、稳定性与统计边界

### 6.1 分类冻结

- 分类**默认在工单创建/派单时冻结**
- 只有**需求范围或主要交付物发生实质变化**才允许变更
- 单纯执行中发现理解错误，不得为统计方便改分类（改=进留痕登记）

### 6.2 待定分类 SLA

- **待定是异常状态，不是正式分类**（不进入正式统计）
- 超过 **7 天自动进入设计师待裁决列表**；每周/两周清理

### 6.3 统计边界

> **分类统计仅用于结构盘点，不代表工作量/成本/优先级**；工作量/优先级由原有维度负责（防分类数量被误用作绩效/资源判断）。

---

## 七、变更留痕（硬规则）

> **分类变更必须进卡状态区登记**，格式：
> `原分类 → 新分类 | 原因 | 裁决人 | 日期`
>
> - 仲裁总归口：**设计师**
> - 不允许无痕改分类
> - 「待定分类」每周/每两周清理一次（不长期滞留）
