**状态**：✅ 总纲 v1（用户质疑「弹窗没成体系、总是修 bug」——应答：属实；本总纲=一次性定尾态，替代继续打补丁）

## 1 核心判断（如实）

审批相关过去 6+ 单（AB 模式→UPG-53 体验→61 伪放行→68 安全闸→75 交互收口→76 预审单）**每一单都是局部正确**，但：
- 无**总数据流图**（请求从 LLM 到用户手指的完整路径）
- 呈现层**从未跑通**（验收员 §P30「环境阻塞」→ 今天真机证伪=运行时空缺）
- 每个单只改一层，层与层接口是「即兴契约」

**结论**：功能正确性高（安全语义层层有），**体系性为零**——用户「很难用、总修 bug」是准的。

```

│ 支付例外：MONEY 永不预批（UPG-76 语义）           │

└────────────────────────────────────────────┘
```

## 3 关键缺口（本次断链根因的性质）

1. **呈现层无单一组件**：弹窗/通知/待办/入口 chip 四处散落（MainActivity 内联 AlertDialog + NotificationAnswerer + chip 刷新），**没有「ApprovalSurface」抽象**——运行时不可测、不可替换、不可锁定。
2. **三渠道无共同数据源**：弹窗决定「waiting」、通知决定「pendingInfos」、chip 读「onQueueChanged」——三份状态。
3. **无组件级测试**：JVM 只测 L0/L1（ApprovalQueue/OnlyOnceGuard/PermissionGuard），**L2 呈现层 0 测试**（这正是「静态全对、运行时黑洞」的来源——§P30 复验就卡在这）。
4. **single-shot answe**r 与生命周期竞态**（approvalDialog 全局单例 + finally dismiss）——真实现象：并发/切换时机弹窗被吞。
