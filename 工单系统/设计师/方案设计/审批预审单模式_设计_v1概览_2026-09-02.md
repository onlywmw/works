# 审批预审单模式 · 设计 v1 概览（2026-09-02 用户拍板）

**一句话**：LLM 执行前先“扫一遍”汇总出一个**审批单**（要做什么/各步工具+参数+理由），用户**同意=整批执行，不同意=不做**；**付钱永远不能预批**（支付步骤即使单子同意，执行到该步仍要实时逐笔确认）。

关联：UPG-75（交互收口——队列/待办/渠道统一）、UPG-68（安全语义）、UPG-73（STALE 五元同验）。

## 1 用户痛点（原话归纳）

「运行中随随时就来个弹窗审批，多麻烦」——现行模型：LLM 边跑边申请，用户被碎片化打扰（且并发弹窗互相盖——UPG-75 根因）。用户判：**体验该是「先给单子，我批一次，然后你去做」**。

## 2 模式定义

```
用户指令 → ① 扫描阶段（只读探察：读工具目录/参数推断/列拟调用清单，零副作用）
        → ② 审批单呈现（结构化：意图摘要 + 步骤清单[工具/参数/侧效应/理由/顺序] + 提示支付例外）
        → ③ 用户裁决（同意全部 / 部分同意 / 拒绝 / 修改后再提）
        → ④ 执行阶段（按批准清单推进；每步仍过 only-once/fail-closed 兜底闸）
```

### 关键语义
- **预审单 ≠ 绕过安全闸**：批准的是「意图清单」，执行时 UPG-68 的 only-once / fail-closed / 嵌套闸全部保留（防批准后清单被换头）。
- **TOCTOU 防护**：审批单批准时**快照清单指纹**（参数/顺序/能力版本），执行阶段逐维复验——**复用 UPG-73 五元同验/STALE 机制**（fingerprint 漂移→APPROVAL_STALE 旧批作废不执行）。
- **支付例外（硬规则）**：`side_effect=MONEY` 的步骤**永远不预批**——审批单明示「含支付步骤，执行到该步将单独实时确认」；支付确认=逐笔（金额/收款方/不可撤销提示），无论如何勾选都不豁免。
- **部分同意**：单子按步骤拆行，用户可勾掉某些步骤（该步不执行；后续依赖步骤自动标记「因前置未批而跳过」）。

## 3 与 UPG-75 的关系

- UPG-75（已派）=「**交互层收口**」（队列/待办列表/渠道统一）——是**必要兜底**：预审单本身也需弹窗/通知；且存在「用户说『先做，中途再问』等仍会运行中审批」的场景。
- **预审单模式 = 主交互升级**（编排层）：审批从「运行中碎片」变「运行前一张单」——**解决根因**。
- 建议：UPG-75 范围不变照做；**预审单模式另立单**（或并入 UPG-75 作为主路径——取决于已派单的进度与认领人）。

## 4 范围初判（供拆解）

- A1 扫描阶段：LLM「预演」只读探察（复用现有只读工具面；描述=参数/理由生成）——编排层新增 plan 请求
- A2 审批单 UI：结构化清单卡（意图/步骤行/勾选/支付行明示），前台弹窗+后台通知
- A3 批准清单状态机：plan→(部分)approved→executing；fingerprint 快照+逐维复验（复用 ExecEngine/ApprovalBook）
- A4 支付例外执行闸：MONEY 步骤实时逐笔确认（复用 UPG-73 dispatch）
- A5 失败语义：用户拒绝=撤销后续全部；执行中失败停止并汇报（可再提新单）
