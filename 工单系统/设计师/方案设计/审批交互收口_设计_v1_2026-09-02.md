# 审批交互收口 · 设计 v1（2026-09-02）

**状态**：✅ 方案 v1（用户拍板「立正式工单」——弹窗并发挤占实测触发）｜ 关联：UPG-75、UPG-68（安全闸线）、挂账×3

## 0 触发背景（2026-09-02 平板实测）

用户演示「注册元能力 fulfillment.track 调用」时暴露：LLM 并行 tool_call（shell.exec×N + fulfill.track）产生多个并发审批请求——
- 用户点「同意」放行的是 **shell.exec 弹窗**（每次都弹）；**fulfill.track 的请求（req-8/9）弹窗从未被看到**——后弹盖前弹（单弹窗无队列）
- 60s 超时自动关闭（fail-closed 正确）→ 用户连「拒绝/确认」机会都没有
- LLM（非常诚实）建议用户「找审批待确认列表」——**该 UI 不存在**
- 结论：审批交互是「一次一弹」原型思维，LLM 并行工具调用时代撑不住

## 1 根因（现状解剖）

| 渠道 | 实现 | 问题 |
|---|---|---|
| 前台弹窗 | `buildApprovalDialogView`（MainActivity:4369-4396，AlertDialog+30s 计数） | **单弹窗无队列**；并发 answerer 调用→后者覆盖前者；被覆盖请求 60s 超时静默丢弃 |
| 后台通知 | NotificationAnswerer（允许/拒绝按钮） | 通知渠道独立；回前台 `onStart takePending` **只取一条**——多条 pending 丢 |
| 回前台接管 | `onStart`（MainActivity:7661-7690） | 第三套逻辑；与前台弹窗/通知互不知情 |
| 待办列表 | **无** | 无任何「待确认请求列表」UI |

安全语义本身经 UPG-68 收口（fail-closed/only-once/嵌套审批闸）是**正确的**——差的是**交互层**：队列/可见性/待办。

## 2 范围

- **A1 弹窗队列**：Agents 审批请求单队列（FIFO）；同一时刻仅展示一个；弹窗顶栏「待审批 N 条·第 i 条」；关闭/超时自动切下一条（不丢）。
- **A2 审批待办列表**：侧边栏（或安全中心）「审批待办」入口——列出全部 pending（工具名/参数摘要/请求时间/状态）+「允许」「全部本轮允许」「拒绝」；列表与弹窗同源（同一队列投影）。
- **A3 渠道统一**：前台弹窗 = 待办列表首条的沉浸形态；后台 = 通知（按钮沿用）；回前台 = 渲染同一列表（删 `takePending` 单条逻辑）；三渠道同一数据源。
- **A4 超时语义保留**：60s fail-closed 不变；超时项进入**审批足迹**（可查）并给 toast「已自动拒绝」。

## 3 不做

- 不改权限判定/审批安全语义（UPG-68 成果不动）
- 不做 push/桌面通知扩展（本卡=同屏交互）
- 不重新设计审批弹窗视觉（沿用大白话 v4）

## 4 验收锚

- A1-1：并发 3 个 tool_call → 依次弹 3 个窗，逐个可点，无丢请求（足迹 3 条均有结论）
- A1-2：首窗超时自动拒绝 → 下一窗自动出现（不阻塞）
- A2-1:待办列表实时反映 pending（数字+条目）；「全部本轮允许」后队列清空且全部 APPROVED
- A3-1:后台通知→回前台=同一请求变列表首条（非新弹窗）；无重复/无丢失
- A4-1:超时项在足迹可见（APPROVAL_TIMEOUT 或近似条目）
- 变异亲杀：队列被改为「只保留最新一条」→ A1-2 红
