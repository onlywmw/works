# SYS-04 状态登记结构化治理 · 方案（工单系统自身改造）

> 设计师 @2026-09-05 ｜ 用户拍板立项
> 触发：2026-09-05 五连事故（UPG-18 已合 7 天未登记 / UPG-81+85 已合挂「待合」2 天 / UPG-65 错挂打回装「回炉」5 天 / UPG-52 续行漏读误报「待领」 / ACCEPTANCE_LOG 合并丢 40 段）+ 验收段错挂邻卡三现（已知坑 #9）
> 治理边界：只动本仓库（工单系统）；不进 UPG 主线；机器只出 flag 人终裁

---

## 〇、一句话

**状态登记从「手写散文+正则猜测」改为「结构化状态块+脚本写入闸+对账入流程」——写入端收 schema，读取端免猜，对账自动化。**

---

## 一、病根（为什么修不好）

| 层 | 现状 | 事故 |
|---|---|---|
| 写入端 | 自由散文，写哪行/哪个卡/什么词全凭自觉 | 三次错挂邻卡；续行/卡点行散落 |
| 读取端 | sync-orders 用正则锚猜角色列 | 「不得合 main」被误提进合 main 列（09-05 实证） |
| 对账 | 无自动核对，纠错=用户抽查 | UPG-18 挂 7 天靠用户问出 |
| 纪律 | 「只有设计师能写库卡」口头约束 | 多线 agent 直接写库卡无人拦 |

既有治理（STD/DEL/审验.py）加固的是**交付链**；**状态写入链**一直是裸的。本单补这一环。

---

## 二、方案（三件）

### 2.1 卡面结构化状态块（schema）

每卡新增一个机器可读块（散文区不动，留作历史/详情）：

````text
```status
phase: merged             # 枚举：registered/dispatched/claimed/in_progress/delivered/accepted/audited/merged/closed/rejected_work/obsolete/on_hold
branch: feat/upg107       # 无分支=—
head: 4e5a2f7c            # 当前交付/合并 hash（短 sha）
std: STD-UPG-107-v1       # 无=—
delivery_id: DEL-…        # 无=—
actor: 设计师
updated_at: 2026-09-05T07:30:00
```
````

- **权威规则**：有 status 块的卡，块=唯一事实源，散文仅供参考；无块的卡=存量，退回既有启发式（渐进迁移，不强迁）
- **phase 枚举即流转顺序**（设计师→程序员→验收员→审验员→合 main 的状态机化）

### 2.2 写入闸：`set-status.py`（新工具）

```
python 审验员/set-status.py UPG-107 --phase delivered --head 4e5a2f7 --delivery DEL-UPG107-… --actor 程序员C
```

脚本内置全部现行纪律（**纪律从口头变代码**）：

1. 卡定位用工单号内容匹配（禁行号）
2. 写前备份 `_备份归档\`（五步铁律内化）
3. **归属校验**：branch 名必须含工单号小写（feat/upg107 ↔ UPG-107；不符=拒写——今天三次错挂全会被这条拦住）
4. **phase 合法迁移校验**（merged 后才能 closed；rejected_work 必须附注）
5. hash 校验：`git cat-file -t <head>` 存在性（写不存在的 hash=拒）
6. 写完自动 `sync-orders.mjs --sync` + `--check` 复核 diff=0
7. 任何角色都能跑（不再「只有设计师能写」——**权限从人转移到 schema+校验**），但写失败=登记无效

### 2.3 对账入流程 + 归属闸

- `recon-queue.py`（已落地）进**合批必跑**：设计师合 main 前/后各跑一次，🔴（分支已在 main 但表未闭环）= 暂停合批先核
- 验收段归属闸：验收员/审验员落档段含分支名（feat/upgN）时，登记卡号必须=N——先靠 set-status/登记模板强提示，v2 再机器拦

---

## 三、sync-orders 改造

- 解析优先级：status 块（schema 解析）> 既有启发式（存量兜底）
- 状态块的 phase/head/delivery_id 直接映射列——**角色列不再靠词猜**
- 存量 92 卡：从工单表**反投影生成基线 status 块**（表已是正确的机器投影）一次性回填，逐卡标注 `actor: sys04-backfill`

---

## 四、分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| 阶段 1 | status 块 schema + set-status.py（含归属/迁移/hash 校验+自动 sync） | 新单 UPG-107 全程走脚本登记；故意写错分支名=被拒实证 |
| 阶段 2 | sync-orders 双模解析（块优先）+ 92 卡基线回填 | check diff=0；抽查 10 卡块内容与表一致 |
| 阶段 3 | recon-queue 入合批门禁 + 归属闸提示入验收模板 | 合批流程文档化；模拟错挂=被拦实证 |

**不做**：不重写存量散文区；不动 STD/DEL/审验.py 既有链路；不改工单库文件格式（仅加块）。

---

## 五、验收要点（SYS 线口径）

- 机械可验：set-status 误写拒绝率（错分支/错 phase/假 hash 三案必拒）+ sync 双模 diff=0 + 回填块抽查一致
- 流程可验：UPG-107 全生命周期用脚本登记一遍（claimed→delivered→…→merged），每步表投影正确
- 防退化：既有 sync-orders --check / DEL 闸 / 审验.py 全绿不回归

## 六、风险

| 风险 | 处置 |
|---|---|
| 双写期块与散文不一致 | 块=权威写进规则；sync check 对块外散文状态词只警告不阻断 |
| 角色习惯切换成本 | 脚本 CLI 比手写散文更快（自动 sync+备份）；老写法不拦（不阻塞流程，只不产生权威状态） |
| 92 卡回填错配 | 从表反投影（表已是真相）；回填后 recon-queue 全量复核 |
