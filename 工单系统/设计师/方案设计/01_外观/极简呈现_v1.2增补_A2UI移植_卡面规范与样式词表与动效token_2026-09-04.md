## 〇、A2UI 深扒结论（前因后果，三条）

1. **A2UI 的漂亮不是 LLM 现生成的**——它内置一整套设计系统（`renderers/web_core/src/v0_8/styles/`）：M3 tonal palette（n/nv/p/s/t/e 六板 × 18 档色调 + `light-dark()` 明暗自动反转）、M3 type scale 十五档（11→57px）、4px grid 圆角/间距档位。**LLM 的 JSON 只能引用这些预置样式类名**，具体值由客户端 theme 决定。
2. **受信目录是双层的**：受信组件目录 + **受信样式词汇表**。我们此前只学到了第一层（引擎规则驱动选壳），样式词表这层是本次补齐的缺口。
3. **A2UI 仓里没有动效系统**（`behavior.ts` 全文只有 hover 透明度过渡）——谷歌的动效设计在 **Material Motion**（M3），不在 A2UI。动效 token 从 M3 拿（见 §三）。

> 「用谷歌的 UI 库」的落地形态：**拿 token 与机制，不引 runtime**。理由：A2UI runtime 是 Lit/Web 渲染器 + 为「LLM 生成 JSON」设计的协议，引入即违背军规「AI 不能生成交互制度」；而 token 是纯 CSS 变量值，MOV 本来就是 WebView 技术栈（tokens.css 体系），即插即用。
>
> **边界声明（大神评审提醒）**：A2UI/M3 作为 token 命名与设计治理的**参考**，不构成 MOV 的视觉风格继承约束——MOV Minimal = A2UI 的受信词表机制 + M3 的 token 化纪律 + MOV 自己的卡片叙事与状态层级，是原创组合，不是 M3 Theme。

## 一、卡面视觉规范（A2UI 软卡语言立规——替代 v1.1 §十 的留白处）

### 1.1 表面与描边

- **卡面一律无描边**（1px border 退役）；hairline（`--line`，8% 透明度）仅允许用于**卡内分隔线**（kv 行、清单分区）。
- 层级靠**投影 + 表面色阶**表达，不靠描边。

### 1.2 圆角档位（4px 网格，守 A2UI border-br-N 思路）

| 用途 | 值 |
|---|---|
| 内容大卡 | 22px |
| 决策小卡 | 20px |
| 卡内媒体区（图位） | 16px |
| 参数槽/标签底 | 12px |
| 小件（勾选框等） | 6-8px |
| 主钮/输入框/chip | 999px（全圆 pill） |

### 1.3 软投影 token（双层柔和，卡片「浮在空气里」）

```css
/* 浅色 */
--card-shadow:    0 8px 24px rgba(20,24,40,.08), 0 2px 6px rgba(20,24,40,.04);
--card-shadow-lg: 0 16px 40px rgba(20,24,40,.12), 0 4px 10px rgba(20,24,40,.05);
/* 深色 */
--card-shadow:    0 8px 24px rgba(0,0,0,.4);
--card-shadow-lg: 0 16px 40px rgba(0,0,0,.5);
```

内容卡/决策卡用 `-lg`；小圆片、契约条、输入框用基准档。

### 1.4 遮罩 scrim 令牌

- 浅色：`rgba(238,240,244,.55)` + `backdrop-filter: blur(3px)`
- 深色：`rgba(0,0,0,.5)`
- 决策遮罩比内容遮罩再深一档（v1.1 §三 L2/L4 不变，本处只定值）。

### 1.5 排版层级（caps 题 + 字重层级，不靠色）

- **caps 小字引导语**：10.5px / 700 / 字距 .12em / 大写 / text3 色——「今日推荐 · OFFER」「需你确认 · APPROVAL」；
- 卡题 20-21px/800；正文 13-14px；辅助 11.5-12.5px/text3；金额类 `tabular-nums`；
- pill 主钮纯黑（守拍板④），次钮 ghost（s2 底 + text2 字）；**例外=destructive 动作（拒绝钮）按 M3 用功能红**（`--danger-tint` 底 + `--danger` 字，见 §五）。

## 二、受信样式词汇表（Style Vocabulary——Registry 增补一层）

学 A2UI 双层受信机制，Registry 登记项增补 `style_tokens` 字段。本节含评审 P1-02/P1-03 吸收。

### 2.0 工程不变量 PV-01（冻结）

```text
PresentationData MUST NOT contain raw visual literals.
```

禁止：`fontSize: 18`、`color: "#FF0000"`、`borderRadius: 16`、shadow 字面量等一切原始视觉值；只允许引用词表词。解析隔离层拦在 Validated PresentationData 之前（与 v1.1 §七 Response Splitter 同一道闸）。**AI 可以组合设计语言，但不能修改设计语言。**

### 2.1 词表命名空间（冻结——评审 P1-02）

词表词一律带命名空间，裸词非法：

| 命名空间 | 管什么 | 例 |
|---|---|---|
| `type.*` | 排版 | `type.caps` / `type.title` / `type.body` / `type.meta` |
| `surface.*` | 容器表面 | `surface.card` / `surface.decision` / `surface.media` |
| `action.*` | 操作控件 | `action.primary` / `action.ghost` / `action.danger` |
| `data.*` | 数据呈现 | `data.kv` / `data.kv.total` |
| `status.*` | 状态语义 | `status.warning` / `status.danger` |
| `motion.*` | 动效意图 | 见 §三.2 |
| `layout.*` | 布局 | 按需扩展 |

命名空间是跨 Runtime 稳定层——将来原生组件 / WebView / MCP UI / 第三方组件共用同一套词，renderer 各自解析。

### 2.2 壳级白名单

每个呈现壳在 Registry 声明**允许使用的词表子集**：

```json
{ "component_id": "approval_card", "style_tokens": ["type.caps", "type.title", "surface.decision", "action.danger", "data.kv"] }
```

壳白名单之外的词出现在该壳的 PresentationData 中 = 拒收。

### 2.3 版本化 + 未知词策略（评审 P1-03）

- Registry 登记项带 `style_vocabulary_version`（当前 = `"1.2"`）；旧版 App 遇新词表的兼容问题由版本号显式化，不靠运气；
- **Unknown Token Policy（冻结）**：未知 style token → ① 拒收该 PresentationData → ② fallback 到壳默认样式 → ③ 记 telemetry。**禁止静默忽略**（「看起来还能渲染但局部设计失真」是最难排查的失真）。

词表新增/改值 = 修订本文档 + 版本号 +1 + 契约测试锚更新，业务单不许顺手加。

**军规延续**：LLM 是个只能挑词造句的诗人，词典是设计师编的——组件目录管「放什么」，样式词表管「长什么样」，两层都不归 LLM。

## 三、动效规范补强（M3 Motion token 对齐——答疑：谷歌有动效设计，在 Material Motion 不在 A2UI）

### 3.1 token 表（照 M3，代码里禁写曲线/时长的字面量）

| token | 值 | 用途 |
|---|---|---|
| `duration-short3` | 150ms | 微交互（勾选、hover） |
| `duration-short4` | 200ms | 小展开/收起 |
| `duration-medium1` | 250ms | 标准退场 |
| `duration-medium2` | 300ms | 卡片浮现/展开 |
| `duration-long1` | 450ms | 底座 docked 大转场 |
| `easing-standard` | cubic-bezier(0.2, 0, 0, 1) | 默认 |
| `easing-emphasized-decelerate` | cubic-bezier(0.05, 0.7, 0.1, 1) | 入场（浮现） |
| `easing-emphasized-accelerate` | cubic-bezier(0.3, 0, 0.8, 0.15) | 退场（收叠） |

### 3.2 Motion Intent Layer（冻结——评审 P1-01：组件层只准引用意图，不准直接引时长）

`medium2 = 300ms` 是实现参数，`enter` 才是设计语义。组件/业务层禁写 `duration-medium2`，只能引用动效意图词（归入 `motion.*` 命名空间）：

| intent | duration | easing | 用途 |
|---|---|---|---|
| `motion.enter` | medium2 300ms | emphasized-decelerate | 任何 Surface 浮现 |
| `motion.exit` | medium1 250ms | emphasized-accelerate | 收叠/退场 |
| `motion.expand` | short4 200ms | standard | 小展开/收起 |
| `motion.docked` | long1 450ms | standard | 底座 docked 大转场 |
| `motion.micro` | short3 150ms | standard | 微交互（勾选/hover/reduced-motion 退化档） |

结构冻结为三层：`组件 → Motion Intent → Duration Token + Easing Token`。新增 intent = 修订本文档，与 Memory OS 同一理念：**上层描述语义，不描述底层实现细节。**

### 3.3 与 v1.1 §五 三原语的对齐（原语不变，参数归 intent）

| 原语 | v1.1 原参数 | v1.2 对齐后 |
|---|---|---|
| 浮现 | 280ms / (.32,.72,.28,1) | `motion.enter`（medium2 / emphasized-decelerate） |
| 收叠 | 260ms | `motion.exit`（medium1 / emphasized-accelerate） |
| 层叠 | 后卡压前卡+遮罩加深 | 不变（遮罩值按 §一.4） |
| 底座 docked | 450ms | `motion.docked`（long1 / standard） |

`prefers-reduced-motion` → 全部退化 150ms（short3）淡入淡出，不变。听/说态眼睛 pulse（1.4s）保留为唯一循环动画。

### 5.1 Danger Semantic Allowlist（冻结——评审 P1-04：从文档纪律升级为 Runtime 可校验规则）

`--danger` 的合法语义用途冻结为四个词，Renderer 收到 danger 类样式请求时**先查语义白名单再解析**，不在表内 = 拒收（同 §二.3 未知词策略）：

| 语义词 | 用途 |
|---|---|
| `action.reject` | 拒绝钮 |
| `time.critical` | 倒计时环低时长段 |
| `payment.sensitive` | 支付行 |
| `security.sensitive` | 敏感关键词/脱敏提示 |

功能红不再扩面——纪律落成系统约束，不靠设计师盯。

## 附录 B · 个性化槽位选择契约（用户拍板方向 @2026-09-04：「商户信息尽量全 + 用户侧个性化显示」）

### B.1 三层模型

```text
① 全量事实层   工具 out schema 承载商户完整字段（有什么收什么，数据层零裁剪）
② 关注点画像   care profile ← Memory OS（ACTIVE 条目驱动；DRAFT 不驱动；敏感类绝不进——UPG-51 红线沿用）
③ 槽位选择层   LLM 持「全量事实 × care profile」做编辑选择——只准从骨架登记的**可选槽池**挑，禁发明新槽
```

边界冻结：LLM 选「给你看哪些事实」=编辑权（放行）；「怎么长」=渲染权（军规不变）。无画像信号 → 引擎默认槽（价格/评分/位置），确定性兜底。个性化输出过 PV-01/词表/白名单三道闸不变。

### B.2 可选槽池（骨架登记项扩展）

- offerCard.v1 增 `amenities` 槽（≤3 坑，chip 形态 `type.meta`）：酒店=早餐/浴缸/停车/取消政策；餐饮=辣度/等位/包间
- ticketCard.v1 增 `seat_pref` 槽：靠窗/靠过道/连座
- rideCard.v1 增 `ride_pref` 槽：拼车意愿/车型
- 槽池词入 `data.*` 命名空间；新增槽=修订本文档+登记纪律（candidate→registered）

### B.3 记忆种子集（测试基件）

种子文件：`方案设计\01_外观\个性化画像_记忆种子集_v1_2026-09-04.json`——8 条 ACTIVE + 2 条 DRAFT + 1 条敏感对照，每条带 `expected`（提炼标签+槽位选择期望），测试 load 后直接断言：
- 正向：酒店卡 amenities 槽含「含双早」（care.hotel.breakfast 命中）
- 兜底：无画像域（电影）= 默认槽
- 负向：DRAFT 条目不驱动；敏感条目（宗教/健康）绝不进画像
