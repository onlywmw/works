## 一、工单怎么流转（一张图）

```
设计师\       ← 源头：出方案、拆工单、维护工单库（工单库 = 派单权威）
        │  派工单（UPG-xx）
        ▼
程序员\         ← 程序员领工单 → 施工 → 交付报告放这
        │
        ▼
验收员\   ← 验收员验收（代码层+真机层，不信自报信实物）→ 结论落 ACCEPTANCE_LOG
        │
        ▼
审验员\   ← 审验员 AI 审验证据链（journal/截图/命令 对账，挑毛病→问题进处理中心）
        │
        ▼
        待设计师合 main（合 main 只归设计师）
```

### 📊 工单进度表（看每个工单到哪了）

**位置**：`工单库.md`（真相/派单源）+ `工单表.xlsx`（Excel 查看，2026-08-16 起）。

- **列 = 流转顺序**：设计师 → 程序员 → 验收员 → 审验员 → 设计师(合main)
- **行 = 工单**：每个工单流转到哪个角色，该角色列就填状态（✅ 完成 / 🔨 在施 / 📌 待派 / 🚀 待合 / ✅ 已合）；还没到的角色列显示「—」
- **用法**：按行看工单卡在哪一环；按列看每个角色手里有什么；Excel 版 `工单表.xlsx` 可筛选
- **同步规则**：进度更新时 md 与 xlsx 保持同步；工单状态变更先改工单表再改工单库

## 四、规则红线（全角色）

1. **合 main 只归设计师，且前提 = 真机验收通过**（验收员/程序员不碰；真机未验收项不可合）
2. 验收结论**落 ACCEPTANCE_LOG**（口头报告未落档 = 违规）
3. **不信自报信实物**——每条验收标准对应亲手产出的实物（测试计数/diff/截图）
4. 证据落盘前**脱敏**（key/token 打码，`git grep sk-` 零命中）
5. 数据不散落桌面——各角色数据进各自报告处/数据区
6. 编译+测试不过**不许报 hash**
7. **进度以 `工单库.md` + `工单表.xlsx` 为准**——每个角色更新自己负责的工单列进度（如程序员完成→填「✅完成」，验收员验收→填「✅验收通过」），不另起炉灶
   - **程序员完成工单后必须立即登记上表**（交付报告落盘的同时）：程序员列填 `✅<代号> 完成`，备注列填 `分支名 + hash + 交付报告文件名`（例：`feat/upg19 07c2f967（报告 DELIVERY_UPG19_2026-08-16.md）`）——报 hash 与登记上表同步完成，缺一不可
8. **合 main 前必须全量绿 + 真机验收通过**（真机未过不可合；编译/测试 FAILED 时必须停，不得合——即使疑似文件锁也要先查真红）
9. **工作顺序（多 agent 协作防撞，2026-08-16 定）**：
   - 工单流转顺序：设计师出单 → 程序员施工（登记上表）→ 验收员验收（代码层+真机层）→ 审验员审验（AI查证据链）→ 设计师合 main
   - **合 main 单点**：同一时间只有一个 agent 执行合 main（rebase/ff-only 都是它做）；其他 agent 撞到先 git 实证谁先完成 → 已完成方跳过、后到者确认不重复
   - **合 main 顺序**：真机验收通过优先 → 同批按「基础先合」（无依赖先合）→ 文档类可先 → 真机受限项设计师核实后定
   - **并发防锁**：不同工单可并行施工；**同一文件/分支同一时间一个 agent**（Windows 文件锁 + gradle 互锁风险）——多 agent 并发时各用独立 worktree
   - **领单认领登记（2026-08-17 定，防占用歧义）**：领单**开工前必先登记**——工单表该行备注追加 `认领: <agent> worktree=<主仓库名>-<工单号> branch=<feat/x> @时间`；worktree 命名强绑定工单号（`<主仓库名>-<工单号>`）；分支被占用 = 该单已被认领 → 直接改领其他单（不冲突不等待）；撞单走 git 实证先完成者胜。认领规范细则见 `设计师\` 目录对应文档
   - **工单表写入纪律（2026-08-31 定 · 三连撞车验证[UPG-54 教训 + UPG-56/57 行丢失 + UPG-60 行回退]）**：多 agent 并发下 `工单表.xlsx` 是最高危共享文件——**写入五步铁律，违反任何一步=登记无效**：
     ① **写前重新读最新文件**（禁复用先前解压/读取的副本——并行 agent 随时可能已改表）
     ② **写前备份**到 `_备份归档\工单表_backup_<动作>_<日期>.xlsx`
     ③ **行定位用工单号内容匹配**，禁行号硬编码（并行插入会使行号漂移）
     ④ **新增行写前必须扩展 `!ref`**（xlsx 库不自动扩展，越界写入静默截断丢行）
     ⑤ **写后全量读回对账**：总行数 + 本单目标行 + 全部既有行抽查（邻行未动/关键列在场/无乱码控制字符）；发现他人行丢失或回退 → **立即按最后备份无损恢复该行 + 显式声明**（不整体覆盖他人更新）
   - 同类事故历史：UPG-54 覆盖事故（08-28）、UPG-53 行 42 emoji 截断、UPG-56/57 丢失+60 回退（08-31）——**凡 xlsx 写入，本条铁律自动适用**
10. **挂账登记与转工单（2026-08-17 定 · 改版：独立挂账登记表 + 处理中心）**：**任何角色**工作中被动发现缺陷/挂账 → **`处理中心\挂账登记表.md` 登记**「⏳挂账待审」（挂账号 `挂账-<描述>`，现象→证据→建议，**不备份不碰主表**）→ **设计师验证**（查代码/证据/复现）→ 通过标「✅已落实」**转工单**（写 `工单表.xlsx`，此时才备份一次）进派单队列；疑义打回补证/销项。⚠️ 不主动收集挂账（真机补验类走工单库「真机补验挂账」区）。规则详见 `处理中心\挂账登记与转工单规则.md`；建议/汇报/问题也统一投 `处理中心\`（2026-08-17 启用）
11. **待合 main 前置校验（2026-08-16 定）**：合main列标「待合」**必须**验收员列 = ✅已真机 或 —无需；真机受限/挂账项标「⏳待核实」，走**设计师核实**（L3 变异亲杀等实物证据补足后转待合），**不混入待合批**。出待合清单前逐行核对验收员列（防「受限还待合」）。**能力护栏衔接（红线 24）**：共享面变更单另须过能力护栏——NONE 禁合、PARTIAL 需设计裁决，未过护栏不进待合批
12. **派单必含（2026-08-17 定 · 每次派工单）**：派单文本交接段**必须包含**——① 完成后**登记两个表**（`工单表.xlsx`：程序员列 ✅完成 + 备注分支/hash/报告名；`工单库.md`：状态快照同步，先表后库）② **交付报告/汇报时说明已登记入表**（明确写「已登记两个表」）③ 交付报告落点（`程序员\交付报告\`）
13. **主文件夹不乱建登记表（2026-08-17 定）**：工单流转中心**根目录**只放核心流转文件（README / `工单表.xlsx` / `工单库.md` / `处理中心\`）；各角色的登记表/临时表**不堆主文件夹**，放各自报告处/处理中心目录，保持根目录清爽便于统筹；确需主文件夹新增登记表 → 交设计师评估后放；临时登记数据用既有表（工单表登记行 / 挂账登记表加行）
14. **目录整洁纪律（2026-08-17 定）**：新增文件先归入对应分类子目录（方案→`设计师\方案设计\`、立项输入→`立项输入\`、派单→`派单\`、建议/汇报/问题→处理中心对应区）；**移动/删除文件必须同步更新所有引用路径**（grep 检查断链）；不留下同名冲突（文件 vs 目录）或空目录；各角色主动维护自己的目录整洁，设计师每周检查一次断链/冗余，不靠用户发现问题
   - **归档边界（SYS-01 §五 收敛点②）**：`_备份归档\` = **只存数据备份**（`工单表_backup_*.xlsx` / `挂账登记表_backup_*.md`）；`归档\` = **只存已成稿文档留档**（历史方案/旧版设计/送审件等只读档案）。二者职责互斥、不混放；`处理中心\归档\` = 已处理完的建议/汇报/挂账区（仅含 `建议_已评审\` / `汇报_已确认\`），与根级 `归档\` 不同，勿混淆。
   - **证据归属唯一化（SYS-01 §五 收敛点③）**：同一工单证据只存在于"产出该证据的角色"证据目录（验收员=`证据数据\`、程序员=`*-evidence\`、审验员=`证据数据\`、设计师=`设计师\检查证据\`）；其他角色只允许**引用路径**，不得**复制副本**（防多份不一致，UPG-01 批3-3 教训）。`设计师\检查证据\` 为设计侧证据/视觉素材落点，只放工单证据目录与视觉素材，不散放顶图。
15. **合批前核实真机证据真实性（2026-08-17 倒查补强 + 防设计师 AI 幻觉）**：设计师合 main 前，验收结论不能只信工单表 ✅——必须核实真机证据真实性（截图/journal 可见「目标达成」，非口头计划/机制触发）；对真机端到端未验/受限/挂账项，不得仅凭 ✅ 标记合入，先登记补验挂账或标记待补验；验收员标 ✅ 时须附可查证实物（核对截图内容逻辑，非仅文件名/OCR 首行）。**抽查防幻觉**：设计师每合前抽关键单（端到端/后端/安全），打开证据核对「用户视角最终结果」；禁止只信✅/只看文件名/机制触发=达成/拿不相关证据/代码+JVM当真机✅/「应该没问题」想当然——写不出可查证依据就不标可合，标待核实（落地细则：`设计师\README.md` §六 合 main 抽查标准）
16. **全角色问题/发现进处理中心（2026-08-18 定）**：**任何角色**（审验员/验收员/程序员/设计师/灵感库）被动发现的问题、缺陷、挂账、疑点，**必须登记到 `处理中心`**——挂账/缺陷 → `处理中心\挂账登记表.md`（⏳待审）；阻塞/疑问/审验证据链问题 → `处理中心\问题区\问题区.md`；建议 → `建议区`；汇报 → `汇报区` → 设计师集中处理（验证/解决/升级/打回/转工单）。**禁止只留存在本地或口头，不登记即不闭环**。审验员审验证据链工具：`审验员\审验.py` + `审验员\工单证据链映射.md`
17. **所有工单必须经审验（2026-08-18 定）**：**每个工单（工具）都要过审验员证据链审验**——审验员用 `审验.py` 逐一核验证据链（journal 工具调用链 + 关键截图含时间戳 + 命令/产物输出，可见「目标达成」）；未审验的工单**不视为可信**、不得标「✅验收通过」/不得合 main；审验通过标 ✅，证据链断裂/缺证据/疑似造假 → 打回补证或降级。工具：`审验员\审验.py`（全量审验）+ `审验员\工单证据链映射.md`
18. **演示数据必须还原（2026-08-26 定 · UPG-08 打回 P2-2 补强）**：交付/验收演示产生的任何临时数据（演示工单状态、假阻塞、假账目等）**必须在报完成前还原**，并用真实数据重新同步覆盖生产态；交付报告须声明「演示数据已还原且生产态已复核」。验收员发现演示残留 → 直接记 P2 缺陷打回，不算「已还原」口头声明。
19. **开工前先 fetch + 看表（2026-08-28 定 · 程序员不知道 UPG-16/W-07 已合 缺口补强）**：任何角色开工前**先 `git fetch origin` + 查工单库/工单表本单及相关单状态**——进度以表为唯一事实源（规则 7 的执行面）：已合 main 的单基于最新 main 重开分支，不在过期 worktree 上续作；交付/验收报告中的队列描述以写报告时表为准，引用前必须复核。设计师合 main 后在工单表备注写清「已合 main @hash，worktree 可收」。
