MOV 发给 LLM 的工具 schema **不直接来自各工具文件**，而是在 `MainActivity.kt` 重新组装：

- **消费点**：`rebuildAgentTools()`（现 `:6153-6175`）description 取值链 = `sceneToolDescriptions[name] ?: providerToolMeta[name]?.first ?: "MOV 工具: $name"`——**v2.3 复核：M3 已建 providerToolMeta 通道（`:241-243`，device/obsidian 20 工具真描述+schema 已上面），「模板串覆盖」从全量退化为兜底回落**；builtin/browser 两族既有真元数据仍未接入此链。
- 参数 schema 取值链 = `toolParamSchemas[name] ?: providerToolMeta[name]?.second ?: 空 properties`（`:6171-6174`）；静态表 71 条（`:244` 起），`paramSchema()` 把字段描述填成参数名本身。
- 宿主工具面：147 处 `mcpHandlers[...]` 字面注册 + 动态 7 + browser 族（见唯一基线表）。

**MCP 面**：对外 MCP 同样模板串（宿主循环 `:3281-3290`、外部/挂载 `"外部 MCP 工具: $name"` `:3311`/`:4505`）；且宿主注册**不传 inputSchema**（`ToolSpec` 默认空 `McpServer.kt:29`）——MCP 面比 AI 面更瞎；`McpServer.registerMovQueryTools()`（`:234`）从未被调用（死代码，已挂账）。

**市场**：包级 desc 存在且契约截断 ≤20 字（`McpMarket.kt:90,481`）；工具级详情描述缺位——**且现存无任何工具级描述 UI 展示面**（市场详情只渲染工具名 chip，`market-web/data.js:63-68`）。

**结论**：「AI 引导层看不到工具用途与参数含义」属实——**约 123 个在面工具 AI 面仍是模板串，约 51 个连参数 schema 都空**——但修复靶点是 `rebuildAgentTools` 取值链收口 + 元数据来源统一（ToolDefinition），不是给个别文件补描述；M3 的 providerToolMeta 通道证明该通路形态可行，批 1 做的是收敛与推广而非新建。

## 二、目标

每个可调用工具登记三件套，且 **AI 面/MCP 面投影必须消费登记层**：

1. **description**：中文真描述（干什么/适合场景/限制），上限 60 字
2. **inputSchema**：完整参数声明，每字段中文 description（**≤15 字/字段**，语义查源码核实，禁止编造）；**真无参工具空 properties 是正确形态**（不算缺登记）
3. **output 声明**：返回结构说明（**必须点名顶层返回键**）；**存在错误码才附错误码语义**（无错误码工具不得编造）

## 四、验收标准（L1/L2/L3，v2.2 批级棘轮）

**批级棘轮**（v2.3 修时序硬伤：三件套全绿按族下放，批 1 只做接线断言）：
- **批 1**：**接线断言**——取值链接通后，已登记工具（scene 2 + provider 20 + 新接入 builtin 5 + browser 14 = **41**）description ≠ 模板串 + 回落清单输出存在 + 冲突检测首用例（builtin 4 条）过；**三件套全绿不在批 1 断言内**——批 1 开工先实测 provider 20/scene 2 的字段级 schema 与 output 现状，缺口列清单**归批 3 首批清偿**（v2.2 把批 2 交付物写进批 1 断言，自相矛盾，v2.3 修正）；其余未登记工具不纳入断言作用域；
- **批 2**：browser 14 三件套全绿（字段级描述 + output 顶层键断言）；
- **批 3**：按子单逐族收口（含批 1 移交的 provider/scene 缺口清单），每族交付即并入全绿作用域；**最终态**：在面**有参**工具 100% 字段级 schema + 三件套齐（真无参除外）**− 有界「待核实」清单**；

- **计数断言不变量化（v2.3）**：防倒退断言写**不变量**（「不存在已注册、非 uiOnly、且无登记[无 ToolDefinition 条目且无静态表补丁]的在面工具」），不写绝对数——批 3 周期内正当新增工具不打红；绝对数（§一基线表）只在收口批核对；**每个子单派发时重跑 §一 grep 基线**（规则 21 已立此纪律）；

## 五、Token 影响 / KV Cache 影响（AGENTS.md 硬规则 1 申报，v2.2 重报）

- **Token 影响（推导式，实测为准）**：三件套全量后每轮增量 ≈ 每工具（描述 ≤60 字 + 字段说明 ≤15 字×均 3-5 参 + output ≤30 字）≈ 120-165 字 ≈ 360-500B；× 约 145 在面工具 ≈ **52-72KB/轮（约 18k-26k token，中文 0.67 token/字口径）**——v2 旧估算（8~12KB）在自家字数上限下不成立，作废。**缓解**：描述/字段字数上限 + 呈现模式过滤控制在面工具数；**若实测增量超预算阈值，需用户拍板**（全量描述 vs 按常用集/呈现模式裁剪在面工具）。
- **拍板数据备采（v2.3，不新打点）**：「常用集」需要调用频次——journal 已有完整 tool_call 事件链，**批 2 交付时附「近 N 天 journal 工具调用频次聚合 Top 榜」**（一次性统计脚本即可，脚本落 tools/ 随单入库），拍板不靠拍脑袋；该榜同时是批 3 子单排序轴的输入。
- **精度稀释预警（v2.3）**：描述变准 × 工具场变挤（145+）可能反而稀释 AI 选择精度——L3 验收重点观察「更准的描述是否换来更准的选参」，若负相关即触发常用集裁剪拍板，不等 Token 超阈值。
- **KV Cache 影响**：描述在会话开始装配注入、会话中不变 → 请求前缀字节稳定。现状 `rebuildAgentTools` 在 install/uninstall/呈现模式切换时会话中途重建（既有变动点，不在本单范围）；描述变长后每次作废代价同步放大——本单**不得新增**中途变动点。
- 交付前自跑 `node scripts/check-token-effect.mjs`，报告以实测数字为准（估算仅量级参考）。
