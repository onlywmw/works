## 〇、溯源摘要（三条基线修正 + 两个设计决策）

**① 批 3 范围基线勘误：116 → 118**（主方案 v2.3 §一「已登记 22」含 scene 2，但 scene 是**动态注册**、不在 `mcpHandlers` 字面注册 147 内）：

**② 宿主工具 description 无登记位（批 3 核心设计缺口）**：
- `projectToolMeta` 取值链（`MainActivity.kt:81-92`）：`desc = registry[name]?.description ?: "MOV 工具: $name"`——**宿主工具不在 registry（toolRegistry 只聚四族：builtin5+scene2+provider20+browser14），description 全部回落模板串**

- **结论**：批 3 必须为 118 宿主工具新建 description 登记位——设计为 `hostToolMeta` 第五族并入登记投影（见 §1.2）

**③ output 声明无 AI 面消费通道**：
- `rebuildAgentTools`（`:6283-6310`）装配 `ToolSchema(name, description, parameters)`——**无 output 字段**，output 不进 AI 面 prompt
- output 现状：browser 14 已登记（`BrowserMcpTools.ToolMeta.output`，批 2）；provider 20 + scene 2 **output 22/22 全缺**（批 1 报告 §一）
- **结论**：output = 登记完整性（L1 断言 + 未来展示/精度面），**当前不进 prompt** → 主方案 §五 Token 账需下修（见 §四）

**设计决策**：
- **D1（批 3）**：新建 `hostToolMeta`（name → desc+params+output 三元组静态登记表），作为 `buildToolRegistry` 第五族并入登记投影——形态与 provider 20 完全同构，零改 `projectToolMeta` 契约

### 1.2 宿主登记位设计（D1：hostToolMeta 第五族）

    //   "保存一条记忆到长期库（供后续 load/search 检索）。",
    //   paramSchemaDesc(listOf(Triple("content","string","记忆正文"),

- **并行窗口（v1.1）**：四子单各碰各的 `meta/HostToolMetaB*.kt`；MainActivity 聚合改动点在 B3-1（首次并入）+ B3-4（收口并入）各一次——标注编辑窗口，遵守规则 9

### 1.4 施工口径（延续 v2.3 §三 + 批级棘轮）

1. **三件套逐工具登记**：description（≤60 字，功能>限制>场景，**近邻工具须写差异点**「何时用我、何时用隔壁」）+ inputSchema（`paramSchemaDesc` 字段级真描述 ≤15 字/字段，语义查 handler 实现，写「来自 xxx.kt:行」）+ output（**点名顶层返回键**；有错误码才附语义，无则不编造）

3. **output 试点先行（v1.1，评审 P2-3 用户拍板）**：B3-1 首批 = output **22 清偿**（provider 20 + scene 2，批 1 欠账）+ 本子单 hostToolMeta output 试点。output 当前无 AI/UI 消费端（唯一现实消费 = L1 断言），**全量与否待 B3-1 验收看 L1 断言实际价值再定**——不预设全量 140 的纯预期投资（清偿形态 = Provider `PARAM_DEFS` 增 output 顶层键声明，或迁 hostToolMeta 时补）

5. **静态表日落（收口后）**：`toolParamSchemas` 唯一消费 = `projectToolMeta` patches（`:3680/:6295`）+ `fallbackTools`（`:6305`）——宿主全进 hostToolMeta 后 patches 零命中 → **清空为 `emptyMap()`（或显式例外清单逐条注释理由）**，日落验收入批 4（见 §2.5）

### 1.6 工具运行环境分类规范 v1（为 PC 连接留位）

> 背景：批 3 的 118 个宿主工具经逐项实现核对（§手机契合度审计），**全部是设备本机能力，无一 PC-only**。为将来「连接 PC」不混乱，本单起统一打「运行环境标签」。
> **落点约束**：不进 hostToolMeta 结构（Triple 不动，投影契约零变化）、不进 description 文本（不污染 AI 面）、代码侧不落盘（禁落盘红线）——只作**分类清单**，随派单文本附录产出。

**三维度分类**（不新增平行投影，只是分类视图）：

| 维度 | 取值 | 含义 | 判定示例 |
|---|---|---|---|
| 域名族 | 复用既有前缀 | 命名空间即族，不重造 | `device.*`/`memory.*`/`vault.*`…（见 §1.3 聚类） |
| **env**（运行环境） | `mobile` / `any` / `pc` | 能力本身所属宿主 | 见下 |
| **cond**（设备条件） | `none` / `hardware` / `vendor` / `disabled` | 真机条件依赖（仅 `mobile` 标注，`any` 恒 `none`） | 见下 |

**env 判定规则**：
- `mobile`：能力绑定手机硬件/手机本地存储/手机应用生态（如 torch、device.*、memory.*、vault.*、biz.*、shell.exec、note.create、spill.*）——**118 中绝大多数**
- `any`：纯计算/纯网络、能力不绑定设备**且实现不绑 Android 特有 API**（如 http.get/post/download、error.classify 纯逻辑）——将来 PC 端天然可用。**注（v1.1，评审 P3-7）**：image.ocr（ML Kit 端侧）/text2image（Android Bitmap/Canvas）/md.render/renderFile（Android 渲染）**实现绑 Android API → 归 `mobile`**，不属 `any`
- `pc`：**预留**——PC 连接单立项时新增，不与现有 118 冲突

**cond 判定规则**：
- `hardware`：需真机硬件 → 模拟器验收跳过、挂账「真机补验」区（**118 内 = torch.*/vibrate/bluetooth.status**；sensor.list/camera.*/qr.scan/screen.capture/calendar.* 属 provider 族、已在批 1 登记，**不在批 3 范围**——派单附录不得照抄示例）
- `vendor`：厂商绑定（xiaomi.assist 仅小米）
- `disabled`：已硬禁用（xiaomi.assist handler 级拒绝，登记名即可不写真描述）
- 引擎动态依赖（tts.speak 视 TTS 引擎可用性）：不写死标签，归 `unavailableTools` 运行时剔除，元数据登记名（tts.speak 不在 118，仅作判定示例）

**118 分类清单落点**：随每个子单派单文本附录产出（B3-1~B3-4 各附本子单工具的 `env/cond` 表，施工当天重跑 §一 grep 基线为准）。

**PC 连接时的扩展方式**：新 PC 工具 → `env=pc`（或 `any`），按同表追加；现有 118 标签不动。若 PC 接入要求「AI 面按环境过滤工具」（手机侧不显示 pc-only），届时单独立项评审——本 v1 不预先进登记层（不为假设的未来设计）。

### 2.2 外部发现补传元数据（McpExtDiscovery）

- **Result 扩元数据**：`Result` 增加 `meta: Map<String, Pair<String, Map<String, Any?>>>`（name → (description, inputSchema)），`discover()` 在遍历 `t` 时提取 `t["description"]`、`t["inputSchema"]`（`as? String`/`as? Map` 容错，缺省回落）
- **结构校验（v1.1，评审 P3-4）**：外部 inputSchema 过结构校验（`type==object` 且 `properties` 为 map；非法/超限 → 回落登记层/模板串），**不原样透传进 AI 面**——防非法外部 schema 污染工具面
- **挂载侧**：外部发现挂载（:3705-3712）改用与 mountExtTools 相同的三态回落投影（见 §2.3），输入 = `ext.meta`
- `McpExtDiscovery` 方法签名可加默认参（`discover(..., includeMeta: Boolean = true)`），不破坏现有调用

### 2.3 热挂载面清偿（mountExtTools 三态回落）

```kotlin
// v1.1（评审 P2-1）：projectToolMeta 内部自带回落（registry?.description ?: "MOV 工具: $name"），
// 原示意里的第二个 ?: 是死分支；且「MOV 工具:」与「外部 MCP 工具:」两套模板串语义分叉。
// 改 nullable 严格版：projectToolMetaOrNull 仅当登记层/补丁真命中才非空 → 三态语义才成立。
private fun projectToolMetaOrNull(
    name: String, registry: ToolSchemaLike, patches: Map<String, Map<String, Any?>>,
): Pair<String, Map<String, Any?>>?   // 未登记 = null（不落内部回落串）

// mountExtTools 升级：加 meta 参数，desc/schema 三态回落
private fun mountExtTools(
    handlers: Map<String, (Map<String, Any?>) -> Any?>,
    meta: Map<String, Pair<String, Map<String, Any?>>> = emptyMap(),  // 外部自带元数据
) {
    mcpHandlers.putAll(handlers)
    for ((name, handler) in handlers) {
        val projected = projectToolMetaOrNull(name, toolRegistry, toolParamSchemas) // 真命中才非空
        val (extDesc, extSchema) = meta[name] ?: projected
            ?: ("外部 MCP 工具: $name" to mapOf("type" to "object", "properties" to mapOf<String, Any?>()))
        mcpServer?.addTool(ToolSpec(name, extDesc, extSchema, handler))
    }
    rebuildAgentTools()
}
```

- **三态优先级（v1.1 定稿）**：外部自带元数据（tools/list 真描述）→ 登记层**真命中**（`projectToolMetaOrNull` 非空，不落内部回落串）→ 外部模板串「外部 MCP 工具:」——**外部未命中回落外部模板串、宿主未命中回落「MOV 工具:」，两套回落语义分家不混**
- **宿主面不变**：`rebuildAgentTools`（宿主 118）仍走非严格 `projectToolMeta`（内部回落「MOV 工具:」），挂载侧与投影内部各归其位（评审 P2-1 挂载点写清）
- **browser 热挂载顺带利好**：browser 14 已在 toolRegistry（键 `mcp__browser__*`），mountExtTools 改投影后自动吃上登记层真描述（当前是模板串）
- 调用点同步：`:2452/:2469`（market install/enable，meta 空走投影）、`:6270`（browser proxy，meta 空走投影命中登记层）

## 四、Token 影响 / KV Cache（AGENTS.md 硬规则 1，v2.3 账目下修）

- **修正**：output 不进 AI 面 prompt（溯源实测 `ToolSchema` 无 output 字段）→ v2.3 §五「output ≤30 字/工具」从 prompt 增量中剔除
- **AI 面增量（三口径，v1.1 评审 P2-2 重算；推导式、实测校准为准）**：
  - **字口径**：desc ~50 字/工具（≤60 上限，非全部顶格）+ 字段级中文描述 ~90 字/工具（均 6 字段 × ≤15 字）≈ 140 字/工具 → 118 × 140 ≈ **16.5K 字/轮**
  - **token 口径**：中文 0.67 token/字 → 描述 118×50×0.67≈**3.9K** + schema 中文 118×90×0.67≈**7.1K** + schema 结构 token（键名/类型/引号，纯英文，均 6 字段 ≈40 token/字段）≈**4.7K** → 合计 ≈ **15.7K token/轮**（原 v1 的 5.5K 是算术错误，已废）
  - **字节口径**：中文 UTF-8 ≈3B/字 → 16.5K 字 ≈ 50KB；加英文结构 → **≈60-70KB/轮（UTF-8 全量）**——与 v2.3 全量账（52-72KB/轮，含 output+145）同量级但**口径更实**；KV cache 命中时按「前缀恒定 + 增量」口径（第 2 轮起增量极小）
- **实测校准点（v1.1 新增）**：B3-1 收口即跑 `node scripts/check-token-effect.mjs` + `tools/journal_freq_top.mjs` Top 榜，实测「工具数 × 均值」校准总账；若实测显著超推导 → 触发常用集裁剪拍板（评审 P2-2 提示「JSON schema 结构 token 可能显著高于推导」——已计入上表，仍以实测为准）
- **缓解**：描述/字段字数上限 + 呈现模式过滤控制在面工具数；若实测超预算阈值 → 用户拍板（全量 vs 按常用集裁剪）
- **精度稀释预警**：描述变准 × 工具场挤（145+）可能负相关——L3 重点观察「更准描述是否换来更准选参」，负相关即触发常用集裁剪拍板
- **KV Cache**：批 3/批 4 均不得新增 tools 字段会话中途变动点（红线 5）；mountExtTools 每次热挂载会 rebuild（既有变动点，不在本单扩大）
