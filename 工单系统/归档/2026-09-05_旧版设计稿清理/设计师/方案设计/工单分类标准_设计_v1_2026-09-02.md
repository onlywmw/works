# 工单分类标准 v1（送大神评审 · 2026-09-02）

**状态**：📤 送审（待大神评审）
**评审对象**：工单系统——工单如何分类（主分类 + 标签）
**目的**：让「某类工作：谁做过 / 做过什么 / 在哪」可检索、可盘点、可统计

---

## 一、背景与现状（为什么要分类）

工单系统目前只有三维：

| 维度 | 现状 | 问题 |
|---|---|---|
| **优先级** | P0（阻塞主线/安全红线）～ P3（优化细节） | 只回答「多急」，不回答「是什么」 |
| **线** | A（设计师）/ B（验收）/ C（程序员） | 只回答「谁在动」，不回答「干什么」 |
| **状态** | 排队/已派/施工/终态/回炉 | 只回答「到哪了」，不回答「哪类」 |

**没有「这个单是关于什么的」这一维度**——现状：

- 想盘点「全部安全类工单」→ 只能人肉从 58 卡标题里扫
- 想看「第三方工具集成了几个、分别怎么迁的」→ 无从查起
- 新单入库时「分类靠手感」——同类工作分类不一致（比如 Obsidian 曾 P0、12306 曾 P0，实际都不是主线阻塞）

**目标**：每张卡有 **1 个主分类 + 0~N 个标签**，一列可筛、一眼可辨。

---

## 二、分类维度

### 2.1 主分类（8 类 · 按「工作性质」定）

| # | 分类 | 定义 | 判定一句话 | 举例 |
|---|---|---|---|---|
| M1 | **安全 / 合规** | 权限/审批/隐私/审计/红线——不做会出事的 | 「这条有红线吗？」 | 审批白名单、隐私政策弹窗、脱敏 |
| M2 | **体系 / 治理** | 改造自己的工具/流程本身 | 「这是在改工单系统/契约/流程吗？」 | 工单系统自改、契约体系、改造计划 |
| M3 | **平台 / 基建** | App 框架/构建/CI/部署/保活——无业务形态 | 「不弄它 App 能正常活着吗？」 | 构建链、Termux 保活、双体架构 |
| M4 | **工具 / MCP 集成** | 接「外部能力」入 MOV——第三方工具库/API/协议 | 「是在接别人的能力吗？」 | Obsidian 工具包、12306、浏览器 WebMCP |
| M5 | **商业 / 账号** | 钱/人/账号/模板/合规经营面 | 「跟钱/人/账号有关吗？」 | 注册登录、支付、账号体系、模板 |
| M6 | **记忆 / 知识** | AI 怎么记住/学到——Memory OS/记忆页/教训/蒸馏 | 「在让 AI 变聪明一点吗？」 | 记忆体系回补、教训蒸馏、Memory API |
| M7 | **资产 / 数据** | 我的资产/密码/文件/数据模型/迁移 | 「在管用户的资产/数据吗？」 | 资产管理注册、vault→credential 迁移 |
| M8 | **UI / 交互** | 外观/组件/页面/手感 | 「用户能看见/摸到的那层？」 | 外观组件级显示、卡片、气泡分流 |

> 兜底规则：以上都不沾 → 落 M8（UI/交互）？**不**——都不沾说明类别需要调整，**登记「待定分类」人工裁决**（防兜底掩盖分类缺失）。

### 2.2 标签（0~N 个 · 任意组合 · 不设上限）

| 标签族 | 值 | 说明 |
|---|---|---|
| **动作** | 新增 / 修复 / 重构 / 迁移 / 合规整改 / 收尾 | 这次改动的性质 |
| **对象** | app / web / 文档 / 脚本 / 契约 / 部署 | 改到什么层 |
| **触发** | 用户报障 / 主动改造 / 评审要求 / 合规要求 / 验收打回 | 谁发起的 |
| **性质** | 安全 / 性能 / 体验 / 兼容 / 回归 / 治理 | 侧重（与主分类无关的横切面） |

## 三、分类规则（判定顺序 → 落类）

**主分类只取 1 个**——按「上游性」顺序走判定树，**第一个命中即落类**（不叠加）：

```
1. 安全/合规      → 有红线/权限/隐私/审计
2. 体系/治理      → 在改工具/流程本身
3. 商业/账号      → 钱/人/账号/模板
4. 记忆/知识      → AI 记忆/学习/教训
5. 资产/数据      → 用户资产/数据/迁移
6. 平台/基建      → 框架/构建/部署（无业务形态）
7. 工具/MCP 集成  → 接外部能力
8. UI/交互        → 以上都不沾且确系用户可见面
9. 待定分类       → 都不沾（人工裁决，不许默认为 UI）
```

- **判定理由**：安全/合规优先（红线优先于一切）；体系/治理优先（改工具的工具先归位）；**动作/对象信息丢给标签**（主分类保持单一）
- **一个单多类怎么办**？如「12306 工具集成 + 合规整改」→ 主分类=工具/MCP 集成（第 7 位命中），标签=`合规整改/修复`——主分类管「是什么」，标签管「带什么属性」
- **历史卡回填**：58 张卡按标准回填（主分类+标签），一次性做（回填后看板可分类筛选）

---

## 四、落位（怎么进系统）

| 位置 | 改动 |
|---|---|
| 工单表 | 新增「分类」列（主分类单值）+「标签」列（逗号分隔） |
| 工单库卡 | 状态区加 `分类：M4 工具/MCP 集成`；标签 `动作=迁移/对象=app` |
| 看板 | 主表加分类筛选下拉；摘要卡可按分类统计 |
| 派单/交付 | 派单文本必写分类；交付报告带分类（防新增单漏填） |

## 五、评审点（请大神重点看）

1. **8 类粒度**——够不够？还是多了？合并/拆分建议？
2. **判定顺序**——安全→体系→商业→记忆→资产→基建→工具→UI，上游性排序合理吗？
3. **标签族**——动作/对象/触发/性质四族够吗？缺什么（如「用户可感知」）？
4. **单主分类 + 多标签**——是否该允许双主分类（如「安全+商业」复合单）？还是保持单值（复合丢给标签）？
5. **历史回填**——58 卡一次性回填的成本/风险；还是新单起分类、老卡抽查回填？
6. **归错怎么办**——谁仲裁（设计师总归口？）；重分类是否需要进卡状态区登记（防无痕改动）？
