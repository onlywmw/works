## 一、最终要达成什么效果（产品 + 工程双视角）

### 产品终态（这个 App 要成为什么）

MOV = **AI Native 办事终端**：用户说/打一句话 → AI 理解并动手办事（工具/MCP 能力，安全审批兜底）→ 结果以卡片浮现于桌面底座 → 能力可从市场装卸。两种模式（经典=全功能主页 / 极简=空画布+输入按钮）共享同一能力面，**能力零阉割**。

产品面已就绪的体系（2026-09-02/03 两天收口）：审批体系（判定单源+FIFO 队列+悬浮卡+预审单）、执行引擎（能力级 S1-S4）、模式收敛（经典/极简+推理档位绑定）、呈现交互体系 v1.1（大神评审吸收版，待阶段 2 引擎化）。

### 工程终态（代码要成为什么样）

```
MainActivity.kt = 薄装配壳（生命周期 + 各模块装配点，目标 < 800 行）
   ├── tools/ToolsRegistry.kt        工具注册面（185 个 handler 的家）
   ├── approval/                     审批面（已拆 ✅ UPG-79）
   ├── market/MarketFeature.kt       市场面（启停/总览/安装）
   ├── pages/PagesBridge 装配         页面桥面
   ├── ui/chips/ + ui/capsule/       chips 气泡 + 主页胶囊
   ├── ui/markdown/                  Markwon 原生视图构建
   ├── agent/AgentFeature.kt         AgentLoop/runChat 装配
   └── boot/BootSequence.kt          启动序列
```

- **加功能=加模块，不是改巨文件**；bug 隔离在面内；多工单并行不再撞 MainActivity；
- **验收一眼看穿**：每个面的改动只落在自己的模块文件里（diff 面=责任面）；
- 与呈现引擎（UPG-89）衔接：拆出的 UI 模块=引擎的宿主挂点（先拆后引擎化）。

## 二、前因后果（怎么变成这样的）

1. MOV 是两周内 70+ 工单高速演进出来的（审批/市场/记忆/模式/极简…），每个工单都在 MainActivity.kt 里加面——**功能正确性高，体系性为零**（审批体系总纲原话）。
2. 实测现状（main@fea2fae）：**MainActivity.kt = 7666 行，185 个 mcpHandlers 注册点**，里面住着：工具注册、chips 气泡（:945）、主页胶囊（:1352）、模型管理（:2352）、Memory OS（:2671）、页面桥（:2906）、对话模式（:4352）、预审单编排（:5317）、Markwon 视图构建（:6839-7028）、市场总览（:7266）、启动序列。
3. 代价实证（这两天真实发生）：每张工单红线第一条都是「MainActivity 纯 CRLF 别撞」；UPG-76/79/84 连续同文件撞车排队；审批呈现层散装导致「静态全对、运行时黑洞」（真机 P0）。
4. 已验证的拆分先例：UPG-79 把审批 UI 拆成 `approval/` 包（ApprovalSurface+ApprovalLogic，零回归）——**模式已跑通：注册器/纯函数搬移 + 唯一写点锚 + 全量契约套件零回归**。
5. 架构图实证（`设计预览\MOV_运行时架构图_2026-09-03.html`）：图上主路径五节点分层清晰，代码里全在一个文件——**「图上分层、代码一锅」就是本计划书要消灭的落差**。

## 三、拆分原则（红线）

1. **纯搬移零逻辑改动**——每批只做「移动+必要接线」（可见性/依赖注入），禁顺手优化；优化另立单。
2. **一批一单**——每批独立工单、独立 STD、独立验收、独立合 main（小 diff 小验收面单点回滚）。
3. **零行为变化锚**：全量 0 失败 + 面专属契约锚（计数/名单/直呼）+ 真机冒烟。
4. **拆分不碰语义**：审批/权限/模式/工具的判定与行为语义一律不动（UPG-68/76/77/79/84 冻结语义全部继承）。
5. **Token/KV 申报**照 AGENTS.md 硬规则 1（预期全程 0/0）。
6. MainActivity 纯 CRLF 保持；新文件行尾约定写入蓝图。

## 四、分批计划（每批一单）

| 批 | 面 | 内容（锚 @fea2fae） | 规模 | 风险 |
|---|---|---|---|---|
| **① 工具注册**（UPG-93 已派） | tools/ | 185 个 mcpHandlers 注册+handler 实现 → `ToolsRegistry.kt`；MainActivity 剩一行装配 | 大（~3500 行搬移） | 中（机械搬移，计数+名单锚锁死） |
| ② 市场 | market/ | 市场启停/总览/安装/本地 tab 投影（:7266 + market.* 注册段）→ `MarketFeature.kt` | 中 | 低（UPG-23/87 已有模块边界） |
| ③ 页面桥 | pages/ | PagesBridge 白名单+页面工具桥（:2906 段）→ 装配模块 | 中 | 低（白名单契约已有测试） |
| ④ UI 件 | ui/chips + ui/capsule | chips 气泡（:945）+ 主页胶囊（:1352）→ 独立模块 | 中 | 中（UI 状态交互） |
| ⑤ Markwon 视图 | ui/markdown/ | buildMathView/buildCodeBlockView/buildTableViews（:6839-7028）→ 渲染构建器模块 | 小 | 低（纯函数构建） |
| ⑥ 启动序列收尾 | boot/ | onCreate 装配顺序审计 + `BootSequence.kt`（模式回落/凭据/预热/桥装配顺序显式化） | 中 | 中高（启动顺序敏感——放最后） |
| ⑦ Agent 装配 | agent/ | runChat/ReactLoopAgent/预审单编排装配（:4352/:5317 段）→ `AgentFeature.kt` | 中 | 中（UPG-76 编排链） |

> 顺序逻辑：先拆**声明式大头**（工具注册，风险最低收益最大）→ 再拆**边界清晰的业务面**（市场/页面桥）→ 再拆 **UI 件** → 最后拆**启动序列**（顺序敏感，放最后等其余面都出去了再理）。

## 五、验收与里程碑

- 里程碑判定：MainActivity.kt 行数逐批下降（每批交付报告报行数）——终态目标 < 800 行；
