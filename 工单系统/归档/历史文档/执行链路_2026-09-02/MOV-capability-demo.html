MOV 能力生态 · 演示

一句话模型：不是"MCP 管理宇宙"，而是 元能力注册（一次实现多次复用）+ bundle 只存编排 + LLM 按需串联 + 护栏扣副作用。

① 本质：外卖 / 闪送 / 快递，是一个引擎、三种壳

外卖
餐饮 · 准时 · 退款 · 保温
闪送 / 跑腿
急件 · 议价 · C2C
快递
批次 · 网点 · 称重
↓ 三个壳，共用同一批 履约元能力（业务壳不注册，元能力才注册）
派单运力地图/路线 签收时效结算/扣款
只要做一次"把物品从 A 送到 B"的引擎，外卖、闪送、快递全是它的壳。 这就是去重来源。

② 注册制：元能力 = id + 契约 + 副作用 + 提供者

元能力 id干什么副作用提供者
fulfill.dispatch派单到最近运力写2
按能力找实现： 自营运力 · 0.8s · 覆盖全市 区域车队 · 0.5s · 仅城东 → 由上层按 SLA/覆盖/价格选，契约相同。 （注册表有真消费者，不是登记表）
fulfill.geo路线 / 实时位置读1
地图基础能力，一次实现，被派单/导航/用户轨迹同时复用。
fulfill.acknowledge签收 / 确认送达写·不可逆2
送达闭环节点：签收后进入结算。护栏要求"确认送达"前给人一次确认。
billing.charge结算 / 扣款花钱1 · 自营
花钱动作 → 永远挂"护栏"，必须过原生审批。商业闭环自营，不外包。
点行看"提供者"；粒度判据：一次实现、多次复用、有清晰副作用契约 —— 够格才进注册表。业务壳（外卖下单流程）不算元能力，不注册。

这一程 = 同一批元能力被 LLM 穿线；实现只有底层一份，付款被护栏拦了一次。若这就是你要的效果 → 方向对。
这次的三条边界（避开旧坑）： ① 注册范围=自己业务域的元能力，不是"全世界的 MCP"； ② 注册表必须有真消费者（按能力找实现/选提供者），否则空转； ③ 粒度=一次实现多次复用 + 副作用契约清晰；业务壳不注册，只组合。 旧"原子/注册中心大 schema/merkle/能力地图"那套重管理，不在本演示内。
