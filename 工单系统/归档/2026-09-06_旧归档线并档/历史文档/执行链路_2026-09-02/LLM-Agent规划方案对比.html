★ deepseek-harness plan-mode 深度解读

先纠偏：plan 不在 Python SDK

入口目录 python/sdk/src/deepseek_harness 是纯 stdio 传输层（JSON-RPC 客户端），grep「plan」零命中，不管规划。真正实现是 TS monorepo 里的 packages/plan/plan-mode（@deepseek-ai/dsh-plan-mode）；Python SDK 只负责：拉起 runtime 子进程 → 发 session/prompt → 收通知直到 idle → 抽最终回答。

① 定位：plan 是「协作状态」，不是执行引擎

plan mode 是 agent 的协作姿态（stance），只做软引导，从不强制。强制是三根独立轴，各自独立 owner、互不读写：沙箱 sandbox（执行范围）、批准策略 approval（权限）、plan mode（只贡献引导文本 + 一个需评审的退出工具）。决策记录明确拒绝把三者捏进同一个「named-mode」抽象。

② 状态存储：log-only 单一事件，靠日志回放推导

唯一持久事实是会话日志里一个事件 plan/mode: {active: boolean}——整值替换、最后一条生效。关键取舍：

  • 没有 live mirror（实时镜像）。恢复 / resume / fork / compaction 全靠 foldPlanMode(events) 回放最后一条；host 重启、别的标签页、冷读都能从日志还原 → 状态与会话日志天然统一，不是边车。
  • 明确拒绝「把 plan 存成文件/目录」：工具参数已记录可评审计划，plan 目录会造成第二个持久家。计划内容工件 = exit_plan_mode 的一段 markdown（须 # 开头命名），无结构化 schema——刻意的克制。

③ 状态机：布尔开关 + pre-step 边界原子刷写

set(agent, active) 返回 committed / queued / cancelled / noop：

  • turn 之间空闲 → 立即 session.append('plan/mode') 提交；
  • turn 开着 → 选择进 pendingIntents，等「下一个被接受的轮内 pre-step」才在边界刷写（挂在 agent/pre-step 钩子上）。
  • 刷写卡在步进边界：新请求组装前应用，同一步骤的重试复用冻结的组装；append 失败则选择留在 pending 可重试，不丢。

核心：状态翻转不靠独立写操作，而是挂在 agent 步进边界上原子提交。

④ 谁触发（3 条通道）

用户命令/plan（进）、/plan [message]（进 + message 成为模型下一条普通用户消息）、/plan off（直接退、不进模型，还能取消尚未刷写的进入）
模型工具exit_plan_mode：plan mode 内展示完整计划，请求人类评审
继承fork 继承已记录状态，新 spawn 从 inactive 开始；无创建期 plan 选项

⑤ 评审闭环：给 LLM 出的 plan 如何被管理

  • 参数 = markdown 计划；执行前校验「正在 plan mode」+「以 # 开头」。
  • 经 ctx.userQuestions.ask() 弹评审：问题 intent:{kind:'plan-review', approve:'Approve'}，detail 携带完整计划 → 有能力的 UI 渲染成「决定卡」而非通用提问。
  • 输出 schema 收窄到 {approved: true}（const）。
  • 只有「Approve 且无自定义文本」放行；拒绝 = 留在 plan mode 并把纠偏反馈回灌给模型继续改；放弃审阅（用户抢话）= 告知模型「停在这等用户消息」。
  • 批准后是 silent pending selection：当前 tool batch 剩余仍带 plan 引导，下一个 request 前移除。
  • presentCall / presentResult 定义 UI 呈现：卡片标题 = 计划第一个 heading，内容 = 原样 markdown。
  • 工具目录常驻注册 exit_plan_mode（非 plan mode 执行才报错）→ 进出 plan mode 不改变工具 schema，保 KV cache 与稳定性。

⑥ 最值得抄的架构决策（与你的理念同源）

  • 不为单一功能建通用抽象：第一版做过通用 ModeConfig.modes 注册表，被砍——产品只有 plan 一个实例，通用机制只是维护负担。「等第二个真实消费者出现，再从两个具体案例抽公共 seam」。
  • plan 引导渲染在系统提示 order 50，inactive 零 token 成本；进出切换会改变 order 50 起的 KV cache 前缀。
  • 已知局限照实写：进程在边界前退出丢一次 pending；评审中插件热重载 → 失败关闭（留 /plan off 手动逃生）；无视引导的模型仍可 mutation → 它是 UX 闸，不是安全闸。

对 MOV「计划审批闸」的借鉴点

可抄清单（对照 deepseek-harness）

  1. 单事实放会话日志：若 MOV 已有 session/event 日志，plan 状态就当一个日志事件类型（log-only、整值替换），别做实时镜像——回放即状态，天然支持恢复 / 续跑 / 会话分叉。
  2. plan 只当 UX 闸，强制另配独立轴：要「计划/审批强制生效」，应独立设 enforcement（沙箱/批准），别硬塞进 plan 状态——否则会像 deepseek 砍掉的第一版一样，把不相干的 owner 拧成一根绳。
  3. 审批走结构化 tool 调用 + intent=plan-review：给 LLM 出的 plan 通过带 intent 的问题通道弹出，UI 据此渲染成「决定卡」而非通用提问；只有明确批准（无自定义文本）才放行，其余把反馈回灌给模型。
  4. 批准动作延到下一步边界：批准不是立刻生效，而是 pending 到下一 request 组装前——保证「带着计划引导跑完本批，下批才脱引导」。
  5. 工具/契约常驻，别随模式启停：plan 工具进出不改变工具 schema，保 KV cache 前缀稳定；状态切换才改 prompt 段。
  6. 别急着做通用 named-mode 注册表：除非 MOV 真出现第二个协作模式，否则先写死 plan，等两个具体案例再抽公共 seam。
核心一句话：deepseek-harness 把「给 LLM 出 plan」管成 = log-only 布尔协作开关（回放即状态）+ 一份必须 # 开头的 markdown 工件 + 一次走 user-questions 的评审 tool 调用——全程数据驱动、无 live mirror、无文件副产物、无通用 mode 注册表。
