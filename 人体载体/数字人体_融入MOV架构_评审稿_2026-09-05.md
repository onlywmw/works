## 〇、一页结论

**方向可行，且 MOV 现有体系为本方向预留了约 70% 的地基**（页面承载通道、能力注册机制、`wardrobe` 衣柜资产类目、商业挂点主体契约、UI 规范条款全部现成）。需要新建的是 **1 个轻量注册表（部位挂点）+ 1 个用户身材参数存储**，无需推倒任何既有架构。主要风险是**合规**（人脸→3D 的开源许可、人脸数据=个人信息）与**资产链路许可**（MakeHuman 输出商用需核），两条均有清晰备胎。

## 一、前因（这件事怎么来的）

1. **起步**：用户想找 GitHub 现成健身 App——「人体构造图，点哪个部位出现相应锻炼内容和方式」。
2. **调研**：GitHub 无「人体图点选」成品；发现两件可组合素材——MuscleMap（人体肌肉图组件，SwiftUI）、free-exercise-db（876 动作库，Unlicense）。已落地中文动作库 86 条：`人体载体/健身动作库_中文100.json`。
3. **愿景升级**：用户明确构想——**数字人体不止健身**：
   - 裸态 = 人体结构体（点部位 → 健身内容/健身房）
   - 穿态 = 衣柜载体（衣服穿在身上，点衣服 → 电商商家）
   - 头发 → 理发店；每个部位 = **商业挂点**
   - 「**数字人体 = MOV 的界面本体**」，与 MOV「线是活的通道/注册能力」哲学同构。
4. **形态拍板**：2D 全身正面 → **直接 3D**（用户 09-05：「2D 体验不好，要么就直接 3D」）。
5. **AI 接入拍板**：用户上传人脸照片 + 身高/体重/腰围/罩杯 → **自动生成与用户等比例的 3D 人体**（像游戏建号捏人，不是调一堆参数）；换衣服点一下就换。
6. **技术栈拍板**：Web（Vue + Three.js）+ 独立 Web 页先行（效果好再嵌 App）。

## 二、想达到的效果（三大诉求）

### 诉求 1「AI 一键生成人体」
- 用户输入：一张人脸照片 + 身高/体重/腰围/罩杯（可更少，缺省用统计估算）
- 产出：与用户相似的 3D 头像 + 等比例身体（可旋转/缩放）
- 体验：像游戏「捏人」——上传完即出模型，微调是滑杆/话术（「微胖」「梨形」）而非参数堆

### 诉求 2「点击部位 → 内容/商业」
- 裸态：点胸/肩/背/腹/臂/腿… → 该部位健身动作（名称/要领/组数，中文）
- 点头发 → 理发店；点衣服 → 电商商家；点胸 → 健身房 —— **部位即入口**

### 诉求 3「点击即换装」
- 衣柜资产穿到人体上（上装/下装/鞋/发型/配饰槽位）
- 换装点击即换，所见即所得；衣服可溯源（品牌/购买/商家）

## 三、技术路线（选型与许可一览）

### 3.1 人脸 → 3D 头（最大合规坑，已全面调研）

| 方案 | 许可 | 结论 |
|---|---|---|
| **DECA** | ❌ 非商业研究专用（LICENSE 原文） | **不可用** |
| **PIFuHD** | ❌ CC BY-NC 4.0 | **不可用** |
| **FLAME 2023 Open** | ✅ **CC-BY-4.0**（可商用，须署名；旧版不行） | **自托管首选** |
| **3DDFA_V2（MIT）+ FLAME 转换** | ✅ 代码可商用 | 工程量大 |
| **Ready Player Me（SaaS）** | ⚠️ 商业条款未全程核实（docs 多次 fetch 失败） | **Demo 首选**，生产前必须核实 |
| **Meshy / Tripo（SaaS）** | 按 ToS（未核）；带 auto-rig | 兜底，人脸相似度不可控 |

**结论**：V1 demo 用 Ready Player Me（快、完整头像+身体+换装）；**生产**力争 FLAME 2023 Open 自托管（合规+可控）；向 MPI 购买商业许可为备胎（`ps-license@tue.mpg.de`）。

### 3.2 身体参数 → 3D
- MakeHuman 宏参数（身高/体重/围度 → 数值向量，社区公式成熟）
- **LLM 只做「体型标签分类」**（微胖/梨形/匀称 → 有限枚举），参数由确定性映射表给出——可审计、无幻觉（这是 MOV「AI 在环」的标准用法，与 Vault/门控哲学一致）
- ⚠️ MakeHuman 软件 AGPL；**输出模型商用许可需官方 FAQ 确认**（正在推进）

### 3.3 渲染/交互
- **Three.js（WebGL2）**（模拟器 WebGPU 不可用；WebView 支持 WebGL；Manifest 已 `hardwareAccelerated=true`）
- 部位拾取：Raycaster 命中面 → 骨骼名（chest/shoulder/upper_arm…）→ 部位注册表映射（自制 1-2 天，无现成库）
- 模型减面 20-40k 三角 + Draco（移动端）

## 五、缺口（需新建，均为轻量扩展）

| 缺口 | 方案 | 规模 |
|---|---|---|
| **身体部位注册表** | `BodyAnchorRegistry`：部位 id（标准解剖 id：chest/shoulder/back/abs/arms/legs…）↔ 动作/商家/能力包 id；复用 AssetRegistry 注册制 | 新小契约，~1 天 |
| **用户身材参数** | 存储位置待定（本机加密 vs 云端账号）——**倾向本机 + 用户显式授权**（InfoVault 白名单现无身材字段，`InfoVault.kt:409-424`；Profile 现仅 phone+tail，`AccountMe.kt:13-21`） | 字段+表 |
| **人脸数据通道** | 人脸=个人信息 → 外发 AI 生成需**显式审批 + 告知**（与「数据不出设备」红线交叉，`InfoVault.kt:8`）；V1 若走 RPM SaaS 需用户主动上传动作 | 审批项 |
| **部位→商家挂点契约** | 轻量 `BodyAnchorRegistry` 绑定 + 市场 registry 可选加部位标签 | 扩展 |

## 七、合规红线（先查后做）

1. ❌ **DECA / PIFuHD 不能碰**（非商用/CC BY-NC）
2. ❌ **FLAME 旧版不能商用**（只 2023 Open，CC-BY-4.0）
3. ⚠️ **RPM 商业条款**——阶段 1 开工前必须核实（免费额度/付费/头像版权/App 内使用）
4. ⚠️ **MakeHuman 输出模型商用**——官方 FAQ 人工确认
5. ⚠️ **人脸数据=个人信息**——隐私政策/用户授权/删除机制（MOV 已有隐私合规体系可挂）
6. ⚠️ 3D 人体数据（身高/围度/体貌）敏感——**不随云端账号**，本机+显式授权（原则与 vault 一致）

## 八、待大神评审的决策点

1. **V1 demo 用 Ready Player Me SaaS 是否 OK**（快 → 但约束：头像风格、商用条款、数据出境）；还是直接上 FLAME 自托管（慢 1-2 周，但全自主）
2. **身体参数落点**：本机加密（InfoVault 扩展）vs 云端账号 profile——合规与体验取舍
3. **部位注册表设计**：标准解剖 id 一套，还是「部位=多域区域」（健身/美发/服装各自区域，用区域注册表统一）——即「一个身体，多套区域语义」怎么建模
4. **makehuman 输出商用确认**（官方 FAQ 原文未抓到）
5. **3D 页在 UI 体系里的身份**：是否作为 UPG-50 组件族新成员（UI-HUMAN-*），还是独立图形页（仅消费 token）——倾向后者（图形画布不是传统组件）
