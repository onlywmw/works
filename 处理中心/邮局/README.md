# 邮局 —— 四角色信件触发层（可视化 · 自动接力）

> **定位**：通知层。工单库=状态层（邮局绝不改写 status 块），git=代码层（邮局绝不碰 merge/push）。
> **哲学**：机器只出 flag、人终裁——邮局只投递和校验信件，闸门（批方案/合 main）永远在人手里。
> **转正说明**：本目录当前为**未纳管原型**（未走 SYS 票）。好用则立 SYS 票转正（配套红线：信件不进工单库、邮箱树进 .gitignore 或归档规则）。

## 全自动值守（推荐形态：收到信自动干起来）

开四个 CMD 窗口，各跑一个值守（**不再需要人敲"收信"**）：

```
值守-设计师.cmd / 值守-程序员.cmd / 值守-验收员.cmd / 值守-审验员.cmd
```

值守循环盯着自己的 INBOX：**信一到，自动在本窗口唤醒该角色 agent 开工**（默认 Claude Code 无头模式，一信一 fresh session——独立性纪律由结构保证），工具调用和发言实时滚动在窗口里，人随时切窗查看；干完自动发下游信+销信，回到等信状态。

- agent 权限默认 `--dangerously-skip-permissions`（全自动必需）。**含义：信就是指令，只投你审过的信。** 谨慎版：启动前 `set AGENT_ARGS=--permission-mode acceptEdits --allowedTools "Read Edit Write Glob Grep TodoWrite WebFetch"`
- 换 agent：`set AGENT_CMD=kimi`（或 zcode 等，需支持无头/stdin 模式）
- **闸门红线不变**：审验员协议明令**不得自行 merge/push**——通过时只发「建议合 main」通知信，合不合你拍板
- 安全边界=信件边界：值守只处理自己 INBOX 里的信，信封带 payload hash（被篡改会亮红）

## 一封信的旅行

```
设计师干完活 → post send --to 程序员 --type 派单 --payload 派单文件.md
                        ↓ 信落盘（信封+payload 指针+hash）
程序员窗口（值守自动唤醒，或人对 agent 说「收信」）
程序员 agent：读信 → 按 payload 开工 → 干完 post send --to 验收员 --type 验收邀请 …
验收员：收信 → 独立复跑 → 通过:发审验邀请 / 打回:发打回信
审验员：收信 → 终审 → 合 main（人闸门）→ post done
每封信办结：post done <信id> --note "…" → 原信归档 + 自动向发件人投回执
```

## 日常操作（人的全部动作）

| 动作 | 命令 |
|---|---|
| 看谁有信 | `post status`（四格邮况） |
| 到有信的窗口让 agent 开工 | 对 agent 说：**收信** |
| 人查某角色最新信 | `post read 程序员` |
| 办结一封（归档+回执） | `post done LTR-xxx --note "验收通过，已落 ACCEPTANCE_LOG"` |
| 全库体检 | `post check`（信封完整/payload 在位/hash 一致） |

## 防串窗

每个 CMD 窗口先设身份（建议写进各角色启动 bat）：`set POST_ROLE=程序员`。
设了之后，在本窗口以别的角色名义发信会被**拒绝**（机器只出 flag：确认真要跨窗发，加 `--force`）。

## 角色 agent 的收信协议（贴进各窗口角色的提示词/记忆里）

> 你的收件箱在 `安卓中国体系建设\处理中心\邮局\邮箱\<你的角色>\INBOX\`。
> 用户说「收信」时：
> 1. 读收件箱**最早的一封**未办信（用 Read 工具读 `.md`，信封在 `---` 之间）。
> 2. 按 `type` 行事：`派单`→读 payload 文件按派单开工；`验收邀请`→读 payload 交付报告走验收流程（L1 独立复跑/L2 L3 证据链）；`审验邀请`→走终审；`打回`→按理由修复；`回执`/`通知`→知悉即可，向用户转述。
> 3. **一次只办一封**，办完才看下一封；办不了（前置缺失/需要人拍板）→ 不硬办，向用户说明。
> 4. 办完必须：a) 干正事（改码/写报告/落日志，按原流程走，不因邮局改变交付纪律）；b) 投下一封信：`node 安卓中国体系建设\处理中心\邮局\post-office.mjs send --to <下游> --type <型> --re "…" --payload <你的产物路径>`；c) 销信：`… post-office.mjs done <信id> --note "一句话"`。
> 5. 信件只做触发与指针：**权威永远是工单库 status 块与盘上正式文件**——信与库冲突时以库为准并提示用户。

## 信封字段

`id / from / to / type（派单·验收邀请·审验邀请·打回·回执·通知）/ re（事由）/ created / status / payload / sha`
payload 存 hash（sha256 前 16 位），`post check`/`read` 会校验——**信在途中活儿被改了会亮红**。

## 命令速查

```bash
POST=post-office.mjs   # 或 Windows CMD 用同目录 post.cmd
node $POST init
node $POST status
node $POST send --to 验收员 --type 验收邀请 --re "UPG-126 批1 交付" --payload 程序员/交付报告/DELIVERY_UPG126.md
node $POST read 程序员
node $POST done LTR-20260909-153000 --note "已合 main c753e8a"
node $POST check
```

测试隔离：设 `POST_ROOT` 环境变量可把邮箱树指到别处（如 `C:\tmp\post-test`），不污染正式邮箱。

## 信件边界（2026-09-11 用户拍板：什么能成信、什么不能）

> 规范全文：`处理中心\汇报区\信件边界规范_草案_2026-09-11.md`。实证：全库 848 封 = 回执 56% + 通知 22%（知悉类 78%）——信量膨胀的正主。

**三条铁律**：①**信=动作**（一封信只承载「需要对方做的一个动作」——没有动作，不是信）②**权威在账本**（工单库 status 是真相源，信只是触发与指针——能用状态变更表达的，不发信）③**一信一事**（不群发/不广播/不夹带/不闲聊，办完即销）。

**能成信**：现有 11 类白名单（派单/验收邀请/审验邀请/合并邀请/裁决/打回/挂起/疯狗/卫生通报 + **通知收紧**=仅限「需触发+必须留痕」，纯知悉不得用 + **回执降级**=归档化不进 INBOX）。

**不能成信（八禁）**：纯确认/纯知悉/状态结果广播（改账本+看板表达）/能改账本表达的/监控告警（走故障.log、看板）/文件本体（只带 payload 指针+hash）/群发/闲聊。附：「等人动手」类堵点（配 key/物理动作）不得埋信里——走人工待办位。

**发信前四问**：①对方要做动作吗？②能由账本变更表达吗？③需要留痕+ref 链吗？④是纯确认吗（是→归档化不进箱）。

度量目标：回执占比 ≤20%（现 56%）；箱深 ≤10；已答未销=0。存量不回改，新信即守。工具提示（send 自检软提示）随 SYS-38 批落地。
