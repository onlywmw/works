## 三、双通道口径（信 vs 实体，2026-09-09 定）

- **信 = 通知层指针**（邮局信件：告诉下游"有你活了+文件在哪"），**实体文件 = 权威**，必须落本 README 第二节所列落点
- 角色卡教 agent 发信；收到信的 agent 按 payload 路径读实体文件干活——**禁止把实体内容写进信里当第二真相**
- 判定口诀：**信可丢（有归档），实体不可丢（是账）**

### 信量边界（SYS-38 @2026-09-12 用户令·减负）

- **判据**：**对方需要动手吗？需要=信｜只需知道=状态位｜查账才用=文件**
- **走信清单**（唯一穿透形态）：派单 / 打回 / 裁决 / 验收邀请 / 审验邀请 / 合并邀请 / 工序完工 / 卫生通报 / 告警 / 挂起 / 疯狗
- **不走信四类**：纯知悉回执 / 同角色笔记 / 无事心跳 / 工序中碎念（→ 状态位或直接落文件）
- **回执归档化**：`done` 自动回执**不再投对方 INBOX**——直接入归档（`read <角色> <id>` 可查）；看板信量格「处理」=**闭环数**（回执不计）
- **回复即销**：发出非回执信且 `ref` 指向自己 INBOX 的原信 → 原信自动销归档（单份留档，不留双份）
- **哨兵口径不变**：巡铃/疯狗/看门狗/专线/卡单 均以 INBOX 实态为输入——回执归档化后 INBOX 更干净，判据零弱化（SYS-38 构造案复核）

## 四、流转（两条路，同一本账）

**人工路（邮局信件流）**：设计师派单信 → 程序员施工+交付报告+发验收邀请信 → 验收员独立复跑+结论+发审验邀请信 → 审验员终审（打回按根因路由：程序→程序员/证据→验收员/方案→设计师重走）→ **回设计师合并位**（设计师执行 git 合并+merged 登记——回环：单子从哪来回哪去）

**机器路（流水线）**：`mov new <工单号>`（须先在工单库建卡）→ 四角回环自动流转（设计师🚦→程序员→验收员→审验员→设计师·合并位🚀→完成），阶段迁移自动 set-status 回写工单库；校验不过原地亮红；打回 `mov reject <号> --to <角色>`

**两路同账**：`工单库.md`（本中心根层，2026-09-09 自体系根迁入）= 唯一权威，信/看板/看板全是投影；对账用 `mov audit`。

## 挂账登记与转工单规则（2026-08-17 定；2026-09-09 自散文件并入手册——四合一先例）

## 一、谁能登记

**任何人**——验收员 / 程序员 / 设计师 / 用户。在工作、验收、施工、真机测试中发现**缺陷 / 观察项 / 挂账**（P2 以上或需跟进），**当场登记**，不等口头汇报。

## 二、怎么登记（挂账登记表加一行）

在 `问题区\挂账登记表.md` 表格加一行：

| 列 | 填法 |
|---|---|
| 挂账号 | `挂账-<简短描述>`（如 `挂账-approval-always-gate`）|
| 标题 | 缺陷/挂账名（一句话）|
| 优先级 | P0-P3（拿不准往高定）|
| 现象→证据→建议 | `现象 → 证据（代码位置/截图/计数）→ 建议` |
| 登记人 / 日期 | 谁发现的 / 当天 |
| 设计师验证 | **`⏳挂账待审`** |
| 施工/转工单 | — |

> **登记挂账不备份任何表**——挂账表是追加式文本，不动权威表（告别每次登记产生 .bak）。
> 复杂缺陷可附工单文档到 `程序员\`。

## 三、设计师验证

设计师审核「⏳挂账待审」挂账（**查代码/证据/复现，不信自报信实物**）：
- **通过** → 挂账登记表「设计师验证」列改 `✅已落实` → **转正式工单**：在 `工单库.md` 登记新工单（**此时改库前备份一次**，`工单表.bak_<日期>_<动作>前.xlsx`），进派单队列
- **疑义** → 打回登记人补证（写清缺什么）或标「不落实」销项

## 四、转工单后

进派单队列 → 程序员施工 → 验收员验收 → 设计师合 main（按既有流转）。

**沉淀进已知坑库（2026-09-01 定 · SYS-01 P1-2，半自动）**：挂账验证解决并**转工单完成后**，追加一步——
1. 设计师/程序员把该条挂账的「现象→根因→药方」提取进 `设计师\知识库\已知坑.md` 新增一行
2. 挂账登记表原条目「施工/转工单」列追加：`→ 已解决，转入已知坑库（坑名: <坑名>）`
3. `已知坑.md` 条目「关联工单」列填：`挂账-<id> → 转工单 <UPG-xx>` —— **双向可追溯**

> 挂账表流程（红线 10）不动，只在「转工单完成」节点加一步沉淀；已解决不重收进挂账待审池。

## 五、红线

1. 登记即挂账，**不删除他人登记**（疑义走打回/销项，不直接删）
2. 真机补验类挂账走工单库「真机补验挂账」区，**不转工单**（归真机检验员）
3. 不主动收集挂账——仅**工作中被动发现**的缺陷/挂账登记
4. **备份只发生在转工单写工单库时**（登记挂账不备份，避免 bak 堆积）
5. **主文件夹不乱建登记表**：工单流转中心根目录只放核心流转文件；登记表/临时表放各角色报告处，**不堆主文件夹**；确需主文件夹新增表 → 交设计师评估

## 八、测试匹配原则（2026-08-17 定 · 派单测试强度 = 工单性质）

| 工单性质 | 测试要求 |

| **代码改动**（动项目源码）| 单测 + 变异亲杀 + 全量测试（命令见仓库根 `README.md` §一.2 仓库与构建）（必要）|

| **纯配置/接线** | 验证生效 + 定向测试 |
| **评估/报告** | 报告 + 实证，无施工测试 |

**判断**：动项目代码 → 才要单测/变异/全量；不动代码（装环境/验证外部）→ 真机证据，不堆 gradle。
