# 工单系统改造方案 v3.1（对照《Automated Alignment Researchers》诊断 · 实施定稿版）

> 日期：2026-09-01
> 定位：审计/制度层改造 —— 不推翻现有制度，只补「可靠算数」的防伪/抗倒退缺口
> 参考：Anthropic 《Automated Researchers Can Reliably Mitigate Alignment Failures》(2026-08)
> v3.1（实施定稿）：v3 已签通过（9.4/10）。按终审吸收 3 个文字收口项——①delivery_id 任意核心对象变化必新交付、不可原地改 ②evidence_manifest 明确为不可变证据清单（每条含 evidence_id/path/sha256/producer/created_at），manifest_sha 为其内容哈希 ③PARTIAL 必须有设计师显式裁决记录（decision/reason/decided_by/decided_at）。**不新增机制/角色/节点/库/分类，只收口实施规范，进入实施。**

## 〇、方案定位

不推翻现有制度——现状红线 21 条、证据链四环节、变异亲杀、独立审验、分层溯源、合 main 抽查都是对的。本方案只补 **5 个缺口**，全部落在"可靠算数"的防伪/抗倒退上。

**评审定调**：方案价值 = 建立**"工单结论的可证明性"**，核心思想一条主线：

> **标准先冻结 → 交付后绑定 → 证据再审验 → 能力防倒退 → 历史可复用 → AI 只做机械检查，人保留最终裁决。**

v3 定稿原则：**机器负责算，人负责判断**。核心防御从"防止人犯错"转为"防止结果出来后系统无法证明这个结果怎么来的"。

## 一、现状一句话概述

| 维度 | 现状 |
|---|---|
| 角色 | 设计师（出单）→ 程序员（施工）→ 验收员（代码+真机）→ 审验员（AI 审证据链）→ 设计师（合 main 单点） |
| 铁律 | 不信自报信实物；合 main 只归设计师且需真机通过；证据链四环节（journal/截图/命令/时间一致） |
| 已有防伪 | 变异亲杀、全量回归、分层溯源(§七)、合 main 抽查防幻觉(§六)、挂账→验证→转工单 |
| 权威 | `工单库.md`（真相/派单源）+ `工单表.xlsx`（Excel） |
| 弱点（靶点） | ①验收标准不"冻结" ②交付 hash 不"绑定" ③只防"证据缺"不防"证据假/行为伪" ④无"未测维度不倒退"护栏 ⑤无"共享坑位库" |

## 二、核心：一条不可篡改的因果链 + 两条红线

### 因果链（一切结论都挂在固定对象上）

```text
ticket_id
  └─ standard_id        ← 标准先冻结：验收"什么是合格"在派单时定死
        └─ delivery_id  ← 交付后绑定：这次交付"到底是什么"用业务身份锁定
              ├─ code_commit_sha
              ├─ artifact_sha
              ├─ evidence_manifest_sha
              └─ standard_id / delivered_at / delivered_by
          └─ evidence_id ← 证据再审验：证据是否可信
        └─ acceptance_result ← 合格结论
```

### 红线 R1：Hash ≠ 身份（架构边界）

> **hash 用于完整性校验，不承担业务身份职责。**

- **身份**（你是谁）：`ticket_id` / `delivery_id` / `standard_id` / `evidence_id`
- **完整性**（你有没有变）：`sha256`

禁止：`if hash==xxx: passed` 这种把 hash 当身份/结论的写法。否则重新掉回"看似可靠"的坑。

### 红线 R2：不可变对象，修订即派生新版本

> **任何标准/交付/证据版本一旦被用于验收，永久保留；不得删除、覆盖、复用。修订 = 派生新版本，不覆盖旧版。**

## 三、改造方案（P0/金，P1/银，P2/铜）

### P0-1 验收标准「冻结」机制

**目的**：堵"事后合理化"。验收"什么是合格"在派单时定死。

**工程契约（评审定死）**：
1. **唯一正式冻结版**：每个工单只允许一个正式冻结版，含不可变 `standard_id`：

```text
standard_id: STD-UPG-054-v1
content_sha256: xxxxxxxx      （内容完整性，非身份）
frozen_at: 2026-09-01T01:20:33
frozen_by: 设计师
approved_by: 审验员
```

2. **内容分两块**（`STD.md`）：
   - **冻结区**：L1/L2/L3、变异锚、测试匹配档——不可改。
   - **追加说明区**：任何人可加（注时间/作者/触发原因）；**默认不作为合格判定正向证据**（"事后合理化"单独存放）。
3. **修订 = 派生，不可覆盖**：修订必然产出**新版本号**（`STD-UPG-054-v2`），**禁止覆盖 v1**；修订需设计师+审验员共批；修订版不计入首次验收合格判定。**任何版本曾被验收即永久保留。**
4. **自动化校验**：验收✅/审验/合main抽查三处，比对当前引用标准与冻结版 `content_sha256`；不一致 → 阻断 + 提示"标准已变更，需重新冻结或走修订"。

**权责**：设计师出冻结版；验收员/审验员对账引用冻结版；追加只入追加说明区。
**落点**：`处理中心\验收标准冻结区\<工单号>\STD-<工单号>-v<n>.md`。

### P0-2 交付 hash「绑定」机制

**目的**：防"验收旧版、改新版"覆盖事故（UPG-54 已现苗头）。

**工程契约（评审定死）**：
1. **引入 `delivery_id` 作业务身份**（不让 hash 当身份）：

```text
DEL-UPG-054-20260901-001
├── commit_sha
├── artifact_sha
├── evidence_manifest_sha
├── standard_id
├── delivered_at
└── delivered_by
```

**收口 ① delivery_id 不可原地修改**：已创建的 delivery_id 不允许原地更新。任何参与验收的代码、最终产物或关键证据发生变化 → **必须新建 delivery_id**；旧 delivery_id 永久保留并标失效。禁止 `DEL-001.artifact_sha = A → 后来改 B` 这种原地更新（会破坏不可变交付）。`DEL-001 / DEL-002` 全部 immutable。

**收口 ② evidence_manifest 数据结构**：`evidence_manifest` 是一份**不可变证据清单**，每条至少含 `evidence_id / path / sha256 / producer / created_at`；`evidence_manifest_sha` 是该清单内容的 SHA-256（**不是"把几个证据 hash 拼起来再 hash"**，而是清单这一结构体的内容哈希）。

```text
DEL-001
  └── evidence_manifest
       ├── EVID-001 (id / path / sha256 / producer / created_at)
       ├── EVID-002
       └── EVID-003
              ↓
       manifest_sha256
```

此后增/删/替换/修改任一证据 → `manifest_sha` 变化 → delivery 失效，证据链闭合。

2. **三重 hash 绑定**：代码分支/commit、最终产物（APK/可执行）、关键证据（manifest_sha）——**三者必须同时匹配**。只绑代码不够（代码 A / 产物 B / 证据 C 可能非同时产出）。

3. **失效标记（弃用"自动回滚"措辞）**：检测到 hash/manifest_sha 变化 → 将该 delivery 标「⏳失效」，原验收结论**保留但不再生效**，工单表新增行"待重新验收"（新 delivery_id）。系统可直接回答"UPG-54 为何重验？→ 旧 DEL-001 失效，原因 artifact sha 变了"。

4. **自动化比对**：验收员/审验员工具链加"hash 一致性检查"，每次打开工单自动比对绑定 hash vs 实际交付物，不一致立即提示。

**权责**：程序员交付登记 delivery_id+三重 hash；验收员绑定；此后 hash 变化自动失效（不依赖人工改状态）。
**落点**：工单表备注列 + 审验工具。

### P0-3 反伪审验

**目的**：从"防证据缺"升到"防证据假/行为伪"。

**工程契约（评审定死——两层分离 + 人工最终裁决）**：

#### 层 A：行为欺骗模式（Behavioral Suspicion）—— 四分类

| 类别 | 检测信号 | 工具/方法 |
|---|---|---|
| ①原样重跑 | 交付内容与上次几乎相同，仅时间戳/窗口变化；hash 变了但 diff 空/极小 | `git diff`、文件 hash 对比、日志时间线 |
| ②基准过拟合 | 测试代码引用基准/产物本身；断言只查"存在"不查语义；覆盖率异常高但断言弱 | 静态扫描引用路径；人工抽查断言质量 |
| ③语义模糊化 | 报告描述与代码行为不一致；"已支持 X"但 X 只被 mock/固定值 | 报告 vs 实现比对；关键函数调用链 |
| ④时序不一致 | 截图/日志时间早于工具调用；虚假时间戳 | 时间线排序；截屏元数据 vs journal 顺序 |

输出字段改为 `integrity_flags`（**flag 不是结论**）：

```json
{
  "original_rerun": false,
  "benchmark_overfit": true,
  "semantic_vagueness": false,
  "time_inconsistency": false
}
```

#### 层 B：证据对象真实性（Evidence Integrity）—— 独立层，不混入四分类

> 前四类判"行为有无欺骗模式"；这一层判"证据对象本身是否可信"。

```text
Evidence Integrity
├── file exists
├── hash matches
├── timestamp plausible
├── producer known
├── source path valid
└── chain intact
```

#### 人工最终裁决（机器只判 flag，人判结论）

```text
integrity_flags（机器）→ integrity_review（人工）
  status: confirmed / cleared / unresolved
  reviewer: xxx
  reviewed_at: xxx
```

**关键约束**：`integrity_flags` 只作标记，**绝不自动等价"不通过"**。最终判定由人工完成。

**我的补充——`unresolved` 必须有归属退出路径**（防永久挂起）：人工复核未决 → 必须落到 排除（cleared）/ 确认（confirmed，转挂账登记表）/ **挂账转工单**；**不允许无归属的"未决"长期滞留**。给未决设超时（如 3 个工作日），超时 → 转挂账待设计师定夺。

**权责**：审验员逐工单核两层；设计师合 main 前复核结论；脚本只出 flag。
**落点**：`审验员\README.md` 检查点表（四分类+integrity 层）+ `审验.py` 输出 `integrity_flags` + `integrity_review`。

### P1-1 能力不倒退护栏

**目的**：防"单点优化破坏未测维度"（MOV 共享面最易踩）。

**工程契约（评审定死——`coverage_status` 三档）**：

**共享面变更声明**：改动涉及下列共享面之一 → 必附《共享面影响清单》：
- MainActivity 注册表；工具面（公共函数/脚本/配置）；协议/接口定义；全局数据结构。

清单含：改哪个共享面 → 影响哪些下游调用方 → 为何无副作用 / 已做哪些回归。并把"未覆盖"正式化为 `coverage_status`：

```text
coverage_status:
  FULL    → 直接通过能力护栏
  PARTIAL → 必须写明：未覆盖维度 + 风险(低/中/高) + 是否允许合main(是/否) + 裁决人(设计师) + 裁决记录
  NONE    → 原则上「共享面变更 + NONE = 不允许合 main」
```

**收口 ③ PARTIAL 裁决责任**：PARTIAL 不能由程序员或验收员单独放行——**必须存在设计师的显式裁决记录**，含 `decision / reason / decided_by / decided_at`。例如：

```json
{
  "coverage_status": "PARTIAL",
  "uncovered": "协议异常重连路径",
  "risk": "medium",
  "merge_decision": "approved",
  "reason": "当前变更仅影响 UI 注册层，协议路径未改动；已有历史回归覆盖",
  "decided_by": "设计师",
  "decided_at": "2026-09-01T..."
}
```

防 PARTIAL 退化成"大家觉得应该没问题"。

**验收硬门槛**：`全量回归 0 新增失败 + 共享面变更清单无未声明已知风险`。
**风险提示**：全量回归 0 新增失败 ≠ 能力没倒退（"没发现失败" ≠ "没倒退"）——未测维度可能已坏，故 `NONE` 强制禁止合 main，`PARTIAL` 需设计师显式裁决。

**权责**：程序员/设计师出清单+coverage_status；验收员核硬门槛；设计师就 PARTIAL/NONE 裁度。
**落点**：交付报告固定一节 + 验收判定标准。

### P1-2 共享「已知坑库」+「复用件表」

**目的**：减重复踩坑 + 重复施工（论文消融：共享历史 > 每重搜）。

**工程契约（评审定死——生命周期干净 + 复用件收紧）**：
- **边界**：挂账表=未解决；坑位库=已解决。**未解决→挂账；解决→自动沉淀→已知坑；过时→标过时**。
- **自动沉淀**：挂账条目验证解决并转工单完成 → 自动/半自动提取到"已知坑.md"；条目加"已解决→转入已知坑库"链接，双向可追溯。
- **条目时效**：适用版本/日期、关联工单号、解决状态（已验证/疑似/已过时）、最后验证时间；定期清理过时。
- **复用件更严格**（防变垃圾仓库），字段：`component_id / 版本 / 适用范围 / 最后验证时间 / 关联工单 / 验证状态 / 使用次数 / 已知限制`。
- **出单前查询强制**：派单模板加字段「已查坑位库/复用件库：是/否，命中条目：___」；不填或填"否"且无说明 → 审验员可退回。

**权责**：设计师出单前必查并填字段；审验员核对字段；设计师维护时效。
**落点**：`设计师\知识库\`（已知坑.md + 复用件.md）。

### P2-1 AI 干机械活（人定基准 + 裁边界）

**目的**：把人类从机械核验解放（论文 $4/h AI vs $150/h 人）。

**优先级**：
- **第一优先**：伪通过预筛（④时序/①原样重跑）、hash 一致性比对、证据链对账（文件存在/时间线顺序）。
- **第二优先**：截图 OCR、时间一致性比对。
- **保留人工**：最终是否达标、边界仲裁、语义模糊化深度审、共享面无副作用合理性。脚本只出 flag 不判结论（同 P0-3）。

**权责**：AI 出预筛标记，人类裁决。

## 四、《工单状态机 v1》（评审唯一强烈建议补的 P0）

把冻结/交付/失效/重验/修订/驳回/合 main 全部做成状态转移表，实施时按此落地：

### 主路径

```text
草稿 → 已冻结 → 已派单 → 施工中 → 已交付 → 待验收 → 验收通过 → 待审验 → 审验通过 → 可合main → 已合main
```

### 异常 / 分支路径

**交付失效（hash 变化）**：
```text
已交付/待验收/验收通过
  └─ hash 变化 → 验收失效 → 待重新验收（新 delivery_id；旧结论保留但失效）
```

**标准修订**：
```text
已冻结 → 申请修订 → 设计师+审验员共批 → 新标准版本(STD-v<n+1>) → 重新验收
```

**反伪**：
```text
integrity_flags 异常 → 人工复核 → 排除(cleared) / 确认(confirmed→挂账) / 未决(unresolved)
  未决 → 超时(3工作日) → 转挂账待设计师定夺   ← 防永久挂起
```

**能力护栏（PARTIAL/NONE）**：
```text
FULL → 通过
PARTIAL → 设计师裁决(是否允许合main)
NONE → 原则上禁止合main
```

### 状态-权责表

| 状态 | 进入条件 | 离开动作 | 负责角色 |
|---|---|---|---|
| 草稿 | 设计师立项 | 冻结标准 | 设计师 |
| 已冻结 | 标准冻结 approved_by 审验员 | 派单 | 设计师 |
| 已派单 | 派单文本下发 | 程序员领单施工 | 设计师 |
| 施工中 | 程序员认领 | 交付报 hash | 程序员 |
| 已交付 | 登记 delivery_id+三重 hash | 验收 | 程序员 |
| 待验收 | 交付登记 | 验收员核标准/证据 | 验收员 |
| 验收通过 | 标准冻结版对账一致 + 证据链完整 | 送审验 | 验收员 |
| 待审验 | 验收通过 | 审验员核 integrity | 验收员→审验员 |
| 审验通过 | integrity 无确认异常 | 可合 main | 审验员 |
| 可合main | 审验通过 + 能力护栏过 | 设计师合 | 设计师 |
| 已合main | 合入主分支 | 归档销单 | 设计师 |
| 验收失效 | hash 变化 | 待重新验收 | 系统自动 |

## 五、文件夹设计分类改造

保留 v1/v2 结构，收敛三处：

```
工单流转中心\
├── README / 项目配置 / 工单库.md / 工单表.xlsx
├── _备份归档\                      ← 只存 .xlsx 工单表备份（数据备份）
├── 处理中心\
│   ├── README / 挂账登记表.md / 挂账登记与转工单规则.md
│   ├── 验收标准冻结区\               ← 【新】P0-1：STD-<工单号>-v<n>.md
│   ├── 建议区\ 汇报区\ 问题区\
│   └── 归档\                        ← 存已完成工单文档/证据/交付报告（文档留档）
├── 设计师\
│   ├── README.md（+§六§七§八）
│   ├── 方案设计\ 设计网络\ 派单\ 立项输入\ 风格统一\ 维度工单表底稿\
│   └── 知识库\                      ← 【新】P1-2：已知坑.md + 复用件.md
├── 程序员\（交付报告\ / 工单文档\ / 证据目录）
├── 验收员\（文档\ / _tools\ / 总览\ / 证据数据\）
└── 审验员\（README / 单证状态 / 映射 / 规范 / 审验.py / 证据数据）
```

**收敛三处**：
1. **`检查证据\`**：优先移入对应角色证据区；迁移**必须全局更新引用路径**（grep 防死链）；若保留根级，只放"进行中"临时证据，完成后立即归档删除。
2. **`归档\` vs `_备份归档\` 边界**：`_备份归档\` = .xlsx 表备份；`归档\` = 已完成工单文档/证据/交付报告。README 写死边界防混放。
3. **证据归属唯一化**（写入红线/证据链规范）：**同一工单证据只允许存在于"产出该证据的角色"证据目录下**；其他角色只允许引用路径，不得复制副本（防多份不一致，UPG-01 批 3-3 教训）。
