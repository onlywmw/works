# 交付绑定规范（P0-2 · SYS-01 引入）

> **「这次交付到底是什么」的业务身份 + 完整性锚定。** 每个交付用 `delivery_id` 锁身份、用三重 hash 锁内容，防「验收旧版、改新版」的覆盖事故（UPG-54 已现苗头）。
> 出处：`SYS\改造计划_工单流转中心防伪抗倒退_2026-09-01.md` §P0-2（v3.1 实施定稿）。
> 配套：`处理中心\验收标准冻结区\README.md`（P0-1，标准冻结）+ 根 `README.md` 红线 22/23。

---

## 〇、一句话

**交付时登记一个不可变的 `delivery_id`，并把「代码 commit / 最终产物 artifact / 证据清单 evidence_manifest」三样东西的哈希同时绑到它上面；任何一样变了，这个交付就自动失效，必须新建交付，不能原地改。**

---

## 一、红线：Hash ≠ 身份

- **身份（你是谁）**：`ticket_id` / `delivery_id` / `standard_id` / `evidence_id` —— 业务身份，用固定编号。
- **完整性（你有没有变）**：`sha256` —— 只校验内容是否被改。

**禁止** `if hash==xxx: passed` 把 hash 当身份/结论的写法。判断「该不该信这次交付」看 delivery_id 与它的绑定状态，不是看某个 hash 值。

---

## 二、delivery_id（业务身份）

**格式**：`DEL-<工单号>-<YYYYMMDD>-<NNN>`

| 段 | 说明 |
|---|---|
| `<工单号>` | 与 `ticket_id` 一致（如 `UPG-054`） |
| `<YYYYMMDD>` | 交付日期 |
| `<NNN>` | 同日同单递增序号，001 起 |

**示例**：`DEL-UPG-054-20260901-001`、`DEL-UPG-054-20260901-002`

**收口 ① delivery_id 不可原地修改**：
- 已创建的 `delivery_id` **不允许原地更新**任何字段。
- 参与验收的代码、最终产物、或关键证据任何一样发生变化 → **必须新建 delivery_id**（新序号）；旧 delivery_id **永久保留并标失效**。
- 禁止 `DEL-001.artifact_sha = A → 后来改 B` 这种原地更新。`DEL-001 / DEL-002 …` 全部 immutable。

---

## 三、三重 hash 绑定（三者必须同时匹配）

每次交付登记三样哈希，**缺一不可**（只绑代码不够：代码 A / 产物 B / 证据 C 可能非同时产出）：

| 绑定项 | 含义 | 来源 |
|---|---|---|
| `code_commit_sha` | 交付所对应的代码分支 commit | `git rev-parse HEAD` |
| `artifact_sha` | 最终产物（APK/可执行）的 SHA-256 | 产物文件 sha256sum |
| `evidence_manifest_sha` | 证据清单（evidence_manifest）内容哈希 | 见 §四 |

绑定关系图：

```text
delivery_id
  ├── code_commit_sha
  ├── artifact_sha
  ├── evidence_manifest_sha
  ├── standard_id          ← 挂到标准冻结版
  ├── delivered_at
  └── delivered_by
```

---

## 四、evidence_manifest 不可变证据清单

**收口 ② evidence_manifest 是一份不可变证据清单**，每条至少含五字段；`evidence_manifest_sha` 是**清单这一结构体的内容哈希**（不是「把几个证据 hash 拼起来再 hash」）。

### 4.1 结构（JSON）

```json
{
  "delivery_id": "DEL-UPG-054-20260901-001",
  "standard_id": "STD-UPG-054-v1",
  "code_commit_sha": "443b288…",
  "artifact_sha": "sha256:xxxx…",
  "delivered_at": "2026-09-01T10:20:33",
  "delivered_by": "程序员-C",
  "evidence_manifest": [
    {
      "evidence_id": "EVID-001",
      "path": "程序员/UPG28-evidence/upg28_01_ask_dialog.png",
      "sha256": "xxxx…",
      "producer": "程序员",
      "created_at": "2026-09-01T10:21:00"
    },
    {
      "evidence_id": "EVID-002",
      "path": "验收员/证据数据/2026-08-30/UPG-28/journal.jsonl",
      "sha256": "xxxx…",
      "producer": "验收员",
      "created_at": "2026-08-30T15:00:00"
    }
  ]
}
```

### 4.2 manifest_sha 计算

- `evidence_manifest_sha` = `SHA-256( evidence_manifest 数组内容的规范化 JSON 序列化 )`。
- 规范化 = 键按字典序、无多余空白、UTF-8。**只对 `evidence_manifest` 数组算**，不含 delivery_id 等外层字段（外层字段已是身份，变了就新建交付）。

```bash
python - <<'EOF'
import hashlib, json
manifest = [ {"created_at": "...", "evidence_id": "...", "path": "...", "producer": "...", "sha256": "..."}, ]
canon = json.dumps(manifest, sort_keys=True, ensure_ascii=False, separators=(",", ":")).encode("utf-8")
print(hashlib.sha256(canon).hexdigest())
EOF
```

### 4.3 不可变语义

此后 **增 / 删 / 替换 / 修改** 任一证据 → `evidence_manifest_sha` 变化 → 该 delivery 失效，证据链闭合被打破。

---

## 五、失效标记（不用「自动回滚」措辞）

检测到 `code_commit_sha` / `artifact_sha` / `evidence_manifest_sha` 任一变化：

1. 该 delivery 标 **「⏳失效」**；
2. 原验收结论**保留但不再生效**（历史可溯，不删）；
3. 工单表新增行「待重新验收」，挂**新 delivery_id**（新序号）；
4. 系统/人可直接回答「该单为何重验？→ 旧 DEL-001 失效，原因 artifact_sha 变了」。

```text
DEL-001（有效）——artifact 变 → DEL-001（⏳失效）→ 新建 DEL-002 → 待重新验收
```

## 六、登记流程与落点（谁登记 / 谁绑定）

| 步骤 | 谁 | 动作 |
|---|---|---|
| ① 交付登记 | 程序员 | 交付完成时生成 `delivery_id` + 三重 hash + `evidence_manifest`，写进交付报告固定节（见 §七） |
| ② 绑定登记 | 程序员 | 工单表该行「delivery_id」列填 `DEL-xxx`（含绑定摘要），README 红线 7 同步完成 |
| ③ 验收对账 | 验收员 | 验收时比对绑定 hash vs 实际交付物，不一致 → 打回 |
| ④ 审验对账 | 审验员 | 审验时重算 `evidence_manifest_sha` 比对绑定值，不一致 → 问题区登记 |
| ⑤ 合前抽查 | 设计师 | 合 main 抽查时核对 delivery 状态非失效 |

**落点**：
- 工单表：新增 **「delivery_id」列**（I 列）。
- 交付报告：固定「交付绑定」一节（§七）。
- 审验工具：`审验员\审验.py` 增加 hash 比对（属 P2 自动化；本阶段先落规则 + 可手动重跑命令）。

## 七、交付报告固定节（程序员交付报告新增）

每份交付报告在头部信息后追加：

```markdown
## 交付绑定（P0-2）
- delivery_id: DEL-<工单号>-<YYYYMMDD>-<NNN>
- code_commit_sha: <git commit>
- artifact_sha: <sha256:...>
- evidence_manifest_sha: <64hex>
- standard_id: STD-<工单号>-v<n>
- delivered_at / delivered_by: <...>
- evidence_manifest: 见 <manifest 文件路径 或 本报告附表>
```

## 八、对账命令（阶段一可手动执行）

```bash
# 1) 代码 commit
git rev-parse HEAD

# 2) 产物 hash
sha256sum <apk/可执行文件>

# 3) evidence_manifest_sha（重算比对）
python -c "import hashlib,json; m=<evidence_manifest>; print(hashlib.sha256(json.dumps(m,sort_keys=True,ensure_ascii=False,separators=(',',':')).encode()).hexdigest())"
```

## 九、与既有制度的关系

- 复用既有红线 7（完成即登记两个表）与红线 9（工单表写入五步铁律）——`delivery_id` 列写入同样适用。
- 不新增角色：登记=程序员，绑定对账=验收员/审验员/设计师，全部是既有职责。
- `delivery_id` 是因果链 `standard_id → delivery_id → evidence_id → acceptance_result` 的中间身份，向上挂 `STD`，向下挂证据（见 `验收标准冻结区\README.md` §七）。
